# スラッシュコマンド / Skill / サブエージェントの使い分け

ハーネスの資産を `.claude/` のどこに置くかの基準。根拠は `docs/adr/0012-issue-command-as-slash-command.md` 決定1、および ADR 0010 §D（サブエージェントは工程で分割する）。

**置き場所を間違えると、動くには動くが「起動されなかったこと」が観測できなくなる。** この文書が守ろうとしているのはその1点である。

> **現時点で `.claude/skills/` は存在しない**（ADR 0010 の実装 Issue 3 は未着手）。本基準は最初の Skill を作る前に定めたものであり、**Skill の欄は実運用の裏付けを持たない**。実際に Skill を導入した時点で、ここに実測を反映すること。

---

## 4つの置き場所

| 置き場所 | 実体 | 起動するのは誰か |
|---|---|---|
| `.claude/commands/` | スラッシュコマンド（プロンプト） | **人間**が `/<name>` と明示的に叩く |
| `.claude/skills/` | Skill（プロンプト＋手順） | **モデル**が文脈から自律的に選ぶ |
| `.claude/agents/` | サブエージェント（プロンプト） | **親エージェント**が Task で呼ぶ（人間の直接呼び出しも可） |
| `.claude/hooks/` | hook（シェルスクリプト） | **ランタイム**がイベントで機械的に発火させる |

hook は前3者と並ぶ選択肢ではない —— **持てるのは「イベントで判定できること」だけ**である。だが強制力の軸で唯一の実効手段なので、比較対象として並べる。

## 判断の3軸

### 軸1 — 誰が起動するか（＝起動されなかったときに気づけるか）

**これが最も重要な軸である。**

| 起動者 | 起動しなかった場合 |
|---|---|
| ランタイム（hook） | **起こらない**。イベントが発生すれば必ず走る |
| 人間（コマンド） | **人間には分かる**（自分が打たなかった）。**機械には分からない** |
| モデル（Skill） | **誰にも分からない**。モデルが選ばなかったことは、資産が存在しないことと観測上区別できない |
| 親エージェント（サブエージェント） | 親のプロンプト次第。親が呼ばなければ走らないが、**親の指示文に手順として書ける** |

**必須の入口をモデルの選択に委ねない。** 「モデルが選ばなかった」は最も検出しにくい失敗であり、ADR 0011 が「既定の入口」を否定した理由（既定は選択の初期値でしかなく、選択を止める力を持たない）と同じ構造を持つ。

逆に、**走らなくても損害が無いもの**（書式の参考、任意の補助手順）はモデルの選択に委ねてよい。判断基準は「走らなかったときに何が素通りするか」である。

### 軸2 — 強制力

| 実体 | 強制力 | 根拠 |
|---|---|---|
| hook | **機械的**。終了コードでプロンプト／ツール呼び出しをブロックできる | `.claude/hooks/check-prompt-entry.sh` は工程をまたぐ依頼を実際に止める |
| コマンド / Skill / サブエージェント | **弱い**。すべてプロンプトであり、「そう書いてある」は「そう振る舞う」を保証しない | ADR 0012「悪い影響」 |

**プロンプトに書いたことは検査されていない。** これは自明だが最も忘れやすい性質である。プロンプト側の資産に「必ず停止する」「必ず確認する」と書いても、それは宣言であって担保ではない。

**したがって、担保が要る部分はプロンプトから切り出す**（下記軸3）。

### 軸3 — 機械検査できるか

| 対象 | 検査できること | 検査できないこと |
|---|---|---|
| シェルスクリプト（hook / 切り出した判定部） | **入出力の全条件**（fixture で固定できる） | 実環境の前提が変わったこと（`gh` の出力形式、ランタイムのバージョン） |
| プロンプト（コマンド / Skill / サブエージェント） | **参照が張られているか**（grep で確認できる） | **記述内容が仕様どおりか。手順が守られたか** |

**解釈の余地なく決まる部分は、プロンプトからシェルスクリプトへ切り出す。** 先例は `.claude/hooks/check-prompt-entry.sh` + `test-check-prompt-entry.sh` + `make test-hooks`、および `.github/scripts/check-review-trail.sh` + `make test-scripts`。

切り出したスクリプトには次を要求する。

- **stdin と引数以外の入力を持たない純粋なフィルタにする。** ネットワークアクセスを内包しない
- **入力を差し替えればローカルで完全に実行でき、fixture で検査できること**
- **`make` ターゲットを持ち、`make test` の依存に入り、CI から呼ばれること。** 3つすべてを満たす。1つでも欠けると、テストが存在するのに実行されない状態が生まれる（Issue #30 で実際に踏んだ。`docs/harness/verification-loop.md`「CI の構成」の注記）

**「生成」は切り出せない。「検証」だけが切り出せる。** 日本語から英語スラグを作る、要約を書く、といった解釈を伴う作業は機械化できない。**AI が提案し、スクリプトが形式を検証する**という分担にする。

## 選び方

```
その資産は「走らないと何かが素通りする」か
├─ はい
│   ├─ イベントで機械的に判定できるか
│   │   ├─ はい → hook（.claude/hooks/）★唯一の実効的な強制手段
│   │   └─ いいえ
│   │        ├─ 人間が起点になる操作か → スラッシュコマンド（.claude/commands/）
│   │        └─ 工程の一部で、親が呼ぶものか → サブエージェント（.claude/agents/）
│   └─ 判定に解釈の余地が無い部分は、いずれの場合もシェルスクリプトへ切り出す
└─ いいえ（走らなくても損害が無い補助手順）
     → Skill（.claude/skills/）
```

**「はい」の枝を選んだ場合、プロンプト側だけで完結させない。** 強制力はプロンプトには無い（軸2）。

## 適用例

### `.claude/hooks/check-prompt-entry.sh` — hook

工程をまたぐ依頼が main エージェントへ直接届くことを検知してブロックする（ADR 0011）。

- **軸1**: ランタイムが `UserPromptSubmit` で必ず発火させる。起動漏れが無い
- **軸2**: 終了コードで実際にプロンプトを止める。**このリポジトリで唯一、規約を機械的に強制している資産である**
- **軸3**: 検知パターンを fixture で固定してある

**それでも偽陰性は残る**（正規表現ヒューリスティックの限界。ADR 0011 決定5）。**hook にしたことは「完全に強制できている」を意味しない。** 受け皿は規律層（`docs/rules/responsibility.md`）である。

### `.claude/agents/` の5エージェント — サブエージェント

orchestrator / specifier / tester / implementer / reviewer。

- **軸1**: orchestrator は人間からも呼ばれるが、工程エージェント4つは **orchestrator が Task で呼ぶ**。呼ぶ順序と受け渡しは orchestrator の指示文に手順として書いてある
- **分割軸は工程**（仕様 / テスト / 実装 / レビュー）。レイヤーでも技術でも分けない（ADR 0010 §D）。工程は逐次かつ依存し、TDD のコミット規約（`docs:` → `test:` → `feat:`）と一致する
- **軸2 の限界が顕在化している**: orchestrator の「承認は2段」は指示文に書かれた宣言であり、**実際に破られた**（ADR 0011「悪い影響」に記録されたインシデント）。**サブエージェントの指示文に強制力は無い**

> **サブエージェント構成の変更（分割軸・エージェント数）は人間の承認事項である**（ADR 0010 §A）。この基準を根拠に AI がエージェントを増減させてはならない。

### `/issue` — スラッシュコマンド（ADR 0012 決定1）

Issue 番号から対応の準備を行う。受け入れ条件は `docs/specs/issue-command.md` が持つ（**ここに書き写さない**。ADR 0004）。

| 軸 | 適用 |
|---|---|
| 軸1 | **人間が明示的に叩く必須の入口**。走らなければ SDD ゲートが素通りする以上、モデルの選択に委ねられない → **Skill を却下** |
| 軸1 | 人間が起点であり、工程の一部でもない → **サブエージェントを却下** |
| 軸2 | イベントで機械的に判定できる操作ではない（人間が Issue に着手しようとした瞬間、というイベントは存在しない） → **hook にできない** |
| 軸3 | 判定部（引数の正規化・ラベル分岐・ゲート判定・形式検証・状態判定）は解釈の余地が無い → **`.claude/scripts/issue-gate.sh` へ切り出して fixture で固定** |

**残る限界を隠さない。** 軸1 の代償として、**人間が `/issue` を使わなければゲートは一度も走らず、そのことは機械では検出できない**（ADR 0012「悪い影響」）。Skill にすればモデルが自律的に拾いえたが、代わりに「拾わなかったこと」が観測できなくなる。**どちらの案も、使われなかった場合を機械では検出できない。**

## この基準の限界

- **軸1 で「人間が起動する」を選んだ資産は、使用率を機械で測れない。** 使われなかったことは記録に残らない
- **プロンプト側の資産（コマンド / Skill / サブエージェント）が仕様どおりに書かれているかは検査できない。** 検査できるのは参照が張られているかまでで、これは ADR 0004 の「CI が検査できるのはリンクが貼られているかだけ」、`review-trail` の「2段承認ゲートの成立は artifact に残らない」と同型の限界である
- **切り出したスクリプトも、外部ツールの前提が変われば無症状で壊れる。** fixture は仕様が定めた入力を再現するだけで、外部ツールが同じ形を返すことを保証しない（`docs/specs/orchestrator-entry-hook.md` P-1〜P-3、`docs/specs/issue-command.md` P-2 / P-3）
- **この文書自体に強制力は無い。** 置き場所の選択が基準どおりかを検査する仕組みは無く、規律で守る
