# 検証ハーネスとフィードバックループ

## なぜハーネスが要るのか

AIは自分の書いたコードが正しいかを、**自分では判断できない**。判断できるのは「実行した結果」だけである。

したがって開発速度は、AIの生成能力ではなく**フィードバックの速さと信頼性**で決まる。人間がレビューして間違いを指摘するループは、人間の可用性で律速される。AIが自分で回せるループを用意することが、ハーネスの目的である。

ハーネスに求める性質は3つ。

1. **決定的** — 同じコードなら同じ結果。Flaky なテストはループを壊す。信用できない Red は、無視される Red になる
2. **高速** — 遅いループは回されない
3. **CIと同一** — ローカルで通ったものがCIで落ちるなら、ローカルの結果に意味がない

## コマンド

| コマンド | 内容 |
|---|---|
| `make help` | ターゲット一覧 |
| `make test` | 全レイヤーのテスト |
| `make test-scripts` | `.github/scripts` のチェッカを fixture で検査（`make test` に含む） |
| `make test-hooks` | `.claude/hooks` のチェッカを fixture で検査（`make test` に含む） |
| `make test-commands` | `.claude/scripts`（スラッシュコマンドの機械判定部）のチェッカを fixture で検査（`make test` に含む） |
| `make lint` | 全レイヤーの Lint / 型チェック |
| `make verify` | `lint` + `test` + `check-domain-deps` + `scan-secrets` |
| `make check-domain-deps` | ドメイン層の依存検査 |
| `make scan-secrets` | gitleaks によるシークレット検出（作業ツリー + 履歴） |
| `make fmt` | 自動整形 |

### 未スキャフォールドのレイヤーは「SKIP」を明示する

`apps/web` と `infra/terraform` は未着手のため、該当ターゲットは対象が無いことを**ログに出して**素通りする。

```
==> test-web
  SKIP: apps/web/package.json が無い（Next.js 未スキャフォールド）
```

黙って成功させないのは、「通った」のか「素通りした」のかを区別できなくするとハーネスが信用を失うためである。一方、**ドメイン層の依存検査だけは対象が無い場合に失敗させる**（後述）。ここは中核であり、素通りを許容しない。

## 実行環境の前提

ハーネスは devcontainer 内で動く。**Go / Terraform / gitleaks / golangci-lint は `.devcontainer/Dockerfile` でビルド時に導入する。**

これは好みではなく制約である。`init-firewall.sh` が実行時の外向き通信を allowlist 方式で遮断しており、`go.dev` / `storage.googleapis.com` / `releases.hashicorp.com` / `deb.debian.org` はいずれも許可されていない。**コンテナ起動後にツールチェーンを入れることはできない。** ビルド中はファイアウォールが未適用なので、そこで入れる。

Go モジュールの取得のみ、allowlist に `proxy.golang.org` と `sum.golang.org` を追加して対応している。両方を許可することで `GOSUMDB` を有効なまま運用でき、`GOPROXY=direct` + `GOSUMDB=off` という回避策を避けている。チェックサム透明性ログの検証を維持するための判断である。

### CI ログの取得

後述の CI ループは「失敗したらログを読む」から始まる。**この最初の一歩には allowlist の設定が要る。**

`gh run view --log` が返すログの実体は GitHub API 上ではなく `productionresultssaN.blob.core.windows.net`（Azure Storage）にある。既定では遮断されるため、`gh pr checks` の pass/fail は取れてもログ本文が読めず、原因を追えない。

この採番は GitHub の内部実装であり公開されていない。実測では `sa0`〜`sa25` が存在し、`sa22` のような飛び番もあった。そのため `init-firewall.sh` では `sa0`〜`sa39` を**ベストエフォート**で解決し、**存在しない番号は黙って skip する**。必須ドメインのループとは分けており、ここで `exit 1` させない。ログが読めないという些細な問題を、コンテナ起動不能に化けさせないためである。

> **`.actions` を丸ごと許可する案は採らなかった。** GitHub Meta API の `actions` レンジは約2760万アドレスあり、その大半は Azure の共有 IP 空間である。egress 制限というファイアウォールの目的に対して代償が大きすぎる。名指しで許可した場合のユニーク IP は29個で、すべて `actions` レンジ内（＝GitHub 管理下）であることを確認済み。
>
> **この方式は壊れうる。** ホストプールが `sa39` を超えて増えた場合、ログが読めなくなる。ただしその失敗は現状復帰であり、悪化はしない。

> **バージョンは `.devcontainer/Dockerfile` と `.github/workflows/ci.yml` の両方で固定し、一致させること。** ずれると「ローカルで通るが CI で落ちる」が発生し、ハーネスの前提そのものが壊れる。Go のバージョンだけは `services/api/go.mod` を単一の情報源とし、CI は `go-version-file` で読む。

### 同名コマンドの別実装 — 対話シェルでの実測が検査対象と別物になりうる

**対話シェルの `grep` はシェル関数で別実装（`ugrep`）にシャドーイングされうる。** Unicode 対応の差により、`?` などの量指定子が多バイト文字に対して実 `/usr/bin/grep` と異なる結果を返す。実測:

```bash
$ type grep
grep is a function
$ printf 'ください' | grep -Eq 'て?ください'                     # 一致（exit 0）
$ printf 'ください' | command /usr/bin/grep -Eq 'て?ください'    # 不一致（exit 1）
```

hook 本体・fixture・CI が使うのは実 `/usr/bin/grep` である。**したがって対話シェルでの実測は、検査対象とは別エンジンの結果を返しうる。正規表現の挙動を検証するときは `command grep` を使うか、スクリプトファイルを `bash file.sh` で実行すること。**

> **この落とし穴により、正しい実装が「未実証の主張」として撤回されかけた。** `.claude/hooks/check-prompt-entry.sh` の「`て?` と書くと `LC_ALL=C` 下で `?` が多バイト文字の最終バイトにだけ適用される」というコメントに対し、オーケストレーター（AI）がシャドーイングされた `grep` で検証して再現せず、コメントを誤りと判断して撤回させようとした。**AI 側の誤りであり、隠さず記録する。**

> **mawk の事故（後述の「往復ブロックの見出し」「例外: プロセス検査」の注記）と同じ類型である。** 共通の失敗モードは、**「ローカルと CI で同一のものが動く」というハーネスの前提が、*同名コマンドの別実装*によって崩れる**こと。mawk 側は「runner の既定 awk がローカルの gawk と違う」、grep 側は「対話シェルの grep がスクリプト実行時の grep と違う」で、方向は違うが同型。

## ドメイン層の依存検査

CLAUDE.md は「ドメイン層は Go の標準ライブラリのみに依存する」と定めている。**この規約は人間のレビューに任せると必ず腐る。** import が1行増えるだけの変更は、レビューで最も見落とされやすい。

そこで機械的に検査する。

```bash
# make check-domain-deps の中核（実装は Makefile を参照）
go list -deps -test -f '{{if not .Standard}}{{.ImportPath}}{{end}}' ./internal/domain/... \
  | grep -v '^$' \
  | grep -v '^<module>/internal/domain/' \
  | grep -v '^github.com/google/go-cmp/'
# 出力が空でなければ違反 → exit 1
```

> **判定には `go list` の `.Standard` フラグを使う。** これは Go 自身が「標準ライブラリか否か」を報告する値であり、判定の権威はツールチェーン側にある。
>
> **採らなかった方法**: 「パスにドットが含まれるか」で判別する案を最初に検討したが、**これは誤りである**。`net/http` などが内部で `vendor/golang.org/x/net/...` を引き込み、これがドットを含むため誤検知する。標準ライブラリのパスにドットが無いという前提は、`vendor/` 配下で崩れる。
>
> 自パッケージ（`<module>/internal/domain/...`）のみ除外する。ドメイン層が同じモジュール内の `usecase` や `adapter` を import した場合も**違反として検出される**（依存の向きが逆転しているため）。
>
> **この検査はクリーンアーキテクチャの最内周を担保している**（ADR 0008）。「依存は内側にのみ向かい、Entities は何にも依存しない」という依存性ルールの、最も内側の主張と一致する。

### この検査が見ていない境界

**担保されているのは最内周だけである。** `usecase` が `adapter` を import しないこと、`adapter` が `driver` を import しないことは**検査していない**。これらは規律で守っている。

ADR 0008 でリングを4つに増やしたが、**層が増えることは、機械が保証する範囲が広がることを意味しない**。増えたのは規律で守る境界のほうである。ここを混同しないこと。

### `-test` を付ける — テストも検査対象である

**`-test` が無いと、テストファイルの import は一切検査されない。** `go list -deps` はテスト以外の依存しか出力しないためである。

これは実測で確認した穴である。`domain` に `net/http` を import する `_test.go` を置いても検出は0件で、`-test` を付けたときのみ検出される。**つまり「ドメイン層は標準ライブラリのみ」はテストコードには効いておらず、主張と実態がずれていた**（ADR 0007 で塞いだ）。

テストバリアント（`workmonth.test` および `workmonth [workmonth.test]`）の ImportPath はいずれも `<module>/internal/domain/` で始まるため、既存のフィルタがそのまま効く。追加の除外は要らない。

検査の主張は以下の2段になる。**どちらも CI で強制される。**

| 対象 | 許される依存 |
|---|---|
| `domain` の本体 | 標準ライブラリのみ（例外なし） |
| `domain` のテスト | 標準ライブラリ + go-cmp のみ |

> **go-cmp を許すのは、テスト専用ライブラリだからである**（ADR 0007）。許可リストは一般則ではなく具体名で書いてある。2つ目を許すには ADR の置換が要る。**ここを黙って増やせるなら、検査は意味を失う。**

### `-test` には終了コードの番人が要る

**`go list` の出力をパイプへ直接繋いではならない。** パイプの終了コードは最後のコマンド（`grep`）のものになり、`|| true` がそれを握り潰す。

これは `-test` を入れると実害になる。`go list -deps -test` は、**テストパッケージの import を解決できないとき何も出力せずに落ちる**（`can't load test package`）。`-test` の無い `go list -deps` が、エラーを出しながらも既知の import パスを出力するのとは挙動が違う。

結果、パイプが空になり、握り潰された終了コードと相まって検査は `OK` を返す。**実際に踏んだ。** `domain` のテストが解決できない `testify` を import している状態で、`OK: 1 パッケージ、標準ライブラリのみに依存` が終了コード 0 で返った。**偽の Green である。** 本当は「そのテストが何を import しているか分からない」が正しい答えだった。

そのため出力は一度変数に取り、終了コードを見てから処理する。**検査対象を読めなかったことは、違反が無いことを意味しない。**

> **この検査は構文エラーを見ない。** `go list` は import しか読まないため、パッケージがコンパイルできなくても依存の答えは返す。それは誤りではなく守備範囲の違いであり、構文エラーは `make lint-api`（`go vet` / `go build`）が捕まえる。

### 検査対象が無い場合は失敗させる

ドメイン層のパッケージが1つも見つからない場合、この検査は**成功ではなく失敗**を返す。「検査対象が無いので通った」は偽の Green であり、ハーネスとして最も避けるべき状態だからである。

**この検査があるから、DDDの「フレームワーク非依存」が主張ではなく事実になる。** ポートフォリオとしての価値はここにある。「ドメイン層を分離しました」は誰でも言える。CIが落ちる状態にしてあることが差になる。

## ループの構造

### TDD ループ（AIが自律的に回す）

```
仕様書 (docs/specs/) を読む
   ↓
テストを書く
   ↓
make test → Red を確認  ★ここを飛ばさない
   ↓
実装する
   ↓
make test → Green
   ↓
リファクタ → make verify
   ↓
コミット
```

**Red の確認を飛ばさない。** Red を踏んでいないテストは、対象が壊れても落ちない可能性を排除できていない。「テストを書いたら最初から Green だった」は、成功ではなく**テストが何も検証していない疑い**である。

### CI ループ（AIが自律的に回す）

```
push → CI 失敗
   ↓
ログを読む
   ↓
ローカルで再現   ★ここを飛ばさない
   ↓
修正 → make verify
   ↓
push → 再実行
```

**ローカル再現を飛ばして「たぶんこれで直る」で push しない。** CIを推測の検証に使うと、1サイクルが数分になり、ループが破綻する。再現できないなら、まず再現方法を確保することが仕事になる。

### ループの作業記憶

ループが回るあいだの進捗・エラーログ・試行錯誤は `progress.md` に書き出し、次のループが読み込む（Context / メモリ機構）。運用は `docs/harness/memory.md`。**優先順位は `docs/` > `progress.md`** で、食い違えば docs が正。`.gitignore` 済みでタスク完了 / PR マージで破棄し、恒久的な証跡の要約は PR コメントに残す。

### ループの上限値 ― 単一の情報源

ループの反復上限は**この表を唯一の定義箇所とする**（DRY）。他の docs・サブエージェント定義（`.claude/agents/`）はここを参照し、**数値を書き写さない**。閾値は人間の承認事項（ADR 0010 §A）であり、変えるときは**この1箇所だけを直す**。

| 上限 | 値 | 主語 / 数える対象 |
|---|---|---|
| 同一失敗の再試行 | **3** | AI 単独 / 同じ失敗に対する修正の再試行 |
| 実装↔レビューの往復 | **3** | オーケストレーター↔工程 / implementer→reviewer→implementer… の往復 |

**2つは値が一致するが別の規則である**（ADR 0010 §C）。二重管理ではなく独立に変更しうる。**片方を変えても、もう片方を追随させてはならない。統合禁止。**

> ADR 0010（§C）は決定の記録として「3」を凍結して持つ。値を変えるときは ADR を書き換えず新 ADR で覆す（ADR 0001）。**運用上の生きた値はこの表**であり、ADR は「なぜその値か」の記録である。

### 実装↔レビューループ（オーケストレーターが回す）

サブエージェント構成（ADR 0010 §D）では、オーケストレーターが実装工程とレビュー工程を往復させる。この往復は**初回 Green を PR にしてから**始まる（PR 作成は実装方向性の承認を経て一気通貫で行う。手順は orchestrator を参照）。

**PR 作成後、往復ループを開始する前に、オーケストレーターは人間の承認（「承認する／承認しない」）を改めて取る。** これは PR 内容を確認したうえでループを開始してよいかの確認であり、承認されるまで往復を開始しない。PR は人間が開始を判断するための成果物であり、往復の経緯を残す先でもある。

ループに入ったら、レビューが指摘を返すと実装工程がそれを反映し、再度レビューへ渡す。レビュー指摘は **Critical / Warning / Info の3段**（定義は reviewer エージェント）で、**往復を回すのは Critical / Warning が残る間**であり、Info は往復を強制しない。**往復の上限は上記「ループの上限値」の値**とし、超えたら下の停止条件に該当してオーケストレーターは握り潰さず**人間へ上げる**（ADR 0010 §D）。

反復の経緯は `progress.md`（作業記憶）に書き、恒久的な証跡は **PR の会話タブにコメントで要約して残す**。「会話タブのコメント」と具体化しているのは、`review-trail.yml` が読むのが issue comments のみだからである。**レビュー要約（Files changed の Review）やインラインコメントに書くと検査からは見えず、証跡があるのに赤くなる**（false Red）。**証跡は1往復＝1コメントで、その往復が終わった時点で追記する。往復をすべて終えてからまとめて投下しない（一括投下の禁止）。** これは、証跡が往復ごとに追記され、追記の順序と各コメントの投稿時刻それ自体が「往復が逐次に回った」ことの記録になるためである。一括で投下すると順序と時刻という記録が失われ、事後に整形しただけのものと区別できなくなる（ただしこの区別を機械では強制しない。下の信頼境界の限界を参照）。コメントは冗長にせず、各往復を**次のフォーマット**で残す。**指摘は Critical / Warning / Info の3段で内訳を示す**（レベルの定義は reviewer エージェント）。

```
### 往復 N
- Critical: <件数> — <要点。無ければ「なし」>
- Warning : <件数> — <要点。無ければ「なし」>
- Info    : <件数> — <要点。無ければ「なし」>
- 対応    : <この往復で implementer が直した点>
- 未解決  : <次往復へ持ち越す点。無ければ「なし」>
```

> **往復ブロックの見出しは「`往復 N` のあとが区切り文字か行末」のものである。** `review-trail.yml` は見出しレベルを問わず（`## 往復 4` も `###往復 4` も）往復ブロックとして拾う。数字の直後が行末、または `—` `–` `：` `:` `（` `(` `-` のいずれかなら往復ブロックとみなす。したがって `### 往復 4（最終）` や `### 往復 4 — 補足` も往復として**数え、上限超過を検出する**。一方 `#### 往復 1 の指摘への回答` や `## 往復2回目のレビューまとめ` のような、**数字のあとに文章が続く見出しは往復ブロックではなく、ふつうの見出しとして扱われる**（証跡コメントの中で自由に書いてよい）。
>
> この線引きは非対称で、意図的である —— 見出しレベルの取りこぼしは `#` の打ち間違いという*事故*で起き、上限超過という停止条件を黙って緑にするので拾う。一方「`往復 N` を含む見出しを何でもブロック扱いする」と、日本語として自然な見出しで必須5行の欠落として恒久的に赤くなり（復旧手段はコメント編集のみ）、**docs どおりに書くと落ちる**検査になる。**事故で誤爆する面だけを狭め、事故で見逃す面は狭めていない。** 区切り文字を許すのは、`（最終）` のような後置きが*上限に達した往復でこそ書かれる*ため、すり抜けと上限超過が相関するからである。この線引きは fixture で固定してある。
>
> 正規表現で多バイト文字を扱うときは、文字クラス `[—：（]` ではなく選択 `(—|：|（)` で書く。**mawk（GitHub runner の既定 awk）はバイト単位で扱うため、文字クラスに入れると継続バイトに誤一致する。** `#{1,6}` の区間指定を解釈しないのと同じ「mawk では黙って壊れる」系で、gawk では通るぶん気づきにくい。

PR に残すのは*決定した仕様*ではなく*経緯・証跡*であり、ADR 0004 とは衝突しない（`spec-link` と同じプロセス側の性質、ADR 0010 §C）。

> **この往復上限は、停止条件「同一失敗の再試行」とは別物である**（上記「ループの上限値」参照）。同じ数字だが別の規則であり、混同して片方に統合してはならない。

#### 上限を超えた往復を人間が承認したとき — `loop-extended` ラベル

上限超過の扱いは「**握り潰さず人間へ上げる**」であって「常に禁止」ではない。上げた結果、人間が「あと1往復で塞げるなら延長してよい」と判断することはある。

問題は、**その承認が session 内の判断で artifact に残らない**ことである。機械には「人間が承認した延長」と「AI が黙って回し続けた握り潰し」の区別が付かない（ADR 0010 §F の止められない側。Issue #25 が2段承認ゲートの機械化をスコープ外としたのはこの理由）。

そこで `no-spec` と同じ形をとる。**PR に `loop-extended` ラベルを付けたときだけ上限超過を通す。**

- **例外にラベルという明示的な操作を要求するのは、例外を使った事実を記録に残すためである**（`no-spec` と同じ原理）
- ラベルで免除するのは**上限だけ**。必須5行やブロックの存在といった形式は免除しない
- 例外で通した場合も `OK（例外）` として出力に残す。**黙って緑にしない**
- ラベルを付けるのは人間であり、**AI がこのラベルを自分で付けてはならない**。付けた時点で「承認の記録」ではなくなる

### 停止条件

以下では**ループを回さず人間に相談する**。

- **同一失敗の再試行が上限（「ループの上限値」）に達した** — 前提が間違っている可能性が高い。試行回数を増やしても解決しない
- **実装↔レビューの往復が上限（「ループの上限値」）を超えた** — 工程間で収束していない。オーケストレーターは握り潰さず人間へ上げる（「同一失敗の再試行」とは**別の規則**、ADR 0010 §C）
- テストを通すために**仕様の解釈を変える**必要が出た — それは実装ではなく仕様の問題（`docs/ai-collaboration.md`）
- テストを通すために**ガードレールを緩める**必要が出た（ADR 0002 / 0003）

**テストを消す・skip する・アサーションを緩めることで Green にすることを禁止する。** これはループを回しているように見えて、ハーネスそのものを壊す行為である。ハーネスが壊れれば、以降の Green はすべて無意味になる。

## CI の構成

`.github/workflows/ci.yml` は**ローカルと同一の make ターゲット**を呼ぶ。

| ジョブID | 必須チェック名（＝ジョブの `name:`） | 呼ぶもの |
|---|---|---|
| `go` | `Go (lint / test / domain-deps)` | `make lint-api` / `make test-api` / `make check-domain-deps` |
| `web` | `Web (lint / test)` | `make lint-web` / `make test-web` |
| `secrets` | `Secrets (gitleaks)` | `make scan-secrets` |
| `terraform` | `Terraform (fmt / validate)` | `make lint-tf` |
| `scripts` | `Scripts (checker logic)` | `make test-scripts`（`.github/scripts` のチェッカを fixture で検査） + `make test-hooks`（`.claude/hooks` のチェッカを fixture で検査） + `make test-commands`（`.claude/scripts` のチェッカ＝スラッシュコマンドの機械判定部を fixture で検査） |

**コードに対する検査を CI 側にだけ作らない。** 作った瞬間、ローカルの Green が信用できなくなる。

> **実際に踏んだ。** `make test-hooks`（`.claude/hooks` の fixture、111件）は `make test` の依存に足されていたが、`ci.yml` のどのジョブからも呼ばれておらず、**hook 本体を壊す変更が CI 緑のままマージできる状態が生じていた**（Issue #30 往復1 C-2）。`scripts` ジョブへ `make test-hooks` の step を追加して解消したが、**新規ジョブを起こす選択も可能だった**。新規ジョブは ruleset `protect-main` の必須チェックへの追加登録（ブラウザ操作。下記「必須チェックへの登録」参照）を人間に要求し、登録漏れは「実行され緑になるがマージ条件ではない」という発見しにくい状態を生む。`.claude/hooks` と `.github/scripts` は対象種別が異なるため make ターゲットは分けたまま（`test-hooks` / `test-scripts`）、CI ジョブは `scripts`（`Scripts (checker logic)`）に相乗りさせることで、この人間作業を発生させずに済ませた。

### 必須チェックへの登録 — ジョブIDではなく表示名で登録する

ruleset `protect-main` の必須チェックは、上表の**ジョブID（`go`）ではなくジョブの `name:`（`Go (lint / test / domain-deps)`）**で登録する。プロセス検査の2本（`PR が docs/ を参照しているか` / `PR に往復証跡が定型で残っているか`）も同様である。ADR 0009 の決定「実行される全チェックを必須にする」に従い、現在この**7本すべてが必須**である。

**ジョブIDで登録すると、一致するチェックが永久に報告されない。** GitHub は必須チェックを check run 名で照合するため、`review-trail` のようなジョブID を登録すると、その必須チェックは pending のまま留まり**全 PR がマージ不能になる**。緑にも赤にもならないため、原因が分かりにくい。

**逆に、ジョブの `name:` を変更すると必須チェックが静かに外れる。** ADR 0009 が「悪い影響」に挙げたとおり保護設定はリポジトリ外にあり、差分に現れない。**`name:` の変更は ruleset の更新とセットで行うこと。** 片方だけでは、チェックは実行され緑になるがマージ条件ではない、という ADR 0009 が解消したはずの状態に戻る。

現在の登録内容は下記で確認できる（リポジトリが public であるか、admin 権限のトークンを要する）。

```bash
gh api repos/h-k741953/effort-tracker/rulesets/19056534 \
  --jq '.rules[] | select(.type=="required_status_checks") | .parameters.required_status_checks[].context'
```

### 例外: プロセス検査

`.github/workflows/spec-link.yml` と `.github/workflows/review-trail.yml` は上記の原則の**例外**である。いずれも PR の本文・コメント・ラベルを対象とし、**ローカルには検査対象そのものが存在しない**ため、原理的に `make verify` には入れられない。

- `spec-link.yml` — PR 本文が `docs/` を参照しているか（ADR 0004）
- `review-trail.yml` — 実装↔レビューの往復証跡が定型フォーマットで残り、往復数が上限内か（上の「実装↔レビューループ」／「ループの上限値」）。上限値はこの doc の表から読み、**スクリプトにハードコードしない**（Issue #25）

**ただし「検査対象がローカルに無い」ことと「チェッカのロジックを検査できない」ことは別である。** チェッカ本体（`.github/scripts/check-review-trail.sh`）は入力（`TRAIL_FILE` / `REVIEW_LOOP_DOC`）を差し替えれば完全にローカル実行でき、**そちらは通常のコード検査として `make test-scripts` が fixture で検査する**（`make test` に含まれ、CI も同じターゲットを呼ぶ）。ここを区別しないと、チェッカのバグだけが検査不能地帯に残る。

> **実際に踏んだ。** 往復見出しを `###` ちょうどに限定していたため `## 往復 4` / `#### 往復 4` / `###往復 4` が黙殺され、**上限超過（＝人間へ上げるべき停止条件）が OK で通っていた**。`#` を1つ打ち間違えるだけで停止条件が赤くならないのは、上の「検査対象を読めなかったことは、違反が無いことを意味しない」が禁じる偽の Green である。さらに `#{1,6}` のような ERE の区間指定は **mawk（GitHub runner の既定 awk）が解釈せず条件が常に偽になる**ため、修正が黙って無効化される。どちらも fixture でしか捕まらない。

> **プロセス検査は「除外軸」自体が偽の Green になりうる。** `spec-link` / `review-trail` は `services/` `apps/` の変更が無ければ SKIP する。するとチェッカを直す PR（`.github/` と docs しか触らない）では構造上いつまでも SKIP になり、**その修正が一度も実行されないまま緑になる**。`review-trail.yml` はチェッカ自身の変更を含む PR では SKIP しない。緑が「通った」なのか「素通りした」なのかを区別するという、この doc 冒頭の要求はプロセス検査にも同じく効く。**なおこの除外軸自体もパスで書かれている以上、改名・移動で静かに外れて元の「いつまでも SKIP」に戻りうる。** そのため `review-trail.yml` は対象パスの実在を確認し、ずれていたら SKIP ではなく**失敗する**（`.github/scripts/` は接頭辞で拾い、スクリプトの改名では外れない）。除外軸の劣化を黙って通さないための措置である。

> **証跡コメントを足しても `review-trail` は再実行されない。** コメントの追加は `pull_request` ではなく `issue_comment` イベントで、そちらのチェック結果は PR の head SHA に紐づかず必須チェックとして機能しない。落ちた後にコメントで証跡を足したときは、push するかジョブを Re-run すること。

> **`review-trail.yml` が見ているのは記録だけである。** 検査対象は *PR に記録された* 往復ブロックの形式と往復数であって、実セッションの実装↔レビュー往復そのものではない。**記録をごまかせば擦り抜ける。** これは「外部が書き込める場所を正解の置き場所にしない」という ADR 0004 と同じ留意であり、限界として明記する。指摘レベルの分類（Critical/Warning/Info の妥当性）と2段承認ゲートの成立は artifact に残らず、ここでは検査できない（ADR 0010 §F の「止められない側」）。コードフェンス内に貼られた整形済みブロックも往復として数える。なお**チェッカ自身の失敗メッセージをそのまま貼っても誤爆しない**（テンプレートの `N` が数字でないため往復見出しに一致しない）。この安全側の性質は fixture で固定してある。

> **検査対象は第三者が書き込める場所である（信頼境界）。** PR 本文は著者とメンテナしか編集できないが、**PR コメントはコメント権限のある第三者なら誰でも追記できる**。上の「記録をごまかせる」は*当事者*の話であり、こちらは別軸である。第三者が必須5行そろいの `### 往復 99` を1つ投稿するだけで**必須チェックを恒久的に赤にできる**（復旧手段はそのコメントの削除のみ）。逆に整形済みブロックを投稿して通すこともできる。証跡は往復ごとに追記され順序自体が記録になるという性質からこの置き場所を選んでいるが、**この検査を「第三者に対する防御」として数えないこと**。なおコメント本文をシェルに展開しない対策（`TRAIL_FILE` 経由で渡す）は別途取ってある。

> **「往復ブロック数＝コメント投稿数＝投稿時刻の整合」は機械検査しない。** 一括投下の禁止（1往復＝1追記。上の「実装↔レビューループ」）は docs の規律であって、`review-trail.yml` はこれを検証しない。同 yml が読むのは *PR に記録された往復ブロックの形式と往復数* だけであり、それらが実際に別々のコメントとして往復ごとに投稿されたか、投稿時刻が往復の進行と整合するかは見ていない。**機械化しない**のは、上の2つの限界と同じ根による —— **証跡コメントを足しても `review-trail` は再実行されず**（`issue_comment` は head SHA に紐づかない）、かつ検査対象は**第三者が書き込める**場所である。仮にコメント数や投稿時刻を検査条件へ組み込んでも、当事者は事後に整形して数と時刻をそろえれば擦り抜けられ、第三者は任意のコメントで数や時刻をずらせる。したがって「往復ごとの追記」と「整形済みの一括投下」をこの検査では区別できず、**区別は規律で守る**（ADR 0010 §F「止められない側」と同型）。

> **必須チェック化により、上の第三者リスクは「赤くなる」から「マージできない」に上がった。** `review-trail` は ruleset の必須チェックであり、`bypass_actors` は空・`current_user_can_bypass` は `never` である（ADR 0009 が承認要件を捨てた代わりに機械的検査を回避不能にした帰結）。したがって**第三者のコメント1件で当該 PR を恒久的にマージ不能にできる**。オーナーであってもバイパスはできず、復旧手段は当該コメントの削除に限られる。これは ADR 0009 の「悪い影響」に列挙されていない、必須チェック化で新たに生じたコストである。**受け入れたうえで記録する**：バイパス経路を用意することは、ADR 0009 が却下した「ルールを装飾にする」案に戻ることを意味するため採らない。

「CI と同一」の原則が守ろうとしているのは、**コードの検証結果をローカルで信用できること**である。PR のメタデータに対する検査はこの利益に影響しない。ローカルで `make verify` が通れば、コードについては CI も通る、という関係は保たれる。

この性質の違いを構成上も明示するため、ci.yml とはファイルを分けている。**プロセス検査を ci.yml に混ぜない。** 混ぜると「ローカルで再現できない CI の失敗」が常態化し、原則そのものが形骸化する。

| 種類 | 対象 | ローカル再現 | 置き場所 |
|---|---|---|---|
| コード検査 | ソース・設定 | **可能（必須）** | `ci.yml`（`make` 経由） |
| プロセス検査 | PR 本文・コメント・ラベル | 不可能 | `spec-link.yml` / `review-trail.yml` |
| チェッカのロジック | fixture（入力を差し替えた検査本体） | **可能（必須）** | `ci.yml`（`scripts` ジョブの `make test-scripts` / `make test-hooks`） |

## ハーネスの限界

正直に記録しておく。以下は**ハーネスでは検出できない**。

- **業務ルールの誤り** — テストごと間違っている場合、Green は何も保証しない
- **ユビキタス言語のズレ** — 用語が現場と違っても CI は通る
- **集約の切り方の誤り** — 動作はする。数ヶ月後に破綻する

これらはすべて `docs/ai-collaboration.md` で**人間の責務**に置いた項目と一致する。**ハーネスで検出できないものを人間が持つ**、という分界であり、両ドキュメントは同じ原則の裏表である。
