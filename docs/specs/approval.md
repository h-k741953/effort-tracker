# 承認申請・承認 — 仕様

MVP ユースケース3「**承認申請・承認**」の受け入れ条件。根拠は Issue #7 の議論と `docs/domain/ubiquitous-language.md`。

**確定済みのユビキタス言語・状態遷移・終端状態の扱いはこの仕様へ書き写さない。** 正解は `docs/domain/ubiquitous-language.md` にあり、本仕様はそれを参照して「承認・差戻しが満たすべき形」だけを定める（ADR 0004）。

- **決定者**: 人間（プロジェクトオーナー）。業務ルールは `docs/ai-collaboration.md` の責務分界に従い人間が決定した（Issue #7 で選択）
- **日付**: 2026-07-23

---

## スコープ

**MVP ユースケース3（承認申請・承認）のみ**を対象とする。

- 対象: 締め済（`PendingApproval`）の勤務月に対する承認（`Approve`）・差戻し（`Reject`）の操作、その可否判定（状態別・認可）、承認/差戻しに伴う状態遷移
- 非対象: **締め（`Close`）の操作仕様は Issue #6（UC2）が持つ。** 本仕様は「締め済（`PendingApproval`）からの承認・差戻し」を対象とし、締めそのものと `PendingApproval` への遷移は UC2 が担う
- 非対象: 稼働実績の入力・編集（Issue #5 / UC1）、契約の管理（与件として扱う。`docs/rules/scope.md`）、技術者の横断ビュー、請求・支払・ファイル添付
- 非対象: **承認取消し・監査履歴・通知**（ユビキタス言語「MVP スコープ外」／後述 D-5・AC-9）

---

## 前提（P）— 確定事項（参照のみ、再定義しない）

`docs/domain/ubiquitous-language.md` の確定事項を前提とする。本仕様はこれらを覆さない。

| # | 前提 | 出典 |
|---|---|---|
| P-1 | 勤務月は `契約 × 年月` で一意。集約ルートは `WorkMonth` の1つのみ | ユビキタス言語「勤務月の同一性」 |
| P-2 | 締め＝承認待ち。締めると状態は締め済（`PendingApproval`＝承認待ちを兼ねる）になる。「締めたが未申請」の中間状態は存在しない | ユビキタス言語「締めと承認申請の関係」／UC2 P-4 |
| P-3 | 状態遷移は `Draft` →（締め）→ `PendingApproval` →（承認）→ `Approved`、差戻しで `PendingApproval` → `Draft`。**承認済は終端で、遷移は循環しない** | ユビキタス言語「状態遷移」 |
| P-4 | 承認者（`Approver`）は技術者の上長。締め済の勤務月を承認・差戻しする | ユビキタス言語「中核概念」 |
| P-5 | 締め済（`PendingApproval`）・承認済（`Approved`）では技術者は稼働実績を編集できない。差戻しで下書き（`Draft`）に戻ると再び編集できる | ユビキタス言語「状態と操作」／UC1 P-5 |
| P-6 | 締め時に算出・保存された超過（`Excess`）／不足（`Shortfall`）は、締めた時点の事実として固定されている | UC2 AC-3 |

## 決定（Issue #7 で人間が選択した業務ルール）

推測で埋めず、Issue #7 で人間が明示選択した。**各行の決定者は人間である。**

| # | 論点 | 決定 |
|---|---|---|
| D-1 | 承認者の決まり方 | **承認者ロールを持つ者なら誰でも承認・差戻しできる。** 承認者を `WorkMonth` 集約に持ち込まず、認可の関心事として**集約の外**に置く。勤務月は「誰が承認者か」を保持しない |
| D-2 | 承認者が複数いる場合 | **誰か1人でよい。** 1人の承認で承認済（`Approved`）に至る。「誰が承認済か」の集合を集約に持たない |
| D-3 | 差戻しのコメント | **MVP では持たない。** 差戻しは状態を下書きへ戻すだけで、理由コメントを勤務月に記録しない（勤務月に議論の履歴を入れない。監査履歴を外したのと同じ思想） |
| D-4 | 自己承認 | **禁止。** 承認者が、自分自身が技術者である勤務月を承認することはできない（差戻しも同様に扱う） |
| D-5 | 通知（メール等） | **MVP スコープに含めない。** 締め・承認・差戻しの際に承認者・技術者へ通知しない |
| D-6 | 承認済の可視性 | **既存の勤務月画面での状態表示のみ。** 技術者は自分の勤務月の状態（`Draft` / `PendingApproval` / `Approved`）を既存画面で確認する。承認済専用の一覧・画面は設けない |

## 受け入れ条件（AC）

| AC | 主題 | 主に効く工程 |
|---|---|---|
| AC-1 | 承認操作の可否（状態別）（P-3） | tester・implementer |
| AC-2 | 差戻し操作の可否（状態別）（P-3） | tester・implementer |
| AC-3 | 承認・差戻しできる人（認可）（D-1・D-2） | tester・implementer |
| AC-4 | 自己承認の排除（D-4） | tester・implementer |
| AC-5 | 承認に伴う状態遷移と帰結（P-3・P-6） | tester・implementer |
| AC-6 | 差戻しに伴う状態遷移と帰結（P-3・P-5・D-3） | tester・implementer |
| AC-7 | 承認済の終端性（P-3） | tester・implementer |
| AC-8 | 承認状態の可視性（D-6） | tester・implementer |
| AC-9 | 限界 — 本仕様が担保しないこと | reviewer |

### AC-1. 承認操作の可否（状態別）

承認（`Approve`）は**締め済（`PendingApproval`）からのみ**行える。下書き・承認済からは承認できない。

| # | 承認操作前の状態 | 承認（`Approve`）操作 | 期待 |
|---|---|---|---|
| 1-1 | 締め済（`PendingApproval`） | 実行 | **許可。** 承認済（`Approved`）へ遷移する（AC-5） |
| 1-2 | 下書き（`Draft`） | 実行 | **弾く**（まだ締められていない。承認対象でない） |
| 1-3 | 承認済（`Approved`） | 実行 | **弾く**（終端状態。二重承認を認めない。P-3） |

### AC-2. 差戻し操作の可否（状態別）

差戻し（`Reject`）は**締め済（`PendingApproval`）からのみ**行える。下書き・承認済からは差戻せない。

| # | 差戻し操作前の状態 | 差戻し（`Reject`）操作 | 期待 |
|---|---|---|---|
| 2-1 | 締め済（`PendingApproval`） | 実行 | **許可。** 下書き（`Draft`）へ戻す（AC-6） |
| 2-2 | 下書き（`Draft`） | 実行 | **弾く**（差戻す対象が無い。既に下書き） |
| 2-3 | 承認済（`Approved`） | 実行 | **弾く**（終端状態。承認後の差戻しは無い。P-3） |

### AC-3. 承認・差戻しできる人（認可）

承認・差戻しは**承認者ロールを持つ者**が行う（D-1）。承認者は勤務月に紐づかず、認可の関心事として集約の外で判定する。

| # | 操作者 | 期待 |
|---|---|---|
| 3-1 | 承認者ロールを持つ者 | **許可**（自己承認に該当する場合を除く。AC-4）。承認者が複数いても、そのうち1人の承認で承認済に至る（D-2） |
| 3-2 | 承認者ロールを持たない者（技術者など） | **弾く**（承認・差戻しは承認者ロールの操作） |
| 3-3 | 承認の成立に必要な人数 | **1人**（D-2）。複数承認者の全員承認を求めない。「誰が承認済か」の集合を勤務月に保持しない |

### AC-4. 自己承認の排除

| # | 条件 | 期待 |
|---|---|---|
| 4-1 | 操作者が承認者ロールを持ち、かつ**その勤務月の技術者本人**である | **弾く**（自己承認・自己差戻しを禁止。D-4） |
| 4-2 | 操作者が承認者ロールを持ち、その勤務月の技術者本人**ではない** | 承認・差戻しの可否は状態（AC-1・AC-2）とロール（AC-3）のみで決まる |

> 承認者を勤務月集約に持たない（D-1）ため、「操作者 ≠ その勤務月の技術者本人」という自己承認の判定も**集約の外（認可の関心事）**で行う。集約が守るのは状態遷移の正当性（AC-1・AC-2・AC-5・AC-6・AC-7）に閉じる。

### AC-5. 承認に伴う状態遷移と帰結

| # | 承認成立（AC-1-1）後 | 期待 |
|---|---|---|
| 5-1 | 状態 | 承認済（`Approved`）へ遷移する（P-3）。承認済は**終端状態**（AC-7） |
| 5-2 | 保持する値 | 締め時に算出・保存された総稼働時間・超過／不足（P-6）を**そのまま保持**する。承認で再計算・変更しない |
| 5-3 | 技術者による稼働実績の入力・編集・削除 | **弾く**（P-5。締め済に続き承認済も編集不可） |
| 5-4 | 承認者情報の保持 | **保持しない**（D-1・D-2）。「誰が承認したか」を勤務月に記録しない（監査履歴は非スコープ。AC-9） |

### AC-6. 差戻しに伴う状態遷移と帰結

| # | 差戻し成立（AC-2-1）後 | 期待 |
|---|---|---|
| 6-1 | 状態 | 下書き（`Draft`）へ戻す（P-3） |
| 6-2 | 技術者による稼働実績の入力・編集・削除 | **再び許可**（P-5。下書きに戻るため編集可能に復帰する） |
| 6-3 | 締め時に保存した超過／不足 | 下書きへ戻った時点で、締めによって確定した事実は**再編集の対象に戻る**。再度締め直したとき（UC2）に改めて算出・保存される |
| 6-4 | 差戻しの理由コメント | **持たない**（D-3）。差戻しは状態を戻すだけで、理由を勤務月に記録しない |
| 6-5 | 差戻し回数の上限 | **設けない。** 下書き ⇄ 締め済 の往復は循環ではない（承認済に至れば終端。P-3）。往復回数を勤務月に記録しない |

### AC-7. 承認済の終端性

| # | 条件 | 期待 |
|---|---|---|
| 7-1 | 承認済（`Approved`）からの承認（再承認） | **弾く**（AC-1-3） |
| 7-2 | 承認済からの差戻し | **弾く**（AC-2-3） |
| 7-3 | 承認済からの再締め | **弾く**（締めは下書きからのみ。UC2 AC-1-3） |
| 7-4 | 承認取消し（承認済 → 締め済／下書きへ戻す操作） | **存在しない**（ユビキタス言語「承認済は終端」）。承認後の訂正手段を MVP では提供しない |

### AC-8. 承認状態の可視性

| # | 条件 | 期待 |
|---|---|---|
| 8-1 | 技術者が自分の勤務月の承認状態を確認する | **既存の勤務月画面で状態（`Draft` / `PendingApproval` / `Approved`）を表示する**だけ（D-6） |
| 8-2 | 承認済の勤務月を一覧する専用画面 | **設けない**（D-6）。承認済を横断的に見る一覧は集約をまたぐ参照系の関心事であり非スコープ |
| 8-3 | 締め・承認・差戻し時の通知 | **無い**（D-5）。状態は画面を開いて確認する（プッシュ通知・メールを送らない） |

### AC-9. 限界 — 本仕様が担保しないこと

**以下は仕様どおりであり、欠陥ではない。**

| # | 内容 |
|---|---|
| 9-1 | **締めの操作は対象外。** `Draft` → `PendingApproval` への遷移（締め）は UC2（Issue #6）が持つ。本仕様は「締め済からの承認・差戻し」に閉じる |
| 9-2 | **承認取消し・監査履歴が無い**（AC-7-4、ユビキタス言語「承認済は終端」）。「誰がいつ承認・差戻ししたか」の履歴を保持しない（D-1・D-2・AC-5-4） |
| 9-3 | **差戻しの理由を記録しない**（D-3・AC-6-4）。なぜ差し戻されたかは勤務月の外（口頭・別チャネル）で伝わる前提 |
| 9-4 | **通知が無い**（D-5・AC-8-3）。承認待ちの発生・承認・差戻しをシステムが能動的に知らせない |
| 9-5 | **承認者の割り当て・承認者ロールの管理そのものは対象外**（D-1）。本仕様は「承認者ロールを持つ者が承認・差戻しできる／自己承認は排除する」という認可の振る舞いだけを定め、誰が承認者ロールを持つかの管理（ユーザー・ロール管理）は MVP の3ユースケース外 |
| 9-6 | 本仕様は受け入れ条件のみを定め、承認者判定・自己承認排除を集約の外（usecase / adapter）に置く配置や、状態遷移を守る集約の内部レイヤー配置（clean architecture の各リング）・永続化の詳細は、実装工程が `docs/adr/0008` に従って決める（AC-4 の注記が示す集約内外の分界だけは本仕様が固定する） |
