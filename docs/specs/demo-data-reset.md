# デモデータの投入と日次リセット — 仕様

Issue #56「デモデータの生成と日次リセット」の仕様である。デモデータを投入する手段、日次で入れ直す手段、そして時刻を持たない稼働実績を含む旧データを破棄する手段を扱う。既存の条文はこれらを「デモデータを扱う Issue」に委ねている（P 節の出典）。本仕様はその受け皿である。

業務ルール・ユビキタス言語は**この仕様へ書き写さない**。正解は各業務仕様と `docs/domain/ubiquitous-language.md` にある。本仕様に書くのは次の5つに限る（ADR 0004）。

- 既に決まっていることの要旨と出典（P 節）
- 人間の決定の記録（Q 節）
- 人間の確認を待つ事項（U 節）
- 受け入れ条件（AC 節）
- デモデータの値（「デモデータの値（人間の再確認待ち）」節）

- **状態**: **Q-1〜Q-8 は 2026-10-27 に人間が決定した。** ただし次の2つが残る。
  - **U 節の確認事項は未決である。** U に依存する AC（各 AC の「依存」欄に U を記した行）は、U の決定まで実装へ進まない（`docs/rules/responsibility.md`）
  - **「デモデータの値」節は人間の再確認待ちである。** 人間は「契約表示名などの細かな値は、`docs:` コミットの前にもう一度確かめる」と選んだ（Q-6）
- **日付**: 2026-10-27（仕様工程が起草し、同日の人間の決定を反映した）
- **決定者**: Q 節の決定は人間（2026-10-27 に AskUserQuestion で明示選択）。AC 節と「デモデータの値」節で「**仕様工程の定め**」と印を付けた行は、仕様工程が定めたものであり、**人間の決定ではない**。覆すのに人間の承認は要らないが、仕様の改訂として扱う
- **前提 ADR**: 0004（docs が正）／0007（標準 `testing` + go-cmp）／0013（ホスティング）／0016（認証・ゲスト）／0017（pgx）／0021（契約期間・閲覧系の画面）／**0022（リセット用 Lambda。提案中）**

## 決定（Q）— 2026-10-27 人間が決定

Q-1〜Q-8 は、2026-10-27 に人間が AskUserQuestion で明示選択した。決定は main セッション経由でオーケストレーターが受領した。各 Q には、選んだ選択肢と、起草時に並べた選択肢の評価を残す。**起草時に仕様工程が付けていた「推奨」は削った。** 決定は人間の選択によるものであり、推奨の採否として読まない。

**各 Q の「決定」に書いたことだけが人間の決定である。** それを AC へ落とすときに仕様工程が補ったことは、AC の側で「仕様工程の定め」と印を付けて書き分ける。

### Q-1. スケジュール実行の手段

- **決定（2026-10-27 人間が決定）**: **(a)**。EventBridge Scheduler から、4本目の Lambda（リセット専用）を呼ぶ。技術選定に当たるため ADR 0022 を起こす（提案中）
- **帰結として未決のまま残るもの**: リセット用 Lambda の予約同時実行数の値（U-5）、デプロイロールの列挙に Scheduler を足すこと（U-4）、`docs/rules/architecture.md` との関係（U-3）、`services/api` に非業務の `cmd` を足すことの引き受け（U-6）

| 選択肢 | 内容 | 起草時の評価 |
|---|---|---|
| **(a) 採用** | EventBridge Scheduler から**4本目の Lambda（リセット専用）**を呼ぶ | Lambda が4本になり、予約同時実行数の行（`docs/rules/cost-guardrails.md`）と `infra-terraform.md` の「3本」を前提にした条文に影響する。Scheduler はデプロイロールの列挙（P-25）に無い。実行ロールに要るのは、自身のロググループへの書き込みと接続文字列の SSM パラメータの読み取りに限られる。Function URL は持たせない。CloudFront 遮断 Lambda を独立させた先例（`infra-terraform.md` AC-4-8）に沿い、破棄の処理を公開経路から切り離せる |
| (b) 退けた | EventBridge Scheduler から、既存の**ドメイン API Lambda に別のイベント源**を足して呼ぶ | `docs/rules/architecture.md`「Route Handler 以外から Lambda を呼ばない」に字面で反する。公開経路を担う関数に全行を破棄する処理が同居し、ハンドラの分岐を誤ると HTTP の経路から破棄に到達する余地が生じる。予約同時実行数を API と分け合う |
| (c) 退けた | GitHub Actions の `schedule` から DB へ直接つなぐ | 接続文字列を GitHub Secrets に置くと、長期認証情報を置くことになる（P-23 の趣旨に反する）。回避にはデプロイロールの拡張か新しいロールが要る。`schedule` は実行時刻を保証せず、公開リポジトリでは活動が無いと無効化される |
| (d) 退けた | Neon の `pg_cron` で、DB 内で実行する | 利用中のプランで使えるか、スケール・トゥ・ゼロの間に走るかが未実測である。組み立てが SQL 側に移り、Go の標準 `testing` で検証する方針（ADR 0007）の外に出る |
| (e) 退けた | リクエスト時の遅延リセット | 利用者の要求の経路で全行の破棄が走り、同時の要求と競合する。`domain-api-http-contract.md` AC-11-8 の趣旨から外れる |

### Q-2. リセットの範囲と、契約期間を持たない既存の行

- **決定（2026-10-27 人間が決定）**: **(a)**。契約の行は残し、日次リセットでは勤務月と稼働実績だけを入れ直す。`contracts-ui.md` P-7 の「日次リセットされる」は、**デモデータ全体の性質として読む**
- **起草時の (a) の内容**: 契約期間を持たない既存の契約行には、一度だけのマイグレーションで契約期間の値を埋める（UPDATE）
- **帰結として未決のまま残るもの**: Q-6 の「契約期間もリセット日基準の相対の年月」と組み合わせたときの扱い（U-1）

| 選択肢 | 内容 | 起草時の評価 |
|---|---|---|
| **(a) 採用** | 契約の行は残す。日次リセットでは勤務月と稼働実績だけを入れ直す | AC-10-20 ③（契約の行は残す）と字面で一致する。デモの契約の集合を後で変えるには、別途マイグレーションが要る |
| (b) 退けた | 契約の行も毎回入れ直す | AC-10-20 ③「契約の行は残す」と字面で食い違い、人間の決定17 の改訂が要る |
| (c) 退けた | (a) を基本とし、食い違うときだけ契約の行を足す・直す | 「契約を作る手段を作らない」（P-7）との境界があいまいになる |

## 未決の確認事項（U）

Q の決定を AC へ落とす過程で、**人間の決定が要るのに決まっていない**ことが見つかった。仕様工程はこれらを**推測で埋めない**。各 U に依存する AC は、AC の表の「依存」欄に U を記した。U が決まるまで、その AC の実装へ進まない。

### U-1. 相対の契約期間と、残す契約の行（Q-2 × Q-6）

**食い違い**: Q-6 は契約期間を含めて「リセット日を基準にした相対の年月」とした（値は「デモデータの値」節）。一方 Q-2 (a) は「契約の行は残し、勤務月と稼働実績だけを入れ直す」とした。

- 契約の行を日次で改めないなら、契約期間は最初に投入した日の相対で固まる
- 勤務月は日ごとにリセット日の相対で作り直されるので、日が経つと両者がずれる
- 例えば、終了のある契約は、その契約の承認済の勤務月より前に終わったように表示される
- 契約期間は表示にだけ使い、整合を検査しない（P-32）。このためエラーにはならない。ただし、契約一覧と稼働の推移で食い違うデモになる

あわせて、デモの契約以外に、契約期間を持たない既存の契約の行が実環境にあった場合に、どの値で埋めるかも決まっていない（Q-2 の「確認が要る事実」）。

| 選択肢 | 内容 | 影響 |
|---|---|---|
| (i) | 日次リセットで、**デモの契約の契約期間の列だけ**を改める（行は削除も追加もしない） | Q-2 (a) の「勤務月と稼働実績だけを入れ直す」を、契約期間の列について広げることになる。契約を更新する手段（P-7）との境界の確認が要る |
| (ii) | 契約期間は最初の投入時の相対で固め、ずれを許す | Q-6 の「相対の年月」を契約期間については初回だけに限る読みになる。日が経つと食い違うデモになる |
| (iii) | 契約期間だけは固定の年月にする | Q-6 の「契約期間は相対」を改める。固定の年月を人間が決める必要がある |

- **依存する AC**: AC-6-2・AC-6-3・AC-3-1〜3-3 の適用時点

### U-2. 1つのトランザクションと、集約をまたぐトランザクションの禁止（Q-6 × Q-8 × P-33）

**食い違い**: 3つの決定と条文が、そのままでは両立しない。

- Q-8 は「破棄と投入を1つのトランザクションで行う」とした
- Q-6 は「集約を組み立てて gateway で保存する」とした
- 既存の `Save` は**集約単位で自らトランザクションを開く**（`workmonth-implementation-design.md` AC-6-1・AC-10-7）
- 同 AC-10-7 は「**集約をまたぐトランザクションを作らない**」と定めている

複数の勤務月の保存と全行の破棄を1つのトランザクションに入れることは、字面上この禁止に当たる。さらに、`Save` は外側のトランザクションを受け取らない。このため、gateway の公開の形（または破棄の SQL の置き場所。SQL は gateway が持つ＝同 AC-9-14-c）を変える必要がある。

| 選択肢 | 内容 | 影響 |
|---|---|---|
| (i) | AC-10-7 の禁止は業務の操作（`Save`）に掛かるものと読み、リセットは対象外とする。gateway に「破棄と、複数の集約の保存を1つのトランザクションで行う」書き込みの手段を足す | AC-10-7 に適用範囲の注記が要る（要求の範囲を狭める変更＝人間の承認事項）。gateway の公開の形が増える |
| (ii) | 破棄を1つのトランザクションで行い、各集約は既存の `Save` で個別に保存する | Q-8 の「1つのトランザクション」を改める。保存の途中で失敗すると、デモデータが欠けた状態が次のリセットまで残る |
| (iii) | 集約で組み立て・検証した結果を行の値へ写し、gateway の外で1つのトランザクションの INSERT を流す | Q-6 (a) の「gateway で保存」から外れる。SQL を gateway 以外に置くことになり、同 AC-9-14-c に反する |

- **依存する AC**: AC-9-1・AC-11-2・AC-11-3

### U-3. `docs/rules/architecture.md`「Route Handler 以外から Lambda を呼ばない」との関係

リセット用 Lambda は EventBridge Scheduler から起動され、Route Handler からは呼ばれない。規約の字面「Route Handler 以外から Lambda を呼ばない」を、「ブラウザからの経路（BFF の一方通行）に限った規約」と読むか、それとも全 Lambda に掛かる規約と読むかを、人間は決めていない。**仕様工程は規約の解釈を決定済みとして書かない。**

| 選択肢 | 内容 |
|---|---|
| (i) | 規約はブラウザからの経路に掛かると読み、`docs/rules/architecture.md` にその旨を明記する（規約の改訂＝人間の承認事項） |
| (ii) | 規約を「Route Handler と、ADR 0022 のスケジュール以外から Lambda を呼ばない」へ改める |
| (iii) | 規約を改めず、ADR 0022 を例外の根拠として参照する |

- **補足（事実）**: CloudFront 遮断 Lambda も SNS から起動され、Route Handler から呼ばれない。この関係も、規約の字面には現れていない
- **依存する AC**: AC-12-1（起動経路）。構成の要求そのものは U-3 に依らないが、規約との整合が確定するまで実装 PR を閉じない

### U-4. デプロイロールの列挙（`infra-terraform.md` D-15）に Scheduler を足すこと

EventBridge Scheduler のスケジュールを Terraform で作るには、デプロイロールに Scheduler の操作の権限が要る。D-15 の限定列挙（P-25）には Scheduler が無い。`10-4-o` は、`Action` がこの列挙のサービス接頭辞に収まることを assert する。**権限を広げる判断は人間の承認事項である**（同 12-10）。仕様工程は列挙を改訂しない。

- **依存する AC**: AC-12-2・AC-12-3（Terraform で作れない）

### U-5. リセット用 Lambda の予約同時実行数の値

全 Lambda に予約同時実行数を明示する要求は既にある（P-21）。しかし、リセット用 Lambda の**値**を人間は決めていない。値の持ち主は `docs/rules/cost-guardrails.md` であり、本仕様は値を書かない。

- **依存する AC**: AC-12-4 のうち値の一致（明示的に設定することは U-5 に依らない）

### U-6. `services/api` に非業務の `cmd` を足すことと、その import の許可

Q-6 (a)（gateway で保存）と Q-7 (a)（`embed` でバイナリに埋め込む）から、リセット用 Lambda は Go で書き、`services/api` モジュールの内部パッケージを使う形になる。一方、`infra-terraform.md` P-5 は、`services/` に遮断 Lambda 以外の非業務コードを足すことを「別途人間の判断が要る」としている。また、エントリポイントの import の許可は、ドメイン API（`workmonth-implementation-design.md` AC-1-7）と遮断 Lambda（`infra-terraform.md` AC-9-10）について個別に定められており、リセット用の `cmd` の許可はまだ無い。

- **人間に確認したいこと**: (1) Q-6・Q-7 の決定が、`services/api/cmd/` 配下へのリセット用の `cmd` の追加を含むと読んでよいか。(2) その `cmd` が import してよい範囲（`internal/domain`・`internal/adapter/gateway`・`internal/driver/persistence`、既に承認済みの AWS SDK の設定解決と SSM、`aws-lambda-go`、標準ライブラリ）。import の許可を足す判断は人間の承認事項である（`infra-terraform.md` AC-9-10 の末尾）
- **依存する AC**: AC-9-1・AC-12-7

### U-7. README のコストの節との同期

Lambda が4本になると、README がコストの節で Lambda の本数や予約同時実行数に触れていれば、その記述との同期が要る。README は仕様工程の変更対象の外にある。同期をどの PR で行うかは決まっていない。

## 受け入れ条件（AC）

各行の「定め」欄は、その行の出所を示す。

- **人間**: 人間の決定（Q・既存の決定）をそのまま条件にした行
- **仕様工程の定め**: 人間が決めていない細部を仕様工程が埋めた行。人間の決定ではない
- **帰結**: 既存の条文から一意に導いた行

「依存」欄に U がある行は、その U が決まるまで実装へ進まない。

**検査の単位**（AC-14）: 次の3つに分ける。

- 組み立ての規則は、Go の単体テストで検査する（標準 `testing` + go-cmp。手書きのインメモリ Fake）
- 構成は `terraform test` で検査する
- 実 DB でリセットが行われたこと自体は、担保の対象外である（P-18）

| 13-2 | **承認者の操作で、デモ群の例は最大1日崩れる**（Q-5 (i)。AC-8-3） |
| 13-3 | **リセットの失敗は通知されない**（Q-8）。気づく手段は CloudWatch Logs を読むことだけであり、ログの保持日数を過ぎれば記録も消える。失敗が続く間、前日のデータが残り続け、相対の年月はリセット日から遅れていく |
| 13-4 | **実 DB でリセットが行われたことは担保しない**（P-18）。トランザクションの原子性（AC-11-2）、破棄が実際に全行に及ぶこと（AC-1）、DDL の冪等性（AC-10-3）は、実 DB を要する |
| 13-5 | **祝日に稼働実績が置かれる**ことがある。稼働日の決め方は暦の曜日だけで決め、祝日を区別しない（「デモデータの値」節 V-4。祝日の区分を持たない＝`daily-record-entry.md` AC-7-5） |
| 13-6 | **リセットは、デモ群以外の利用者が入力した勤務月も破棄する**（P-4）。分離（Q-5）は1日の中での分離である |

### V-6. 各月の総稼働時間と超過／不足（暦による不変性の確認）

**計算の前提**

- 総稼働時間は、各日の稼働時間を15分単位で切り捨てて合計する（`daily-record-entry.md` AC-6。時刻が15分刻みなので、切り捨てで値は変わらない）
- 超過／不足は `monthly-closing.md` AC-4 の判定規則で求める。**精算幅の境界は両端とも「含む」**（同 AC-4-2・AC-4-4。下限・上限ちょうどは精算幅に収まる）
- 比較と減算は分単位で行う
- 1か月の平日の数は 20〜23 のいずれかである（2月の28日間は平日がちょうど20、31日の月は最大23）
- 1か月の土曜の数は4か5である

**契約 A**（精算幅 140時間0分〜180時間0分）

| 型 | 平日 20 | 平日 21 | 平日 22 | 平日 23 | 判定 |
|---|---|---|---|---|---|
| 標準型 | 152時間0分 | 160時間0分 | 168時間30分 | 176時間30分 | どの月も 140時間0分 以上 180時間0分 以下。**超過 0・不足 0（精算幅に収まった月）**。下限との差は最小 12時間0分、上限との差は最小 3時間30分 |
| 超過型 | 185時間0分 | 194時間0分 | 203時間30分 | 212時間30分 | どの月も 180時間0分 を上回る。**超過** 5時間0分／14時間0分／23時間30分／32時間30分、不足 0 |
| 不足型 | 117時間30分 | 123時間15分 | 129時間15分 | 135時間0分 | どの月も 140時間0分 を下回る。**不足** 22時間30分／16時間45分／10時間45分／5時間0分、超過 0 |

計算の内訳は次のとおりである。

- **標準型**: 20日は 38時間0分 × 4 で 152時間0分 になる。21日目に余り1（8時間0分）、22日目に余り2（8時間30分）、23日目に余り3（8時間0分）を足す
- **超過型**: 奇数日が 9時間0分、偶数日が 9時間30分 である
  - 20日 = 10 × 9時間0分 + 10 × 9時間30分
  - 21日 = 11 × 9時間0分 + 10 × 9時間30分
  - 22日 = 11 × 9時間0分 + 11 × 9時間30分
  - 23日 = 12 × 9時間0分 + 11 × 9時間30分
- **不足型**: 奇数日が 5時間45分、偶数日が 6時間0分 である。日数の内訳は超過型と同じに数える

**どの型も、平日の数によって判定の別が入れ替わらない**（AC-4-6）。いずれの合計も精算幅の端に一致しないので、境界の扱いに依らずに別が決まる。

**契約 B**（精算幅 20時間0分〜40時間0分）

| 土曜の数 | 総稼働時間 | 判定 |
|---|---|---|
| 4 | 24時間0分 | 精算幅に収まった月（超過 0・不足 0） |
| 5 | 30時間0分 | 精算幅に収まった月（超過 0・不足 0） |

**当月の `Draft`**: 超過／不足は未確定（NULL）であり、判定しない。

- 平日が最大の22日（31日の月で、リセット日が月末日のとき）でも、標準型の合計は 168時間30分 に収まる

### V-7. 掛け持ちの2契約の重なり

**既存仕様の確認**:

- 時刻の妥当性（`daily-record-entry.md` AC-3）は、1つの稼働実績の中の前後関係と休憩の位置だけを扱う
- 1日1レコード（同 D-1・AC-2-2）は、**同一勤務月内**の対象日の一意性である
- 勤務月は `契約 × 年月` で一意である（ユビキタス言語「勤務月の同一性」）

以上から、**契約をまたいで同じ日の時刻が重なることを扱う条文は無い**（禁止も許可もしていない）。検査もされない。

**配置**: 業務の実態として不自然な重なりを避けるため、契約 A を平日、契約 B を土曜に置き、**同じ日に2契約の稼働実績を置かない**（AC-9-10）。【仕様工程】
