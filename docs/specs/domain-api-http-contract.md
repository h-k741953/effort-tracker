# ドメイン API の HTTP 契約 — 仕様

`services/api`（Lambda Function URL）が公開する **HTTP の契約**。MVP 3ユースケース（稼働実績の入力・編集／月次締め／承認申請・承認）と、それを支える参照系のエンドポイント・リクエスト／レスポンス DTO・エラー表現を定める。

**この契約は BFF（Next.js Route Handler、Issue #54）が参照・消費する唯一の実体である。** 契約の内容を Issue コメント・PR 本文・BFF 側のコードコメントへ書き写さない。参照はこのファイルへのリンクで行う（ADR 0004）。

**業務ルール（値域・丸め・未来日・締め可否・承認可否・自己承認排除・状態遷移）はこの仕様へ書き写さない。** 正解は `docs/specs/daily-record-entry.md` / `docs/specs/monthly-closing.md` / `docs/specs/approval.md` と `docs/domain/ubiquitous-language.md` にある。本仕様が決めるのは**その業務ルールを HTTP でどう表すか**だけである。実装設計（層への型配置・ポート）は `docs/specs/workmonth-implementation-design.md` が持つ。

- **決定者**: HTTP 表現の各決定は仕様工程（AI）。**業務ルールを新たに決めていない。** 業務仕様が答えを持たなかった論点（未生成の年月の締め・参照系の認可・操作者の伝達）は **2026-07-27 に**、当該年月に属さない対象日への削除は **2026-07-28 に**、いずれも**人間が明示選択して確定**し、末尾「人間が確定させた決定」に残した。`daily-record-entry.md` の時刻への改定（D-2・D-3・D-7・D-10〜D-17）に追随する際の論点（時刻の表し方・休憩の表し方・時刻の違反の `code` の粒度と判定順序上の位置）も **2026-10-15 に人間が明示選択して確定**した（決定5〜決定7）。その追随で AI が起案した点（D-16 の `code` の名前と `WORKING_HOURS_OUT_OF_RANGE` の廃止・D-17・D-18）も **2026-10-15 に人間が承認**した（条文中の「AI 起案（2026-10-15 に人間が承認）」）。契約一覧・稼働の推移の読む口の論点（口の形・認可・契約期間を持つ型）は **2026-10-21 に人間が明示選択して確定**した（決定8〜決定10。D-19〜D-21）。その反映で**仕様工程が定めた細部**（パス・クエリ・JSON の形・403 の `code` の流用・判定順序への当てはめ。D-22・AC-10-4・AC-10-5・AC-12・AC-13）は**人間の決定ではない**（条文中の「仕様工程の定め」。人間は採否を選んでいない）。ログインした技術者の契約を用意する口（E-10）の論点（口を足すこと・場所と契機・値を外から受け取らないこと・ロールを問わないこと）は **2026-10-29 に人間が明示選択して確定**した（`engineer-contract-provisioning.md` Q-3・Q-6・Q-7。D-23）。その反映で仕様工程が定めた細部（パス・応答の形・判定順序への当てはめ。D-23・AC-14）は人間の決定ではない。**未決の論点は無い**

## スコープ

- **対象**: エンドポイントの一覧（メソッド・パス）、操作者の伝達方法、リクエスト／レスポンスの JSON フィールド名と型、ステータスコード、エラーコードと判定順序、一覧の並び順・ページング
- **非対象**:
  - **業務ルールそのもの**（3業務仕様が持つ。参照のみ）
  - **BFF・ブラウザ側の実装**（Issue #54。本仕様は BFF が呼ぶ相手側の契約に閉じる。BFF 側の実装設計は `docs/specs/bff-wiring.md`）
  - **画面の受け入れ条件**（各 UI 仕様）
  - **SigV4 署名の実装方法**（ADR 0003 / 0014。`apps/web/src/lib/lambda-client.ts` に集約する。`docs/rules/architecture.md`。仕様は `docs/specs/bff-wiring.md`）
  - **Cognito のトークン検証**（BFF で終端する。ADR 0016）

## 前提（P）— 確定事項（参照のみ、再定義しない）

| # | 前提 | 出典 |
|---|---|---|
| P-1 | Function URL は `authorization_type = "AWS_IAM"`。**呼べるのは SigV4 署名できる BFF のみ**で、ブラウザから直接到達する経路は構造的に存在しない | ADR 0003・0013・`docs/rules/architecture.md` |
| P-2 | エンドユーザー認証は **BFF で終端**する。ドメイン API はトークン検証をせず、BFF が確定させた操作者・ロールを受け取る | ADR 0016・`login-ui.md` AC-5 |

## 決定（D）— HTTP 表現

| # | 論点 | 決定 |
|---|---|---|
| D-1 | リソースの識別 | 勤務月は **`/work-months/{contractId}/{yearMonth}`** で識別する。代理キー（サロゲート ID）を導入しない（`契約 × 年月` で一意という P-4 をそのまま URL に写す） |
| D-2 | 操作者の伝達 | **リクエストヘッダ `X-Actor-Id` / `X-Actor-Role`** で伝える。両者は SigV4 の署名対象ヘッダに含める（署名済みのため経路上で改竄できない）。ゲストは**両ヘッダを送らない**（`Guest` というロール値を作らない）。**人間が 2026-07-27 に確定**（実装設計 D-9 の `port.Actor` と同じ決定） |
| D-3 | 稼働の量の表現 | 時・分の組 `{"hours": n, "minutes": n}` で表す。分は 0〜59。**小数・ISO 8601 duration・分の総和単一値を使わない**（UI が時・分で入出力し、値域の判定も時・分で行うため。`daily-record-entry.md` AC-3・`monthly-closing-ui.md`）。**時刻（1日の中の時点）には使わない**（D-14） |
| D-4 | 日付・年月の表現 | 対象日は `YYYY-MM-DD`、年月は `YYYY-MM`。**いずれもタイムゾーンを含めない**（暦日そのものを表す。当日判定は JST。`daily-record-entry.md` D-8） |
| D-5 | 日次の丸め値の返却 | 各稼働実績に**稼働時間**と**15分切り捨て後の寄与**の両方を含める（**2026-10-15 改定**: 稼働時間は入力値ではなく、**保存した時刻から算出した値**である＝`daily-record-entry.md` D-2・AC-2-6。旧: 「入力値」）。丸め規則を BFF / Web 側に再実装させないため（`daily-record-entry-ui.md` AC-1-2 の「整合」を BFF が計算せずに満たせる） |
| D-6 | 更新系の応答 | 入力・編集・削除・締め・承認・差戻しは、いずれも **更新後の勤務月の表現**を返す（BFF が再描画に使う。`work-month-screen-ui.md` AC-6-4 の「現在の状態を反映し直す」を1往復で満たす） |
| D-7 | 未生成の年月の取得 | 生成されていない `契約 × 年月` の取得は **404 にせず、空の下書き相当の表現**を返し、`generated: false` を添える（画面は「空状態と同じに見せる」。`daily-record-entry-ui.md` AC-2-2。かつ契約表示名・精算幅は常時表示が要る。`work-month-screen-ui.md` AC-1-1・AC-1-4） |
| D-8 | エラー表現 | `{"error": {"code": "...", "message": "..."}}`。**`code` が契約であり、利用者向け文言は BFF / UI が `code` から決める**（`message` は診断用。API は画面文言を持たない） |
| D-9 | 一覧の絞り込み | 単一のコレクション `GET /work-months` にクエリで絞り込む。**技術者を指定しない横断的な一覧は `state=PendingApproval` のときだけ許す**（承認済・下書きの横断一覧を構造的に不可能にする。P-7） |
| D-10 | API のバージョニング | **行わない**（消費者は BFF ただ1つ。ADR 0003 の一方通行）。パスに `/v1` 等を置かない |
| D-11 | 未生成の年月への**更新系**（締め・承認・差戻し） | **弾く（404 `WORK_MONTH_NOT_FOUND`）。** 締めを勤務月の生成契機にしない（`daily-record-entry.md` AC-1-5 を保つ）。`monthly-closing.md` D-6「空の勤務月は締められる」は**生成済みで実績0件の勤務月**を指すと確定した（同 D-6 の注記・AC-7-4）。**人間が 2026-07-27 に確定**。取得（D-7）とは扱いが異なることに注意 |
| D-12 | 参照系の認可 | **勤務月の取得（E-1）と `engineerId` 指定の一覧（E-2）は操作者で絞らない**（ゲストでも 200）。**承認待ち一覧（`engineerId` 省略 + `state=PendingApproval`）だけが `Approver` を要求する**。ゲスト＝閲覧のみ（`docs/rules/scope.md`・ADR 0016）というデモ公開の前提に沿う。**人間が 2026-07-27 に確定**（実装設計 AC-8-8〜AC-8-10 と同じ決定）。**本行は E-1・E-2 に限る決定であり、E-8・E-9 には及ばない**（D-20。2026-10-21 に人間が据え置きを確定＝決定9） |
| D-13 | 当該年月に属さない対象日への**削除**（E-4） | **400 `DATE_OUT_OF_WORK_MONTH`** で弾く（入力・編集の AC-4-7 と同じ表現に揃える）。**業務ルールの正解は `daily-record-entry.md` D-9・AC-5-5 が持ち**、本契約が定めるのはその違反の HTTP 表現（ステータス・`code`・判定順序上の位置＝AC-9 の順 6「業務バリデーション」）だけである。**未生成の年月への削除を 200 とする AC-5-3 の扱いより優先する**（未生成でも 400）。**人間が 2026-07-28 に確定**（それ以前の実装は 200 no-op だった） |
| D-14 | 時刻の表現（**2026-10-15**） | **時・分の組 `{"hour": n, "minute": n}`**（以下「**時刻オブジェクト**」）で表す。**稼働の量の時分オブジェクト `{"hours", "minutes"}`（D-3）とは別の形**とし、時刻と時間の長さを型で区別する（ユビキタス言語「時刻」`TimeOfDay` は「`WorkingHours` とは別の型」【確定】）。**文字列（`"9:15"` 等）・分の総和単一値を使わない**（D-3 が退けた理由＝UI が時・分で入出力し値域も時・分で判定する、は時刻にも当てはまる）。値の粒度と値域は `daily-record-entry.md` D-10・D-11 が持ち、本契約は書き写さない。**人間が 2026-10-15 に確定**（決定5） |
| D-15 | 休憩の表現（**2026-10-15**） | **`"break": null` または `"break": {"start": 時刻オブジェクト, "end": 時刻オブジェクト}`**。`null` が休憩なし、オブジェクトが休憩あり（休憩開始時刻＝`start`・休憩終了時刻＝`end`）。**休憩の有無を別のフィールド（`hasBreak` 等）に持たない。2つ目の休憩を表すフィールドを持たない**（`daily-record-entry.md` AC-3-10 の字面どおり）。2つ目に当たる値は**未知のフィールドとして無視する**（AC-4-10 の規則のまま）。リクエスト（AC-4）とレスポンス（AC-10-1）で同じ形を使う。**人間が 2026-10-15 に確定**（決定6） |
| D-16 | 時刻の違反の `code` と判定順序上の位置（**2026-10-15**） | **2つの `code` に分ける**: ①**時刻の値域外**（`daily-record-entry.md` AC-3 の 3-A のうち粒度・値域の行）→ **`TIME_OF_DAY_OUT_OF_RANGE`**、②**時刻の組み合わせの不正**（同 3-B の弾く行＝前後関係・休憩の前後・休憩の位置・稼働 0）→ **`INVALID_TIME_COMBINATION`**。**どちらも AC-9 の順6（業務バリデーション）**に置く。**項目の欠落・型の不正は従来どおり順2 の `INVALID_REQUEST`**（AC-4-9）。**`code` の分け方と位置は人間が 2026-10-15 に確定**（決定7）。**2つの `code` の名前は AI 起案（2026-10-15 に人間が承認）**である（決定7 で人間が選んだのは「2つに分ける」までで、名前は同日に別途承認した。名前を変えるときは本行・AC-9 の表・実装設計 AC-11-4 を同時に改める）。**帰結として `WORKING_HOURS_OUT_OF_RANGE` を廃する**（AI 起案（2026-10-15 に人間が承認））: 稼働時間を入力として受け取らなくなり（`daily-record-entry.md` D-2）、算出値に掛かる D-7 の違反のうち下限側（稼働 0）は ② に属すると人間が決め、上限側は 3-A・3-B を満たす入力から到達しない（同 AC-3-12）ため、**この `code` を生む要求が存在しない**。発生条件の無い `code` を表に残さない |
| D-17 | E-3 の順6 の中の順序（**2026-10-15**。AI 起案（2026-10-15 に人間が承認）） | E-3 で順6 の違反が複数同時に当たるときは **①時刻の値域外 → ②時刻の組み合わせの不正 → 当該月外（`DATE_OUT_OF_WORK_MONTH`）→ 未来日（`FUTURE_DATE_NOT_ALLOWED`）** の順に判定し、先に当たったものを返す（AC-4-13）。**業務ルールの優劣ではなく**（AC-9 の判定順序と同じ位置づけ）、この順序は**実装設計の構造から導かれる部分**と**AI が起案して選んだ部分**（2026-10-15 に人間が承認）からなる。**(1) 構造から導かれる部分**: 不正な値のインスタンスを存在させない（実装設計 AC-3 冒頭）ため、稼働実績が構築できなければ**稼働実績を受け取る集約のメソッド**（同 AC-4-1。当該月外 → 未来日の順に検査する）に到達しない。ゆえに **①・② → 当該月外 → 未来日** と、**ある休憩・稼働実績の構築（②）はそれが受け取る時刻の構築（①）の後**であることは一意に定まる。**(2) AI が起案して選んだ部分**（2026-10-15 に人間が承認）: **4つの時刻すべての値域の判定（①）を、休憩を含む組み合わせの判定（②）のいずれよりも先に行う**こと。構造だけでは一意に定まらない — 休憩の2時刻の構築と `Break` の構築を、開始時刻・終了時刻の構築より前に行っても不正なインスタンスは生じないため、開始時刻が値域外（`daily-record-entry.md` AC-3 の 3-2-b）で休憩の前後が不正（同 3-6-b）な入力に ② を返す順も構造上は成り立つ。これを ① に固定する理由は、(a) **AC-4-5-a が ② を「4つの時刻がいずれも 3-1・3-2 を満たし」たうえでの違反と定めている**こと（値域外の時刻を含む入力は ② の定義に入らない）、(b) 実装設計 AC-7-18 の **(i) 4つの時刻すべての `TimeOfDay` の構築 → (ii) `Break` と `DailyRecord` の構築** の順と一致させること、(c) どの時刻に値域外が現れても同じ `code` を返す（AC-4-5）のと同様に、**値域外の時刻の位置（開始・終了か休憩か）で返る `code` を変えない**ことである。組の期待は AC-4-13-b（休憩の時刻が値域外・開始と終了の組み合わせが不正）・AC-4-13-i（開始時刻が値域外・休憩の組み合わせが不正）・AC-4-13-j（終了時刻が値域外・休憩の組み合わせが不正）の3つで固定する。3つ要る理由は、**値域外を置く位置ごとに、その時刻の構築を `Break` の構築の後へ回す実装を検出する必要がある**ためである。開始時刻と終了時刻はそれぞれ独立に構築されるので、値域外を**開始と終了の両方の位置に**置く（4-13-i・4-13-j）。片方だけでは、もう片方の時刻の構築を `Break` の後へ回す実装が ② を返さず、Green のまま残る。休憩の側は、`Break` の構築が休憩開始・休憩終了の両時刻を受け取る（両時刻の構築が `Break` の構築より必ず先になる）ため、値域外を休憩の一方に置く1行（4-13-b）で足りる。2026-10-15 より前は順6 の中の順序を本契約が定めておらず、本行がそれを埋める。**E-4（削除）の順6 は当該月外だけ**であり、本行の対象外 |

| 5-3 | 未生成の `契約 × 年月`（`{date}` の年月は `{yearMonth}` と一致） | **200**。勤務月を**生成せず**、空の表現（`generated: false`）を返す（明示的な生成契機を作らない。P-5）。**削除は D-11（未生成なら 404）の対象外**である。削除の観測可能な結果は 5-2 と同じ「その日にレコードが無い」であり、404 にする理由が無いため。**`{date}` の年月が一致しない場合はこの行を適用しない**（5-8 が優先し 400） |
| 5-4 | 操作者が本人でない | **403 `FORBIDDEN_NOT_OWNER`** |
| 5-5 | 状態が `PendingApproval` / `Approved` | **409 `WORK_MONTH_NOT_EDITABLE`** |
| 5-6 | 実在しない `contractId` | **404 `CONTRACT_NOT_FOUND`** |
| 5-7 | ボディ | 取らない（送られても無視する） |
| 5-8 | **`{date}` の年月が `{yearMonth}` と一致しない**（例: `/work-months/ctr-0001/2026-07/daily-records/2026-08-01`） | **400 `DATE_OUT_OF_WORK_MONTH`**（`daily-record-entry.md` AC-5-5・D-9。D-13）。**当該日にレコードがあるか否か、勤務月が生成済みか否かを問わず 400**（5-1〜5-3 に優先する）。入力・編集の AC-4-7 と同じ `code`・ステータス |
| 5-9 | 5-8 と他の条件が同時に該当する場合 | **AC-9 の判定順序に従う。** 5-8 は**順 6（業務バリデーション）**であり、認証(1)・構文(2)・存在(3)・認可(4)・状態(5) の後に判定される。したがって、ゲスト → **401**（AC-1-6）、`{date}` が暦上存在しない／書式不正 → **400 `INVALID_REQUEST`**、実在しない `contractId` → **404**（5-6）、本人でない → **403**（5-4）、`PendingApproval` / `Approved` → **409**（5-5）が**先に**返る |

### AC-6. 締め（E-5）

| # | 条件 | 期待 |
|---|---|---|
| 6-1 | 生成済み・`Draft`・本人 | **200**。締めが成立し、超過／不足が確定した勤務月の表現を返す（`state: "PendingApproval"`、`excess` / `shortfall` は数値）。算出規則・境界は `monthly-closing.md` AC-4 が持つ |
| 6-2 | 状態が `PendingApproval` / `Approved` | **409 `INVALID_STATE_FOR_CLOSE`**（二重締め・終端。同 AC-1-2・AC-1-3） |
| 6-3 | 操作者が本人でない（他の技術者・承認者） | **403 `FORBIDDEN_NOT_OWNER`**（承認者の代行締めは無い。同 D-5・AC-2-2・AC-2-3） |
| 6-4 | 締めのタイミング | 月末・月途中を問わず受け付ける（月末制約を課さない。同 D-3・AC-1-4） |
| 6-5 | **生成済み**で稼働実績が0件（空月）／未入力日を含む月 | **締められる**（同 D-1・D-6・AC-7-1・AC-7-2）。未入力を理由に弾かない・警告を返さない |
| 6-6 | **未生成**の `契約 × 年月`（一度も入力されていない年月） | **404 `WORK_MONTH_NOT_FOUND`**（締めを生成契機にしない。P-5・`daily-record-entry.md` AC-1-5）。**人間が 2026-07-27 に確定**し、`monthly-closing.md` D-6 の「空の勤務月」は**生成済みで実績0件の月**（6-5）に限ると確定した（同 AC-7-4）。6-5 とは別物である |
| 6-7 | 締めの取り消し | **エンドポイントを設けない**（同 D-4・AC-6）。`PendingApproval` → `Draft` は差戻し（E-7）だけが起こす |
| 6-8 | ボディ | 取らない（送られても無視する） |
| 6-9 | 複数の条件が同時に該当する場合 | **AC-9 の判定順序に従う。** ゲスト → **401 `UNAUTHENTICATED`**（順1。AC-1-6）、`yearMonth` の書式不正 → **400 `INVALID_REQUEST`**（順2）、実在しない `contractId` → **404 `CONTRACT_NOT_FOUND`**（順3）、未生成 → **404 `WORK_MONTH_NOT_FOUND`**（順3。6-6。**操作者が本人でなくても 404 が先に返る**）、本人でない → **403 `FORBIDDEN_NOT_OWNER`**（順4。6-3）、`Draft` 以外 → **409 `INVALID_STATE_FOR_CLOSE`**（順5。6-2）。**締めには順6（業務バリデーション）に当たる判定が無い**（未入力日・空月を弾かないため。6-5・`monthly-closing.md` D-1・D-6） |

> **Issue #54（BFF / Web）への申し送り**: **未生成の月（`generated: false`）に締めボタンを提供しないのは BFF / Web 側の責務である。** ドメイン API は 404 `WORK_MONTH_NOT_FOUND` で弾くだけで、導線の抑止は行わない。`monthly-closing-ui.md` AC-5-2 の「空月でも締めボタンを提供する」は、`generated: true` かつ実績0件の月（6-5）を指す（`monthly-closing.md` AC-7-4）。**未生成の月に締めボタンを出すと、利用者から見て理由の分からない 404 になる。**

### AC-9. エラー表現・ステータスコード・判定順序

**エラーボディ**（すべてのエラー応答で共通）:

```json
{ "error": { "code": "INVALID_STATE_FOR_CLOSE", "message": "work month is not in Draft" } }
```

| # | 条件 | 期待 |
|---|---|---|
| 9-1 | 形 | `error.code`（文字列・下表のいずれか）と `error.message`（診断用の短い説明）。**フィールドを増やさない** |
| 9-2 | `code` の位置づけ | **`code` が契約である。** BFF / UI は `code` から利用者向け文言を決める（D-8。`work-month-screen-ui.md` AC-6-1 の「理由の提示」は BFF 側の責務） |
| 9-3 | `message` | 診断用。**利用者向け文言としてそのまま画面に出すことを前提にしない。** 機密・内部実装の詳細（SQL・スタックトレース等）を含めない（`docs/rules/security.md`） |

**判定順序**（複数の条件に該当する場合、**先に該当したものを返す**。テストが期待値を一意に決められるようにするための順序であり、業務ルールの優劣ではない）:

| 順 | 判定 | 例 |
|---:|---|---|
| 1 | 認証（更新系・承認待ち一覧・**E-8・E-9**での操作者ヘッダの有無。**2026-10-21 改定**＝D-22 ③。**E-10 も同じ**＝**2026-10-29 改定**、D-23 ⑦。**E-10 は順3〜順6 に当たる判定を持たない**） | ゲストが締めを実行 → 401。ゲストが承認待ち一覧を要求 → 401。ゲストが `yearMonth=2026-13` で契約一覧を要求 → 401（順2 より先＝AC-12-19-a） |
| 2 | リクエストの構文・型・書式 | `yearMonth=2026-13` → 400 `INVALID_REQUEST` |
| 3 | 対象の実在（契約 → 勤務月） | 未生成の月への承認 → 404 |
| 4 | 認可（本人・ロール・自己承認。**E-8・E-9 では「Engineer かつ本人」**＝D-20・D-22 ③） | 承認者ロールを持たない者が `Draft` を承認 → 403。承認者が契約一覧を要求 → 403 `FORBIDDEN_NOT_OWNER`。**E-8・E-9 は順3・順5・順6 に当たる判定を持たない**（D-22 ③） |
| 5 | 状態 | 承認者が `Draft` を承認 → 409 |
| 6 | 業務バリデーション（時刻の値域・時刻の組み合わせ・当該月外・未来日。**E-3 での順序は D-17**＝AC-9-7） | 本人が `Draft` に `daily-record-entry.md` AC-3 の 3-2-b に当たる終了時刻を入力 → 400 `TIME_OF_DAY_OUT_OF_RANGE`。本人が `Draft` に同 3-5-a に当たる時刻を入力 → 400 `INVALID_TIME_COMBINATION`（**2026-10-15 改定**。旧例「25時間0分を入力 → 400」は稼働時間を入力しなくなったため改めた）。本人が `2026-07` の `Draft` に対し `2026-08-01` の削除を要求 → 400 `DATE_OUT_OF_WORK_MONTH`（AC-5-8。**勤務月が未生成でも 400**。ただし同じ要求をゲストが行えば 401、他人が行えば 403、`Approved` に対して行えば 409 が先に返る） |

| # | 条件 | 期待 |
|---|---|---|
| 9-4 | 競合（他経路で状態が変わっていた） | 状態の検査で弾かれ 409 を返す。**部分的な更新を残さない**（更新は集約単位で原子的。`workmonth-implementation-design.md` AC-10-7）。BFF は 409 を受けて再取得する（`work-month-screen-ui.md` AC-6-4） |
| 9-5 | 版番号・ETag による楽観的排他 | **設けない**（`workmonth-implementation-design.md` AC-13-5） |
| 9-6 | 500 の応答 | `code: "INTERNAL_ERROR"` のみを返し、原因の詳細を含めない |
| 9-7 | 順6 の中の順序（**2026-10-15 追加**） | E-3 では **時刻の値域外 → 時刻の組み合わせの不正 → 当該月外 → 未来日**（D-17）。組の期待は AC-4-13。E-4 の順6 は当該月外だけである（AC-5-9） |

### AC-10. 表現（JSON）の定義

#### AC-10-1. 勤務月の表現（E-1・E-3〜E-7 の 200 応答）

```json
{
  "contractId": "ctr-0001",
  "contractDisplayName": "サンプル株式会社 / 基幹システム保守",
  "yearMonth": "2026-07",
  "state": "PendingApproval",
  "generated": true,
  "settlementRange": {
    "lowerBound": { "hours": 140, "minutes": 0 },
    "upperBound": { "hours": 180, "minutes": 0 }
  },
  "totalHours": { "hours": 180, "minutes": 15 },
  "excess": { "hours": 0, "minutes": 15 },
  "shortfall": { "hours": 0, "minutes": 0 },
  "dailyRecords": [
    {
      "date": "2026-07-01",
      "startTime": { "hour": 9, "minute": 15 },
      "endTime": { "hour": 17, "minute": 45 },
      "break": { "start": { "hour": 12, "minute": 30 }, "end": { "hour": 13, "minute": 15 } },
      "workingHours": { "hours": 7, "minutes": 45 },
      "roundedWorkingHours": { "hours": 7, "minutes": 45 }
    },
    {
      "date": "2026-07-02",
      "startTime": { "hour": 9, "minute": 0 },
      "endTime": { "hour": 18, "minute": 0 },
      "break": null,
      "workingHours": { "hours": 9, "minutes": 0 },
      "roundedWorkingHours": { "hours": 9, "minutes": 0 }
    }
  ]
}
```

（`dailyRecords` の2要素は `daily-record-entry.md` AC-2-6-a・AC-2-6-b の値。2要素目の稼働時間は同 AC-3-11。**2026-10-15 改定**: 旧例の稼働時間 8時間50分 → 寄与 8時間45分 は、時刻からの算出では生じない＝同 AC-6-2。`totalHours` 等は形の例示であり、2要素の合計ではない）

| フィールド | 型 | 説明 |
|---|---|---|
| `contractId` | string | 契約の識別子（AC-1-10） |
| `contractDisplayName` | string | **契約表示名**（人間可読。`work-month-screen-ui.md` AC-1-1・確定事項 Q9） |
| `yearMonth` | string | `YYYY-MM`（D-4） |
| `state` | string | `"Draft"` / `"PendingApproval"` / `"Approved"`（ユビキタス言語の英語名） |
| `generated` | boolean | 当該 `契約 × 年月` の勤務月が生成済みか（D-7・P-5） |
| `settlementRange.lowerBound` / `.upperBound` | 時分オブジェクト | 精算幅。生成済みなら**生成時に複写したスナップショット**、未生成なら契約が現在定める値（AC-2-2） |
| `totalHours` | 時分オブジェクト | 総稼働時間（各日を15分切り捨てて合計した値。`daily-record-entry.md` AC-6） |
| `excess` | 時分オブジェクト **または `null`** | 超過。`Draft` では `null`（未確定。P-6・AC-2-6） |
| `shortfall` | 時分オブジェクト **または `null`** | 不足。`Draft` では `null` |
| `dailyRecords` | 配列 | 稼働実績。**対象日の昇順**。レコードの無い日は要素として現れない（`daily-record-entry.md` D-5） |
