# インフラ（Terraform）— ホスティング本体とコストガードレール／GitHub OIDC

Issue #8 の仕様。ADR 0013（AWS ネイティブホスティング）・ADR 0003（Function URL の IAM 認証）・ADR 0014（実行ロールで呼ぶ）が決めた構成を、**Terraform として実在させる**ための受け入れ条件を定める。

**設定値そのものはここに書き写さない。** 予約同時実行数・Function URL の認証方式・Budgets の本数と閾値・ログ保持日数・使用禁止リソースの実体は `docs/rules/cost-guardrails.md` にあり、認証方針の実体は `docs/rules/security.md` にある。本仕様が持つのは、**#8 へ委譲されていた決定**と、**それらがコードとして満たすべき形（AC）**、および**その決定の帰結として Terraform の外に残る人手の手順**（「運用手順」節）だけである（ADR 0004。二重管理を作らない）。

---

## スコープ

`infra/terraform` に置く構成のうち、次を対象とする（D-1）。

- **tfstate の置き場所とロック**（D-2）
- **リージョンと provider**（D-3）
- **provider の取得経路と、実行時にネットへ出ない初期化**（D-10・D-20。取得は devcontainer のビルド時に済ませ、版は `.terraform.lock.hcl` が確定させる。**参照させる手段は D-26**）。**CI はレジストリから取得する**（D-22。経路がローカルと異なることは 12-22）
- **ホスティング本体** — S3（静的アセット）／CloudFront／**BFF・SSR Lambda**／**ドメイン API Lambda**（ADR 0013 の構成図）。**3本すべての Lambda のランタイム種別を #8 が決める**（ドメイン API は D-5、BFF・SSR は D-16、CloudFront 遮断は D-17。Terraform の `aws_lambda_function` が必須項目として要求するため）。**成果物そのものの生成は含まない**（D-13）
- **コストガードレールの取り付け** — 予約同時実行数・Function URL の認証方式・Budgets・Budget Actions・CloudFront 従量遮断回路（**遮断 Lambda を含む**）・ログ保持
- **IAM** — 各 Lambda の実行ロール（権限最小化）と、**CI（GitHub Actions）→ AWS の OIDC**（D-7）
- **ドメイン API のパッケージング**（D-5）・**CloudFront 遮断 Lambda のパッケージング**（D-17・D-18。`services/api` に `cmd` を1つ増やす）と、**Neon 接続文字列の取得経路**（D-4。`services/api` 側の改修を含む）
- **AWS API を呼ぶための Go 依存の追加**（AC-8 と AC-5-4 の帰結として**必然的に発生する**＝AC-9-14）。**手段は AWS SDK for Go v2**（D-19）で、**人間が承認した用途は3つ**（設定の解決 / SSM / CloudFront＝AC-9-15）**と、それらが依存する SDK のコアモジュール**（D-25。人間、2026-08-24。**承認範囲は計4本**）。版の反映先は `services/api/go.mod` と `.devcontainer/Dockerfile` の2箇所である（AC-9-16）。**依存解決の結果 direct require がこの承認範囲を超えた場合は停止して人間へ上げる**（AC-9-18）

### 非スコープ

- **Cognito（エンドユーザー認証）の構成** — Issue #52 が持つ（ADR 0016）。本仕様は Cognito のリソース・環境変数・IAM を定義しない
- **独自ドメイン・Route 53・ACM 証明書** — CloudFront の**既定ドメイン**で公開する（D-14）。証明書もホストゾーンも作らない（AC-11-9・AC-11-10）
- **OpenNext の導入・ビルド / デプロイ設定** — 別 Issue が持つ（D-13）。`docs/specs/web-app-scaffold.md` が「Terraform の Issue」へ送った項目のうち、**#8 が受けるのは成果物のパスを変数で受け取るところまで**である
- **SSM パラメータの値の投入** — Terraform の管理外（D-12）。**手順は本仕様の「運用手順」節が持ち、実値は `docs/` に残さない**
- **GitHub のリポジトリ設定・ruleset の codify（Terraform GitHub provider）** — ADR 0009「悪い影響」が **#8 のスコープ外**として見送り済み。本仕様はこの削減を維持し、GitHub provider を導入しない。GitHub Environment そのもの（承認ゲート）も GitHub 上の設定であり、Terraform の管理外である（AC-12-4）
- **デモデータの日次リセット**（`docs/rules/cost-guardrails.md` の該当行）— 本仕様が定義する Lambda は **3本**（BFF/SSR・ドメイン API・CloudFront 遮断）であり、リセット用の実行基盤は含まない。別 Issue で扱う
- **Route Handler のレート制限** — `apps/web` の実装であり、インフラではない
- **Neon（DB そのもの）のプロビジョニング** — AWS 外のマネージドサービスであり、Terraform の管理下に置かない
- **アプリケーションの業務ロジック・HTTP 契約** — `docs/specs/workmonth-implementation-design.md` / `docs/specs/domain-api-http-contract.md` が持つ。本仕様が触れるのは接続文字列の取得経路（AC-8）だけである
- **遮断 Lambda の遮断以外の振る舞い** — 本仕様が求めるのは**当該ディストリビューションの無効化**だけである（AC-5-4・AC-7-2）。通知の整形・復旧の自動化・他リソースの停止を持たせない
- **`docs/rules/` の改訂** — 本 Issue が触れるのは **D-8 / D-9 が名指す `docs/rules/cost-guardrails.md` の記述**だけである。**`docs/rules/scope.md` は改訂しない**（衝突しないことは P-5 で引き受ける）
- **本番への apply**（デプロイの実行）— 人間の承認事項（`docs/rules/responsibility.md`）。本仕様は構成と検証までを定める

## 前提（P）

### P-1. 決定は ADR 0013 / 0014 / 0003 で確定済み

ホスティングの選定・認証機構・Function URL の保護方式は決着している。本仕様はそれらを**再検討しない**。新たな技術選定に当たる判断は D の表に列挙したものに限る。**D-11 / D-20 / D-26 と、2026-08-24 に確定した D-21〜D-25 を除き、いずれも人間が 2026-08-21 に確定させた**（決定者の列を参照）。**D-16 と D-18 は仕様工程が導いた原案を、人間が 2026-08-21 に追認したものである**（D-16 は ADR 0013 から、D-18 は D-17 の採用理由から導いた）。仕様工程が埋めた **D-11 は既決事項（D-2）の帰結**、**D-20 は改訂後の D-10 の帰結**、**D-26 は AC-1-8 が実装工程へ明示的に委ねた手段の選択の記録**であり、いずれも**人間が選んだ決定ではない。覆すには人間の承認を要する**。

**2026-08-21、人間は次の3点を確定させた**（いずれも承認者は人間、日付は同日）。

1. **D-10 の改訂** — provider は devcontainer の**ビルド時に取得してイメージへ焼き、実行時はネットへ出ない**形にする（改訂前の「allowlist へ2ドメインを追加する」は採らない＝「D-10 の改訂」節）
2. **backend の検査を限界へ移す** — 要求（AC-2-1 / AC-2-2）は条文として残し、**機械検査だけを 12-20 へ移す**（旧 AC-10-4-k）
3. **遮断 Lambda の起動経路の検査を狭める** — assert は「SNS 購読が1つ存在する」までとし、**「それ以外のイベント源を持たない」ことの検査を 12-21 へ移す**（禁止そのものは AC-5-4・AC-11-22 が持ち続ける）

**2 と 3 は検査範囲を狭める緩和であり、人間の承認事項である**（`docs/rules/development-process.md`「要求を実装の都合で緩めない — 緩める判断は人間の承認事項」）。**承認済み: 人間、2026-08-21。この3点以外の要求を、この機会に緩めない。**

**2026-08-24、人間はさらに次の5点を確定させた**（いずれも承認者は人間、日付は同日）。

1. **provider の版の制約の形** — `infra/terraform/versions.tf` の制約は **provider のメジャー・マイナーまで固定する形**にし、**緩い下限のままにしない**（D-21・AC-1-10）
2. **CI の provider 入手経路** — CI は**レジストリから取得する**。温めが要る理由は devcontainer のファイアウォールであり、CI の runner には egress 制限が無い（D-22・AC-1-12）
3. **lock のプラットフォーム** — `.terraform.lock.hcl` に含めるのは **`linux_amd64` ただ1つ**とする（D-23・AC-1-9）
4. **12-20 / 12-21 を文字列検査で補わない** — 限界のまま残し、担保をレビューと規律に置く（D-24）
5. **direct require の承認範囲にコアを加える** — AC-9-15 の3用途に加え、**AWS SDK for Go v2 のコアモジュールが direct require に現れること**を承認する（D-25。承認範囲は計4本）

**4 は「検査を足さない」ことの確定であって、既存の要求（AC-2-1 / AC-2-2 / AC-5-4 / AC-11-22）を緩めるものではない。5 は承認範囲を1本広げるものであり、依存の許可リストと同じく人間の承認事項である**（`docs/adr/0010-harness-engineering.md` §A）。**承認済み: 人間、2026-08-24。この5点以外の要求を、この機会に緩めない。**

### P-2. 検証はプロバイダの取得を要し、実装は Go 依存の追加を伴う

`make lint-tf` は `terraform init -backend=false` を経由し、`terraform test`（D-6）も初期化を要する。すなわち**検証は provider の存在を前提とする**。**その provider は devcontainer の Dockerfile がビルド時（ファイアウォール未適用の時間帯）に取得してイメージへ焼き、実行時の初期化はネットへ出ずに成立させる**（D-10。既存の `GOMODCACHE` 温めと同型＝`docs/specs/devcontainer-go-module-policy.md`）。**実行時に配布元へ取りに行く経路を前提にしない**（その経路が決定的でない理由は 12-6）。

**devcontainer のリビルドが要る理由は、この provider の温め（D-10）だけではない。** AC-8（SSM からの取得）と AC-5-4（遮断 Lambda による CloudFront の無効化）は AWS API の呼び出しを要求し、**`services/api` の direct 依存が増える**（AC-9-14）。**実行時のモジュール取得は成立しない**ため、依存は `go.mod` → Dockerfile の `ARG` pin → リビルド、の順で入れる（`docs/specs/devcontainer-go-module-policy.md` P-3・`docs/rules/commands.md`）。**手段は D-19 で確定済み**だが、**リビルド前に `go get` / `go mod tidy` で凌がない**（順序の要求は手段の決着とは別であり、決着によって消えない）。**逆に「リビルドさえ済めば tidy を回してよい」とも読まない** —— **`go mod tidy` は import の無い direct require を削る**ため、**実装が SDK を import する前に回すと、入れたばかりの require がそのまま消える**。回してよい時点は **AC-9-19** が持つ。

**帰結として、`go.mod` の direct require に実際に何が並ぶかは、リビルド後の依存解決まで確定しない。** 本仕様はこれを推測で埋めず、**確定した集合が承認範囲を超えた場合の停止条件**として扱う（AC-9-18）。

provider の温め・依存の追加・**allowlist へ加えた2ドメインの取り消し**（D-10・AC-1-11）・リビルドはいずれも #8 の作業に含まれるが、**本仕様の AC はリビルドされたことを検査しない**（12-6・12-14・12-19）。

### P-3. ツールチェーンの版は本仕様が持たない

backend の `use_lockfile`（D-2）と `terraform test` / `mock_provider`（D-6）を解釈できる Terraform 版であることを要求する。**版の値は `.devcontainer/Dockerfile` と `.github/workflows/ci.yml` が現況として持ち、本仕様には書かない**（両者は同時に更新する＝`docs/rules/commands.md`）。

**この要求を構成側で表す制約（`required_version`）の持ち主は、各構成の `versions.tf` のままとする**（`infra/terraform` と、AC-2-4 で切り出した構成の双方）。**`.devcontainer/Dockerfile` / `.github/workflows/ci.yml` への一本化は #8 の範囲外であり、本仕様は組み替えを求めない**（人間、2026-08-27）。**制約の値も本仕様に書かない**（上と同じ扱い）。

### P-4. `sub` 粒度と機械検査は #8 へ委譲されていた

`docs/specs/security-rules.md` は、(i) `sub` 条件を `repo:[OWNER]/[REPO]` より細かい粒度まで固定する判断（同 非スコープ）と、(ii) 信頼ポリシーに `sub` 条件が実在することの機械検査（同 AC-7-4「約束するなら Issue #8 の仕様で明示的に引き受ける」）を、**本 Issue へ明示的に委譲していた**。本仕様は (i) を D-7 で、(ii) を AC-7・AC-10 で**引き受ける**。引き受ける範囲の限界は AC-12-1 に固定する。

### P-5. `services/` に業務ロジックでないコードが入ることを引き受ける

D-17 / D-18 により、`services/api` に **CloudFront 遮断 Lambda の `cmd`** が1本増える。これは業務ロジックではない。**既存の規約と衝突しないことを、本仕様がここで明示的に引き受ける。**

- `docs/rules/scope.md` が限定しているのは **MVP の業務ユースケース（3つ）**と**集約（WorkMonth ただ1つ）**である。遮断 Lambda は**ユースケースを1つも足さず、集約を1つも足さない**。`internal/domain` にも `internal/usecase` にも触れない（AC-9-10）
- 遮断 Lambda は `docs/rules/cost-guardrails.md` が定める**従量遮断回路の実行主体**であり、CLAUDE.md は「**コストとセキュリティのガードレールは機能要件と同格**」「後で入れることは許容しない」と定めている。すなわち**既存の規約が既に要求しているもの**であって、本仕様が新しい要求を足すのではない。**決まっていなかったのは置き場所だけである**（Q-8 → D-17）
- したがってこれは、`docs/rules/scope.md` が Cognito を「**4つ目の業務ユースケースを追加するものではなく、3ユースケースを支える横断的なインフラ**」として引き受けたのと**同型**である。遮断 Lambda も**横断的なインフラの実行主体**として扱う
- **`docs/rules/scope.md` へ同型の節を書き足さない。** 認証は「スコープに入れるか」自体が人間の決定だったため rules 側に節が要ったが、遮断回路は `docs/rules/cost-guardrails.md` が既に要求済みであり、置き場所の帰結まで rules へ書き写すと正解が二重になる（ADR 0004）。**この引き受けの持ち主は本仕様である**
- **本項を根拠に範囲を広げない。** 引き受けるのは `docs/rules/cost-guardrails.md` が要求する**遮断回路の実行主体1本**に限る。業務ユースケースを増やすこと、`services/` へこれ以外の非業務コードを足すことは、**別途人間の判断が要る**（`docs/rules/responsibility.md`）

### D-2 の逸脱を記録する — なぜ DynamoDB を作らないか

Issue #8 の本文は起票時点で「S3 + DynamoDB lock」を書いている。本決定は**そこから意図的に外れる**ため、逸脱した事実と理由をここに残す（Issue 本文は書き換えず、正解は本仕様が持つ＝ADR 0004）。

- **S3 backend が native lockfile を持つ**ため、ロックのためだけに別サービスのテーブルを作る必要がない
- **月額固定費が発生しうるリソースを1つ減らせる。** 単独開発でロック競合が起きないため、テーブルの設計・容量モードの選択がまるごと不要になる
- **`docs/rules/cost-guardrails.md` の使用禁止リストとは無関係**（DynamoDB は禁止リストに無い）。禁止だから避けるのではなく、**不要だから作らない**

### D-19 で採らなかった案 — なぜ Lambda 拡張でも自作署名でもないか

**(b) SSM だけ AWS Parameters and Secrets Lambda Extension（Lambda レイヤー）で取り、CloudFront は SDK — 採らない。**

- レイヤーが localhost に HTTP エンドポイントを出すため SSM 側は標準の `net/http` で済み、direct 依存が1つ減るのは事実である。しかし**レイヤーの ARN をリージョンごとに指定する必要**があり、**Terraform 側の要求が増える**（レイヤーの付与と ARN の変数化＝AC-4 / AC-7 の改訂）
- **レイヤーの版が AWS 側にあり、本仕様の外で動く。** 版の持ち主を `go.mod` / Dockerfile の外へ1つ増やすことになり、`docs/specs/devcontainer-go-module-policy.md` が固定した「版は2箇所へ同時に入る」という形から外れる
- **CloudFront の無効化は SigV4 を要するため、(b) を採っても SDK は入る。** 「SDK を入れずに済む」という利得は最初から得られない

**(c) SigV4 の署名を自作し、標準の `net/http` だけで両方を呼ぶ — 採らない。**

- **署名の誤りはランタイムでしか露見せず**、標準 `testing` + go-cmp（ADR 0007）で正しさを担保しにくい。実 AWS を呼ばない方針（12-9・12-15）と組み合わせると、**どのテストでも Red にならない誤りの面**ができる
- 得られるのは**依存の本数の削減だけ**であり、上記の代償と釣り合わない

### D-10 の改訂 — なぜ allowlist をやめ、ビルド時に温めるか

**改訂前の D-10 は「allowlist へ2ドメインを追加すれば、実行時に provider を取得できる」という前提に立っていた。この前提は機構として成立しない**（12-6）。`.devcontainer/init-firewall.sh` は**起動時に名前解決した IP を ipset へ入れる**方式であり、CDN 上のホストは A レコードを入れ替えて返すため、**スナップショットは陳腐化する**。到達は当たり外れになり、**決定的でない**（`docs/harness/verification-loop.md` ハーネスの性質1）。**当たりを引いた実行を「通る」と読まない。**

採る形は **provider をビルド時にイメージへ焼くこと**である。ファイアウォールが未適用の時間帯に取得を済ませ、実行時はネットへ出ない。`docs/specs/devcontainer-go-module-policy.md` が Go のモジュールについて既に採っている形と同型であり、**新しい方式を持ち込まない**。

**2ドメインの追加は取り消す。** 判断の分岐（実行時に版の解決が要るのか）に対する答えは次のとおり。

1. **版の解決は実行時に起きない。** 版は `.terraform.lock.hcl` が確定させ（D-20）、provider の実体はイメージに焼かれている。ビルド時の取得は**ファイアウォール未適用**の時間帯に行われ、allowlist の対象外である。したがって `registry.terraform.io` は**実行時には要らない**
2. **配布元は allowlist に置いても到達を担保できない**（上記）。置けば「効いているように見える死んだ設定」が残る
3. **残すと AC-1-7 の破れを隠す。** レジストリへ出られる状態では、ビルド時の温めが壊れていても初期化が（当たれば）成功し、**「ネットへ出ずに成功した」と区別がつかない。** 偽の緑を作る経路を残さない
4. **理由の消えた許可を残さない。** egress 制限を、目的の消えたまま広げたままにしない（D-3「理由の消えた alias を空で残さない」と同型）

**取り消しの範囲は、この2ドメインの行と、それを説明するコメントだけである。** Go のモジュールホスト2件（`proxy.golang.org` / `sum.golang.org`）には触れない —— `docs/specs/devcontainer-go-module-policy.md` AC-1-5 が「変更しない・削らない」と定めており、**本仕様はそこを覆さない**。

### D-20 の理由 — なぜ `.terraform.lock.hcl` をコミットするか

- **実行時にネットへ出ないなら、版を確定させる持ち主がリポジトリ側に要る。** lock が無ければ初期化は版の解決のためにレジストリへ出る（AC-1-7 に反する）か、環境ごとに別の版を掴む
- **`h1:` の有無で実行時の挙動が変わる。** レジストリ経由で生成した lock は配布元由来の形式のハッシュを持つが、**ローカルに焼いた provider はその形式では照合できない。** 照合できるハッシュ（`h1:`）が無ければ **init はチェックサム不一致で落ちる。** ゆえに「コミットする／しない」だけでは決めたことにならず、**含むべきハッシュの種類とプラットフォームまで**決める（AC-1-9）
- **コミットしない案を採らない。** 手元と CI が別の版を掴み、「ローカルで通るが CI で落ちる」を招く（`docs/rules/commands.md` が禁じる形）。lock を無視して毎回解決させる形も、実行時の取得を前提にする点で D-10 に反する
- **代償は版の持ち主が1つ増えること**（12-18）。それでも、**版が実行のたびに動く**ほうがハーネスの前提を強く壊す

### D-21〜D-25 の理由 — 制約の形・入手経路・プラットフォーム・検査を増やさないこと・承認範囲

**D-21 — 制約が実態と乖離したままだと、lock を消したときに古いメジャー版を引いて壊れる。** 版を確定させるのは lock であり（D-20）、**lock がある限り制約が緩いことは表面化しない**（12-24）。しかし lock を作り直す場面（版の更新・破損からの復旧・生成のやり直し）で、**緩い下限のままの制約は古いメジャー版の取得を許す**。焼いた provider（D-10）と食い違えば初期化が落ち、落ちなければ構成が想定していない版で解決される。**制約の形そのものを実態に合わせて固定しておく**ことで、この経路を塞ぐ。**版の値は制約にも本仕様にも書き分けない** —— 実体の持ち主は AC-1-10 の3者である。

**D-22 — 温めはファイアウォールへの対処であって、再現性の手段ではない。** provider をイメージへ焼くのは、devcontainer の実行時に外へ出られないためである（D-10・12-6）。**CI の runner にその制限は無い**（12-14・12-19 が既に記録している非対称）。CI にまで焼き込みやキャッシュを持ち込めば、**版の持ち主がもう1つ増え**（12-18 と同型）、温めが壊れていても CI が緑になる面が広がる。CI 側で版を確定させるのは lock であり（D-20）、レジストリからの取得はその照合を通る（AC-1-9・AC-1-12）。**入手経路が2つに分かれること自体は限界として残す**（12-22）。

**D-23 — 使われていないプラットフォームのハッシュを「将来のために」入れない。** devcontainer も CI の runner も amd64 であり、**現に実行されるのは1つだけ**である（D-3「理由の消えた alias を空で残さない」と同型）。**代償は、別アーキテクチャの開発機で `terraform init` がチェックサム照合に失敗して落ちること**である（12-23）。**落ちたときに lock を手で編集して凌がない**（AC-1-9）。足す判断は人間の承認事項であり、実装工程で決めない。

**D-24 — 検査の手段を2系統に増やさない。** 12-20 / 12-21 が検査できないのは、`terraform test` の assert が **plan に現れる値**しか参照できないためであり、構成ファイルへの文字列検査を足せば形式上は塞げる。しかし**構成の検査に `terraform test` と文字列検査の2系統が並ぶと、要求の持ち主が割れる** —— 片方だけを更新した状態が緑になり、**限界の所在も二重になる**。**限界であることを条文に残し、担保をレビューと規律に置くほうが、所在が1つに保たれる**（12-13・12-16 と同じ扱い）。**したがって「補ってもよい」と読まない。**

**D-25 — コアが direct に現れることは、承認範囲の拡大であって既定ではない。** AWS SDK for Go v2 は複数のモジュールに分かれており、3用途を import した結果として**コアが direct require に並ぶ可能性**を、本仕様は AC-9-18 で「確定するまで推測で埋めない」扱いにしていた（12-17）。**人間の調査で現れることが確定したため、承認範囲へ明示的に加えた**（人間、2026-08-24）。加えたのは**コア1本だけ**であり、**AC-9-18 の停止条件はそのまま残る** —— 承認範囲の4本に収まらないものが現れたら、`ARG` を足して通さずに停止する。

### D-26 の理由 — なぜ CLI 設定でミラーを既定にするか

**AC-1-8 は「手段は実装工程が選び、選んだ手段と採らなかった手段の理由を D として本仕様へ追記する」ことを求めていた。本節と次節、および D-26 の行が、その記録である**（Issue コメント・PR 本文に書いて済ませない＝ADR 0004）。

- **経路を塞ぐことが AC-1-7 の担保になる。** ミラーを CLI 設定の既定に据えると、初期化はレジストリを**参照しに行かない**。「出ようとしたが届かなかった」ではなく「出る経路が無い」形であり、**当たり外れが残らない**（12-6 が退けた ipset の性質と対照）
- **フォールバック（`direct`）を置かない。** 置けば、ミラーに無い provider を要求したときに**黙って外へ出る**。devcontainer では落ち、CI では通る（12-19・12-22 の非対称）ため、**温めの破れが CI の緑で覆い隠される**。これは D-10 の改訂 3 が「偽の緑を作る経路を残さない」として退けたものと**同じ性質**である。**ミラーに無いものを要求したら、明示的に失敗するほうを採る**（11-29）
- **`-platform=linux_amd64` を明示し、ビルドホストの実アーキテクチャに依存させない。** 省くとミラーの中身がビルドホスト次第になり、**`linux_amd64` ただ1つを持つ lock**（D-23・AC-1-9）と食い違う。食い違いは初期化のチェックサム照合の失敗として現れる（12-23 と同じ面）
- **AC-1-9 と噛み合う。** リビルド後、`terraform providers lock -fs-mirror=<イメージ内のミラーのディレクトリ> -platform=linux_amd64 <provider>` により、**ネットへ出ずに lock を生成できる**。この経路が生成する lock は **`h1:` を含み `zh:` を含まない形式**であり、**チェックサム照合は有効なまま成立する** —— **照合の無効化にも、lock の手編集にも当たらない**（AC-1-9 の要求を満たす。**`-upgrade` の常用で凌ぐ形にもしない**）
- **持ち主を増やさない。** ミラーのディレクトリのパスは Dockerfile と CLI 設定が実体として持ち、本仕様は**役割で参照する**（版の値を本仕様に書かないのと同型＝AC-1-6・AC-1-10）
- **既定化は、設定が実行ユーザーに読まれて初めて成立する。** CLI 設定が特権ユーザー専用の置き場所・所有のままだと、`terraform` を実行するユーザーからは**設定が無いのと同じ**になり、**「経路を塞いだつもりで開いたまま」**という最も見分けにくい破れ方をする（破れは手元でしか現れない＝12-19・12-22）。**置き場所と適用ユーザーまでを条文で押さえる**（AC-1-14）
- **この形が保たれていることは機械検査されない**（12-19。外向き通信の不在を assert する手段が無く、CI の runner には egress 制限が無い）。破れは **devcontainer の手元でだけ** `make lint-tf` / `terraform test` の失敗として現れる

### D-26 で採らなかった案 — なぜ `TF_PLUGIN_CACHE_DIR` でも `-plugin-dir` でもないか

**(a) `TF_PLUGIN_CACHE_DIR`（プラグインキャッシュ）へ温める — 採らない。**

- **キャッシュに当たっても、`init` がレジストリへメタデータ（版の一覧・署名）を照会しに行く余地が残る。** すなわち「実行時にネットへ出ない」（AC-1-7）を**構造として保証できない**。成否が当たり外れになる点は、**D-10 の改訂で退けた allowlist 案と同じ性質**である（12-6。**当たりを引いた実行を「通る」と読まない**）
- キャッシュは**取得経路を塞がない**ため、温めが壊れていてもレジストリへ出られる環境では初期化が成功する。**偽の緑を作る経路が残る**（D-10 の改訂 3 と同型）

**(b) 個々のコマンド呼び出しへ `-plugin-dir` を渡す — 採らない。**

- **`init` の既定を変えるのではなく、呼び出しごとにフラグを渡す形になる。** 本仕様が要求する初期化の経路は `make lint-tf`（`terraform init -backend=false`）と `terraform test` の**複数コマンド**、`infra/terraform` と AC-2-4 で切り出した構成の**複数ディレクトリ**にまたがる（AC-1-7）。**渡し漏れが1箇所でもあれば、そこだけレジストリを見に行く**
- しかも**渡し漏れは CI では緑のまま通り**（runner に egress 制限が無い＝12-19・12-22）、**手元でだけ落ちる**。**「渡し忘れたら通ってしまう」経路を作らない** —— CLI 設定による既定化は、忘れうる手順そのものを消す（担保を規律に置かない＝`docs/harness/verification-loop.md`）

| 1-13 | 手段の理由の持ち主（D-26） | **手段の選択とその理由（採らなかった案を含む）の持ち主は本仕様＝D-26 である。** `.devcontainer/Dockerfile` と CLI 設定には**参照だけを置き、「なぜこの形か」を説明する記述をそちらへ重ねない**（ADR 0004。理由が2箇所にあると、片方だけ更新された状態が緑のまま残る）。**現に選択理由の要約が Dockerfile 側へ書かれているなら、本仕様への参照1行程度へ縮める** —— **消すのは判断の理由であって手順ではない**（何をするコマンドかを示す記述は残してよい）。**この書き換えは本仕様の改訂（`docs:` コミット）では行わない** —— **`.devcontainer/` を触るのは実装 PR の側である**（AC-1-8 と同じく、仕様・テスト・実装を1コミットに混ぜない＝`docs/rules/commit-convention.md`） |
| 1-14 | CLI 設定の置き場所と適用ユーザー（D-26） | **CLI 設定（`.terraformrc`）は、devcontainer で `terraform` を実行するユーザーが読める場所・所有・権限で置く。** D-26 が要求するのは「ミラーを**既定**に据えて、レジストリを参照する経路そのものを塞ぐ」ことであり、**設定が実行ユーザーから読まれなければ既定化は成立しない**（設定が無いのと同じ状態になり、初期化はレジストリを見に行こうとする＝AC-1-7 の破れ）。**特権ユーザー専用の置き場所・所有のまま残さない。** **パスを本仕様に書かない** —— 実体の持ち主は `.devcontainer/Dockerfile` と CLI 設定そのものであり、本仕様は**役割で参照する**（D-26・AC-1-6・AC-1-10 と同型）。**環境変数で置き場所を指す形にする場合も、`make lint-tf` / `terraform test` を実行する経路すべてに効く形にする** —— **呼び出しごとに与える形にしない**（渡し漏れが1箇所でもあればそこだけレジストリを見に行く＝「D-26 で採らなかった案」(b)）。**この成立は機械検査されない**（12-19）。破れは **devcontainer の手元でだけ** 初期化の失敗として現れ、**CI では現れない**（12-22）。**落ちたことを理由に、フォールバックの `direct` を足して通さない**（11-29） |
| 1-15 | 両構成の lock が確定させる版と、制約の形の一致（D-26） | **`infra/terraform` の `.terraform.lock.hcl` と、AC-2-4 で切り出した構成の `.terraform.lock.hcl` は、同一の provider の版を確定させる。** AC-1-10 が持つのは**1つの構成における `versions.tf` ↔ lock ↔ `ARG` の一致**であり（**その内容をここへ書き写さない。参照する**）、**本条が足すのは、構成が2つに増えたことによる lock 同士の横方向の一致**である。**理由は、温めの `ARG` が1本しかないこと** —— `.devcontainer/Dockerfile` が provider を温める `ARG` は1つであり、**ビルド時に作られるミラーには単一の版しか入らない**（D-26・AC-1-7）。**片方の lock がそれと異なる版を確定させていると、その側の `terraform init` はミラーに存在しない版を要求して落ちる** —— フォールバックの `direct` を置かないため（D-26・AC-1-14）、**外へ出て埋めることもできない**。**版の値を本仕様に書かない** —— 実体の持ち主は `versions.tf`・**両構成の lock**・`ARG` である（AC-1-6・AC-1-10・AC-9-16 と同型）。**版を上げるときに同時に直す対象には、両構成の lock が含まれる**（AC-1-10 の「同一 PR で同時に直す」の適用先）。**この横方向の一致は機械検査されない**（12-18）。**ずれて落ちた側の lock を手で編集して凌がない。`-upgrade` で解決し直す形にもしない**（AC-1-9。lock は生成物である＝D-20）。**`ARG` を増やして両方の版をミラーへ入れる形でも通さない**（11-32）。**一致させる対象は版だけではない** —— **`versions.tf` の制約の形も両構成で一致させる。** 切り出した構成の `versions.tf` は、`infra/terraform` の `versions.tf` と**同じ制約の形** —— すなわち **AC-1-10 が定める「provider のメジャー・マイナーまで固定する形」** —— を持ち、**片方だけを緩い下限のままにしない**（D-21・11-25）。**制約の値を本仕様に書かない**（AC-1-6・AC-1-10 と同型）。**理由は、制約の食い違いが lock を作り直すまで表面化しないこと** —— 版を確定させるのは lock であり（D-20）、片方の制約が緩くても**既存の lock がある限り初期化はその版で通る**。**破れが現れるのは lock を作り直したときであり、そこで緩い側だけが別の版を引き、上の横方向の一致が崩れる**（12-24 と同じ遅延経路）。**この一致も機械検査されない**（12-18・12-24）。だからこそ**制約の側を揃えさせ、レビューで見つけられる形にしておく**。**版と制約の形に加えて、両構成は同じ provider の集合を要求する。** 切り出した構成が `infra/terraform` に無い provider を要求すると、**ビルド時に温めたミラーにその provider が入っておらず、その側の `terraform init` が落ちる**（AC-1-7・D-26）—— フォールバックの `direct` を置かないため（AC-1-14・11-29）、**外へ出て埋めることもできない**。**provider の名前を本仕様に書かない** —— 実体の持ち主は**両構成の `versions.tf`** である（AC-1-6・AC-1-10 と同型）。**足りない側を、`ARG` を増やしてミラーへ別の provider を入れる形で通さない**（11-32 と同型）。**この集合の一致も機械検査されない**（12-18） |

### AC-8. Neon 接続文字列の取得経路（D-4・D-12）

**この AC は `services/api` 側の改修を伴う。** `docs/specs/workmonth-implementation-design.md` AC-10-12 は「接続情報は**環境変数から取得**する」と定めており、D-4 はその出所を変える。**両者の関係を次のとおり解決する。**

## 未決（Q）— 残っていない

**Q-1〜Q-9 はすべて確定済み**（Q-1〜Q-7 は 2026-08-21、Q-8 は同日に人間が (a) で確定＝D-17、Q-9 も同日に人間が (a) で確定＝D-19）。**いずれも D / AC へ移した。番号は再利用しない**（決着済みの論点をここに残さない＝ADR 0004）。**本仕様に人間の判断待ちの論点は残っていない。**

**新たに人間の判断を要する論点が出たら、推測で埋めず、Q-10 以降として本節へ起票する**（`docs/ai-collaboration.md`「AIの停止条件」）。**実装工程が停止すべき既知の条件は、Q ではなく AC 側が持つ** —— **AC-9-18**（direct require が承認範囲を超えたとき）・**AC-4-7**（Node のマネージドランタイムに `apps/web` の版が無いとき）・**AC-3-3**（特定リージョンを要するリソースを持ち込む必要が生じたとき）・**12-10**（デプロイロールの権限が足りないとき）・**AC-1-8**（provider の参照手段を選んだ結果、`docs/rules/` の改訂が要るとき。**手段そのものは D-26 で確定済みであり、変える必要が生じたときも同じく停止して人間へ上げる**）・**11-24**（実行時の初期化が落ちたとき —— allowlist へ足し直して通さない）。**これらは「未決」ではなく「決まった要求に反する事態が観測されたときの扱い」であり、Q へ戻さない。**

## 運用手順 — SSM パラメータの値の投入（D-12・AC-8-2）

**手順の持ち主は本仕様である。** 値の出所（D-4）と「Terraform を値の管理者にしない」（D-12）を決めたのが本仕様であり、別ファイルへ切り出すと参照の持ち主が二重になる（ADR 0004）。**この節は AC ではなく、機械検査の対象でもない**（12-5）。

- **投入は人間が Terraform の外で行う**（AWS CLI の `aws ssm put-parameter` またはマネジメントコンソール）。**apply より前に投入しておく** — 無いままだとドメイン API がコールドスタートで失敗する（AC-8-5）
- パラメータの**名前は Terraform の変数に与えたものと同一**にする。**型は `SecureString`**、**鍵は AWS 管理鍵 `alias/aws/ssm`**、**階層は標準パラメータ**（D-4）。**リージョンは既定リージョン**（D-3）
- 値を差し替えるときも**同じ経路で上書きする。Terraform を経由させない**
- **値をシェルの履歴やプロセス一覧に残さない形で渡す**（平文をコマンド引数に置かない）
- **実値（接続文字列・パラメータ名の実値・アカウント ID）を `docs/`・Issue・PR・チャットに残さない**（`docs/rules/security.md`）。**本節にも書かない**

**`terraform test` が検査するのは「構成ファイルがどう書かれているか」までである。** 実際に AWS 上へ適用された結果・課金の実額・遮断の実効性は、この仕様では機械検査しない。
