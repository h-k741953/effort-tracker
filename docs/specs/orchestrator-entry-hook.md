# 入口ガード hook — オーケストレーターを必須の入口にする

工程をまたぐ依頼が main エージェントへ直接届くことを、`UserPromptSubmit` hook で機械的に止める。根拠は `docs/adr/0011-orchestrator-required-entry.md`。

**このファイルが検知パターンの単一情報源である。** ADR・エージェント定義・スクリプトへ条件を書き写さない（ADR 0004）。

---

## 対象

| 項目 | 値 |
|---|---|
| hook イベント | `UserPromptSubmit` |
| 配線 | `.claude/settings.json` の `hooks` キー |
| 検知本体 | `.claude/hooks/check-prompt-entry.sh` |
| テスト | `.claude/hooks/test-check-prompt-entry.sh`（fixture。`make test-hooks` に組み込み、`make test` から実行される） |

`test-scripts` に相乗りさせないのは、`.github/scripts` が CI スクリプトであるのに対し `.claude/hooks` はハーネス（Claude Code）側の資産であり、対象種別が異なるためである。

配線は `hooks.UserPromptSubmit[].hooks[]` に `type: "command"` / `command` / `timeout` を置く形とする。**`UserPromptSubmit` は `matcher` を非対応**（指定しても黙って無視される）なので書かない。`timeout` の既定は 30 秒。プロジェクトルートの参照には `${CLAUDE_PROJECT_DIR}` を使う。

検知本体は stdin 以外の入力を持たない純粋なフィルタとする。**`.github/scripts/check-review-trail.sh` と同じく、入力を差し替えればローカルで完全に実行でき、fixture で検査できること**を要件とする。

## 前提（P）

> **P-1 / P-2 / P-3 の検証環境**: Claude Code **2.1.214** / **2026-07-18** 実測。リポジトリ外の一時ディレクトリに payload を記録するだけの log-only hook を仕込み、`claude -p` を1回実行して stdin payload を採取した。**これは Claude Code のバージョンに依存する前提であり、本リポジトリが決められる事柄ではない。**

### P-1. `UserPromptSubmit` の終了コード規約 — **確定（実測 + 公式ドキュメント）**

| 終了コード | Claude Code 側の挙動 | 根拠 |
|---|---|---|
| `0` | プロンプトを通す。**stdout の内容はコンテキストへ注入される**（`UserPromptSubmit` の特例） | 公式ドキュメント |
| `2` | **プロンプトをブロックし、main へ渡さない。stderr のテキストが人間に表示される** | 公式ドキュメント |
| `0` / `2` 以外 | ブロックしない非致命エラー。stderr を人間に表示し、処理は続行する | 公式ドキュメント |

**ブロックの表明手段として、終了コード 2 方式を採る**（exit 0 + stdout に `{"decision":"block","reason":...}` を出す JSON 方式は採らない）。理由は3点。

1. **stdout の扱いを1つの不変条件に統一できる。** 本 hook は「stdout に何も出さない」を全経路で守ればよくなる（AC-4-2 / AC-5-2）。JSON 方式を混ぜると、通過時は無出力・ブロック時は JSON という**経路依存の規約**になり、実装の誤りが「無関係な文字列がコンテキストへ注入される」という静かな汚染として出る
2. **理由を人間に返す経路が stderr で明示される。** ADR 0011 決定3 は「判断は AI ではなく人間に返す」と定める。stderr は AI に渡らないことが規約で確定しているが、stdout 上の JSON を Claude 側がどう扱うかは本リポジトリの制御外である
3. **シェルスクリプトで任意文字列を JSON へ埋め込む必要がない。** ブロック理由には一致した検知パターン（＝人間の入力に由来する文字列）が入る（AC-4-6）。JSON 方式はここにエスケープ処理を要求し、AC-8-4 と同種の入力起因の破綻面を増やす

> **JSON 方式は未実測である。** 上記は公式ドキュメントの記述に基づく選択であり、実測で確認したのは終了コード方式の payload 側のみ。**JSON 方式へ切り替えるときは実測をやり直すこと。**

### P-2. 発火範囲 — **確定（実測）**

`UserPromptSubmit` は**人間がプロンプトを送信したときにのみ発火し、`Task` によるサブエージェント起動では発火しない**。Task でサブエージェントを1体起動させるプロンプトを1回実行し、記録された payload が1件のみであることを確認した。

**したがって、オーケストレーター → 工程エージェントの正規経路は本 hook にブロックされない。** 本仕様はこの性質に依存する。

> **payload にエージェント識別子のフィールドは存在しない**（`agent_id` / `agent_type` 等は無い。全キーは P-3 のとおり）。**hook 側でサブエージェント由来かを判定する手段は無く**、正規経路が守られるのは上記の発火範囲そのものによる。限界は AC-6-4 / AC-6-5 に記す。

### P-3. 入力形式 — **確定（実測）**

stdin に JSON が1つ渡る。全キーは次の7つ。

```
cwd / hook_event_name / permission_mode / prompt / prompt_id / session_id / transcript_path
```

- `hook_event_name` の値は `"UserPromptSubmit"`
- **人間の入力した文字列を持つキーは `prompt` である**（`user_input` ではない）。判定は `prompt` の値のみを見る
- 上記以外のキーは本仕様では使用しない

## 受け入れ条件

判定の優先順位は **AC-1（許可） > AC-2（ブロック） > AC-3（通過）** とする。

### AC-1. `[direct]` で始まるプロンプトは常に通す

許可の**唯一の**条件である。`prompt` の**先頭の空白文字（スペース / タブ / 改行）を除いた直後**が、半角8文字の `[direct]` に完全一致する場合に許可する。

| # | 入力（`prompt`） | 期待 | 備考 |
|---|---|---|---|
| 1-1 | `[direct] 一覧APIを実装して` | **通す** | ブロック条件に一致しても許可が優先する |
| 1-2 | `\n\n  [direct] 実装して` | **通す** | 先頭の空白・改行は無視する |
| 1-3 | `[direct]実装して` | **通す** | トークン直後の空白は要求しない |
| 1-4 | `[direct]` のみ | **通す** | 本文が無くてもよい |
| 1-5 | `よろしく [direct] 実装して` | **ブロック** | 冒頭でない |
| 1-6 | `実装して [direct]` | **ブロック** | 冒頭でない |
| 1-7 | `[Direct] 実装して` | **ブロック** | 大文字小文字を区別する |
| 1-8 | `[DIRECT] 実装して` | **ブロック** | 同上 |
| 1-9 | `［direct］ 実装して` | **ブロック** | 全角角括弧は一致しない |
| 1-10 | `[ direct ] 実装して` | **ブロック** | 内側の空白は一致しない |
| 1-11 | `(direct) 実装して` | **ブロック** | 括弧の種類が違う |

**曖昧な一致を許さない。** 揺れを許すほど「うっかり一致」が増え、例外が意図的な選択でなくなる（ADR 0011 決定2）。

### AC-2. 工程をまたぐ依頼はブロックする

`prompt` が **B-1 または B-2 のいずれか**に一致したらブロックする。

#### B-1. 変更指示（コードベース・docs への変更を伴う依頼）

**一致させるのは指示形のみである。名詞単独では一致させない。**

`実装` `修正` のような名詞は、変更依頼だけでなく質問・説明・調査の対象としても最頻で現れる（「この実装どうなってる?」「この修正の意図を教えて」）。名詞で一致させると AC-3 の「質問・調査・説明は通す」が実挙動と食い違い、かつ質問のたびに `[direct]` を打つ習慣が生じて hook が実質無効化される（ADR 0011 悪い影響の退化リスクが例外ではなく常態になる）。したがって**動作語と指示語尾の連接**で一致させる。

##### B-1-a. 動作語（サ変名詞型）

| 記号 | 語 |
|---|---|
| S | `実装` `修正` `対応` `作成` `追加` `削除` `リファクタ` `リファクタリング` `コミット` `起票` |

一致条件は次のいずれか。**S の直後に連接すること**を要求し、間に助詞・空白・記号を挟むものは一致させない。

- `S` + `し` + 指示語尾 T
- `S` + `せよ`
- `S` + `お願い` / `S` + `おねがい`

##### B-1-b. 動作語（動詞連用形型）

| 記号 | 語 |
|---|---|
| V | `直し` `作っ` `消し` `書い` `書き換え` `置き換え` |

一致条件は `V` + 指示語尾 T。**`ろ` は適用しない**（`直しろ` は非文であり、五段動詞の命令形 `直せ` `作れ` `消せ` は下記の理由で拾わない）。

##### B-1-c. 指示語尾 T

| # | 形 | 一致する例 | 一致しない例 |
|---|---|---|---|
| T-1 | `て` + **区切り** | `実装して` / `実装して、` / `直して。` | `実装している` / `実装しても` |
| T-2 | `て` + **依頼接尾** | `実装してください` / `直してもらえる?` | 同上 |
| T-3 | `といて` | `実装しといて` / `直しといて` | — |
| T-4 | `ろ`（B-1-a のみ） | `実装しろ` | — |

- **区切り**: 文字列の終端 / 改行 / 空白（半角・全角スペース、タブ）/ `。` `、` `．` `，` `.` `,` `!` `！` `?` `？`
- **依頼接尾**: `くれ` `ください` `下さい` `ほしい` `欲しい` `おいて` `もらえ` `もらい` `もらっ` `いただけ` `いただき`

区切りと依頼接尾を列挙で閉じるのは、`実装している` `実装しても`（進行・仮定であって依頼ではない）を通すためである。**これは「文字を後置きすれば逃げられる」構造ではない。** T-2 が依頼表現側を明示的に拾っており、逃げるには依頼であることをやめる必要がある。

##### B-1-d. 拾わない形（意図的な偽陰性）

| 形 | 例 | 理由 |
|---|---|---|
| 名詞単独 | `この実装どうなってる?` `テストの修正箇所はどこ?` | 上記のとおり。**これが本節の主目的である** |
| 助詞を挟む依頼 | `実装をお願いします` `修正のほうお願い` | S と指示語尾の間に助詞が入る。連接規則を緩めると名詞形の質問へ再び波及する。**代償として偽陰性へ回ることを承知で採る** |
| 五段動詞の命令形 | `直せ` `作れ` `消せ` | 可能形（`直せますか?` `作れる?`）と同綴で区別できない。質問を誤爆する |
| 進行・仮定・完了 | `実装している` `実装してある` `実装しても` | 依頼ではない。T-1 / T-2 の列挙から外れる |

##### B-1-e. 英語

`implement` のみを、**大文字小文字を区別せず語境界で**一致させる。

- **`implement` は残す。** 名詞形は `implementation` であり別語なので、語境界一致すれば動詞用法だけを拾える。名詞形の混入が起きない
- **`fix` は語彙から外す。** 名詞と動詞が同綴（`the fix` / `a quick fix`）で、語境界一致では区別できない。残すと `What is the fix?` のような質問がブロックされ、日本語側で是正したのと同じ非対称を英語側に残すことになる
- **`the` / `a` / `this` などの限定詞を前置きの除外条件にする案は採らない。** 文字列の付加によって除外が成立する構造であり、Issue #25 の往復4 C-1 で塞いだすり抜けと同型になる
- 代償として `fix this bug` は偽陰性へ回る。本リポジトリの運用言語は日本語（ADR 0010 §G）であり、英語の網羅より判定規則の一貫性を優先する

#### B-2. Issue / PR への着手指示

`Issue #<数字>` または `#<数字>` を含み、**かつ** B-1 のいずれか、または次のいずれかに一致する。

B-1 と**同じ指示形の規則**を適用する（名詞単独では一致させない）。

| 型 | 語 | 接続 |
|---|---|---|
| 動詞連用形 | `やっ` `進め` `片付け` | + 指示語尾 T（B-1-c） |
| サ変名詞 | `着手` | B-1-a と同じ |
| 依頼単独 | `お願い` `おねがい` | そのまま一致 |

`着手` を名詞単独で拾わないのは B-1 と同じ理由による（`#30 の着手条件は?` は質問である）。`お願い` / `おねがい` は語そのものが依頼表現であり、名詞形の質問用法を持たないため単独で残す。

番号だけの言及（AC-3 の 3-6）はブロックしない。

| # | 入力（`prompt`） | 期待 | 一致 |
|---|---|---|---|
| 2-1 | `稼働実績の一覧APIを実装して` | **ブロック** | B-1-a `実装` + T-1（終端） |
| 2-2 | `Issue #30 を対応して` | **ブロック** | B-1-a `対応` + T-1 / B-2 |

| 2-5 | `テストを書いてから実装して` | **ブロック** | B-1-a `実装` + T-1（末尾）。冒頭の `書いて` は直後が `か` のため不一致 |
| 2-6 | `WorkMonth に締め処理を追加して` | **ブロック** | B-1-a `追加` + T-1 |
| 2-7 | `Please implement the close-month usecase` | **ブロック** | B-1-e `implement` |
| 2-8 | `docs/rules/scope.md に1行追加して` | **ブロック** | B-1-a。**偽陽性だが仕様どおり**（AC-6-2） |
| 2-9 | `Issue #30 お願い` | **ブロック** | B-2 依頼単独 |

| 2-14 | `締め処理を実装しといて` | **ブロック** | T-3 |

### AC-3. 工程をまたがない依頼は通す

B-1 / B-2 のいずれにも一致しないものは通す。**調査・質問・要約・説明は変更指示ではない。** 変更対象を名詞として指す質問（「この実装は」「この修正の」）も、指示形でない限り変更指示ではない。

| # | 入力（`prompt`） | 期待 | 理由 |
|---|---|---|---|
| 3-1 | `ADR 0010 の §D は何を決めている?` | **通す** | 質問 |
| 3-2 | `make verify は何を呼ぶ?` | **通す** | 質問 |
| 3-3 | `docs/rules/ を読んで要約して` | **通す** | `要約` は B-1 に無い |
| 3-4 | `CI が落ちた原因を調査して` | **通す** | `調査` は B-1 に無い |
| 3-5 | `check-domain-deps が -test を付ける理由を説明して` | **通す** | `説明` は B-1 に無い |
| 3-6 | `#30 の背景を教えて` | **通す** | 番号の言及のみ。B-2 の着手表現が無い |
| 3-7 | `` （空文字列） | **通す** | 判定対象が無い |
| 3-8 | `   ` （空白のみ） | **通す** | 同上 |
| 3-9 | `fixture の prefix を確認したい` | **通す** | B-1-e から `fix` を外したため一致しない |
| 3-10 | `この実装どうなってる?` | **通す** | **名詞形。`実装` の直後が `ど`**（B-1-d） |
| 3-11 | `今の実装を説明して` | **通す** | **名詞形。`実装` の直後が助詞 `を`。`説明` は B-1 に無い** |
| 3-12 | `この修正の意図を教えて` | **通す** | **名詞形。`修正` の直後が助詞 `の`** |
| 3-13 | `テストの修正箇所はどこ?` | **通す** | **名詞形。`修正` の直後が `箇`** |
| 3-14 | `もう実装している?` | **通す** | T-1 / T-2 に無い形（`して` の直後が `い`） |
| 3-15 | `この機能は実装してある?` | **通す** | 同上（`あ`） |
| 3-16 | `ここを修正しても大丈夫?` | **通す** | 同上（`も`） |
| 3-17 | `この関数は直せる?` | **通す** | 五段動詞の可能形。命令形 `直せ` を拾わない帰結（B-1-d） |
| 3-18 | `spec にそう書いてある` | **通す** | `書い` + `て` の直後が `あ` |
| 3-19 | `#30 の着手条件は?` | **通す** | `着手` の直後が `条`。B-2 も指示形に絞る |
| 3-20 | `implementation の方針を教えて` | **通す** | `implement` の語境界に誤一致しないこと |
| 3-21 | `実装をお願いします` | **通す** | **偽陰性。仕様どおり**（B-1-d / AC-6-6）。助詞を挟む依頼は拾わない |
| 3-22 | `Where is the fix?` | **通す** | `fix` を語彙から外した帰結（B-1-e） |

3-10〜3-13 は**実測で偽陽性が確認されたケース**である（名詞を裸で語彙に登録していたため一律ブロックされていた）。3-21 / 3-22 は**通ることが仕様であって、検知漏れの放置ではない**。

### AC-4. ブロック時の出力

| # | 条件 | 期待 |
|---|---|---|
| 4-1 | ブロックする | 終了コード **2**（P-1。JSON 方式は採らない） |
| 4-2 | ブロックする | メッセージは **stderr** に出す。**stdout には何も出さない** |
| 4-3 | ブロックする | ブロックした理由（工程をまたぐ依頼はオーケストレーターが入口であること）を含む |
| 4-4 | ブロックする | **回避手段1**: オーケストレーターを使う旨を含む |
| 4-5 | ブロックする | **回避手段2**: 冒頭に `[direct]` を付ける旨を、**トークンそのものの表記を含めて**示す |
| 4-6 | ブロックする | 一致した検知パターンを含む。**一致した語（動作語 + 指示語尾の実文字列。例: `実装して`）を示す**。動作語だけでは、名詞形が通ることとの区別が人間に伝わらない。**なぜ止まったかを人間が判断できること** |
| 4-7 | ブロックする | 根拠として `docs/adr/0011-orchestrator-required-entry.md` を参照する |
| 4-8 | ブロックする | メッセージは日本語（ADR 0010 §G） |

4-2 で stdout を使わないのは、`UserPromptSubmit` の stdout がコンテキストへ注入されるためである（P-1）。exit 2 の stderr は人間にのみ表示される。**ブロックの理由は AI ではなく人間に返す**（ADR 0011 決定3）。

### AC-5. 通過時の出力

| # | 条件 | 期待 |
|---|---|---|
| 5-1 | 通す（AC-1 / AC-3 のいずれでも） | 終了コード **0**（P-1） |
| 5-2 | 通す | **stdout に何も出力しない** |
| 5-3 | 通す | **stderr にも何も出力しない** |

5-2 は必須である。stdout はコンテキストへ注入されるため、`OK` のような文字列を出すと**毎プロンプトに無関係な文字列が混入する**。ここは `check-domain-deps` の「黙って成功させない」とは要求が逆になる。通過が既定の経路であり、可視化の利益より汚染のコストが上回るためである。

### AC-6. 限界 — 完全な検知は保証しない

**この検査は網羅的でない。以下は仕様どおりの挙動であり、欠陥ではない。**

| # | 内容 |
|---|---|
| 6-1 | **偽陰性は残る。** 「例のやつ、いい感じにしといて」のような言い換えは B-1 / B-2 に一致せず**通る**。検知パターンを増やしても、自然言語である以上ゼロにはならない。受け皿は `docs/rules/responsibility.md` の規律層（ADR 0011 決定1・決定5） |
| 6-2 | **偽陽性は `[direct]` で回避する。** 軽微な変更（2-8）もブロックされるが、恒久的に詰まることはない。ただし**回避手段があることを、偽陽性を放置してよい理由にしない。** 名詞形の質問（3-10〜3-13）のように**最頻のやり取りで常時発火する偽陽性**は、`[direct]` を常用する習慣への退化を招き、hook を実質無効化する（ADR 0011 悪い影響）。この種の偽陽性は逃げ道で吸収せず、検知条件の側を直す |
| 6-3 | この hook は `.claude/settings.json` に依存し、**CI では動かない。設定を外せば無効化できる** |
| 6-4 | P-2 のとおり、サブエージェント起動には発火しない。**これは正規経路を通すために必要な性質であると同時に、検知の穴でもある。** main が Task で起動した先のプロンプトは一切検査されない |
| 6-5 | **6-4 の非対称性は hook 側で埋められない。** payload にエージェント識別子が無いため（P-3）、hook は「誰の入力か」を知る手段を持たない。発火しない経路に対しては、検知の強弱ではなく**存在しない**。受け皿は 6-1 と同じく規律層 |
| 6-6 | **指示形に絞ったことで、助詞を挟む依頼が偽陰性へ回る。**「実装をお願いします」「修正のほうお願い」は通る（3-21）。これは 6-1 と違い**設計上の選択**であり、名詞形の偽陽性（6-2）を下げるために意図的に引き受けた代償である（ADR 0011 悪い影響）。**連接規則を緩めて拾いにいかないこと。** 緩めれば名詞形の質問へ再び波及する |
| 6-7 | **英語は `implement` のみを拾い、`fix` は拾わない**（B-1-e）。`fix this bug` は通る（3-22）。名詞と動詞が同綴で機械的に区別できないための選択であり、日本語運用（ADR 0010 §G）を前提に許容している |
| 6-8 | **P-1 / P-2 / P-3 は Claude Code 2.1.214（2026-07-18 実測）に対する前提であり、バージョン依存である。** 将来のバージョンで payload のキー名・終了コード規約・発火範囲が変わると本仕様は成立しなくなる。**この破綻は fixture では検知できない**（fixture は仕様どおりの入力を再現するだけで、実環境が同じ入力を送ることを保証しない）。**実環境でしか検知できず、しかも通過側に倒れれば静かに壊れる**（キー名が変われば AC-7-3 の警告が全プロンプトで出るため気づけるが、発火範囲の変化は無症状で進む） |

**「完全な検知を保証する」と読める受け入れ条件を後から足さないこと。** 保証できない主張をハーネスに書くと、通ったことの意味が変わる。

### AC-7. 判定不能な入力は警告して通す

| # | 入力 | 期待 |
|---|---|---|
| 7-1 | stdin が空 | 通す。終了コード **1**（P-1 の「0 / 2 以外」＝非致命エラー）。**stderr に警告。stdout には何も出さない** |
| 7-2 | stdin が JSON として壊れている | 同上 |
| 7-3 | JSON に `prompt` キーが無い | 同上 |

終了コードを 1 に固定するのは、fixture で期待値を1つに定めるためである。P-1 の規約上は 0 / 2 以外なら同じ扱いになる。

**ブロック側に倒さない。** 検査対象が人間の入力経路そのものであり、fail-closed にすると復旧の指示すら送れないデッドロックになる（ADR 0011 決定6）。ただし**黙って通さない**。警告は人間に見える形で出す。

### AC-8. 入力の頑健性

| # | 入力 | 期待 |
|---|---|---|
| 8-1 | `prompt` に改行を含む複数行プロンプト | 冒頭判定は最初の非空白文字を見る。B-1 / B-2 は全体を対象に判定する |
| 8-2 | `prompt` の JSON エスケープ（`\n` / `\"` / `\\`） | 解いた文字列に対して判定する |
| 8-3 | 数千文字のプロンプト | 切り捨てずに判定する |
| 8-4 | `prompt` に引用符・バッククォート・`$(...)` を含む | **シェルに展開しない。** 判定はファイル / 変数経由で行う（`check-review-trail.sh` が `TRAIL_FILE` を使うのと同じ理由） |
| 8-5 | `prompt` 以外のキー（`cwd` / `session_id` 等）に B-1 の語が含まれる | **判定に影響しない。** 取り出すのは `prompt` の値のみ（P-3） |
| 8-6 | `user_input` キーを持ち `prompt` を持たない JSON | AC-7-3 として扱う（通す + 警告）。**`user_input` へフォールバックしない** |

**キー名は `prompt` に固定する**（P-3 の実測。`user_input` ではない）。8-6 は、誤ったキー名で書かれた実装が「たまたま動いてしまう」ことを防ぐための境界値である。フォールバックを許すと、payload 形式が変わったときに**壊れたことに気づけない**。
