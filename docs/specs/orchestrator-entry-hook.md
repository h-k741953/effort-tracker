# 入口ガード hook — オーケストレーターを必須の入口にする

工程をまたぐ依頼が main エージェントへ直接届くことを、`UserPromptSubmit` hook で機械的に止める。根拠は `docs/adr/0011-orchestrator-required-entry.md`。

**このファイルが検知パターンの単一情報源である。** ADR・エージェント定義・スクリプトへ条件を書き写さない（ADR 0004）。

---

## 対象

| 項目 | 値 |
|---|---|
| hook イベント | `UserPromptSubmit` |
| 配線 | `.claude/settings.json` の `hooks` キー |
| 検知本体 | `.claude/hooks/check-prompt-entry.sh` |
| テスト | `.claude/hooks/test-check-prompt-entry.sh`（fixture。`make test-hooks` に組み込み、`make test` から実行される） |

`test-scripts` に相乗りさせないのは、`.github/scripts` が CI スクリプトであるのに対し `.claude/hooks` はハーネス（Claude Code）側の資産であり、対象種別が異なるためである。**別ターゲットにした帰結として、`.github/workflows/ci.yml` に `make test-hooks` を呼ぶジョブの登録が要る。** `make test` に組み込むだけでは CI で一度も実行されない（`test-api` / `test-web` / `test-scripts` はいずれも個別ジョブから呼ばれている）。登録作法は `docs/harness/verification-loop.md` に従う。

配線は `hooks.UserPromptSubmit[].hooks[]` に `type: "command"` / `command` / `timeout` を置く形とする。**`UserPromptSubmit` は `matcher` を非対応**（指定しても黙って無視される）なので書かない。`timeout` の既定は 30 秒。プロジェクトルートの参照には `${CLAUDE_PROJECT_DIR}` を使う。

検知本体は stdin 以外の入力を持たない純粋なフィルタとする。**`.github/scripts/check-review-trail.sh` と同じく、入力を差し替えればローカルで完全に実行でき、fixture で検査できること**を要件とする。

## 前提（P）

> **P-1 / P-2 / P-3 の検証環境**: Claude Code **2.1.214** / **2026-07-18** 実測。リポジトリ外の一時ディレクトリに payload を記録するだけの log-only hook を仕込み、`claude -p` を1回実行して stdin payload を採取した。**これは Claude Code のバージョンに依存する前提であり、本リポジトリが決められる事柄ではない。**

### P-1. `UserPromptSubmit` の終了コード規約 — **確定（実測 + 公式ドキュメント）**

| 終了コード | Claude Code 側の挙動 | 根拠 |
|---|---|---|
| `0` | プロンプトを通す。**stdout の内容はコンテキストへ注入される**（`UserPromptSubmit` の特例） | 公式ドキュメント |
| `2` | **プロンプトをブロックし、main へ渡さない。stderr のテキストが人間に表示される** | 公式ドキュメント |
| `0` / `2` 以外 | ブロックしない非致命エラー。stderr を人間に表示し、処理は続行する | 公式ドキュメント |

**ブロックの表明手段として、終了コード 2 方式を採る**（exit 0 + stdout に `{"decision":"block","reason":...}` を出す JSON 方式は採らない）。理由は3点。

1. **stdout の扱いを1つの不変条件に統一できる。** 本 hook は「stdout に何も出さない」を全経路で守ればよくなる（AC-4-2 / AC-5-2）。JSON 方式を混ぜると、通過時は無出力・ブロック時は JSON という**経路依存の規約**になり、実装の誤りが「無関係な文字列がコンテキストへ注入される」という静かな汚染として出る
2. **理由を人間に返す経路が stderr で明示される。** ADR 0011 決定3 は「判断は AI ではなく人間に返す」と定める。stderr は AI に渡らないことが規約で確定しているが、stdout 上の JSON を Claude 側がどう扱うかは本リポジトリの制御外である
3. **シェルスクリプトで任意文字列を JSON へ埋め込む必要がない。** ブロック理由には一致した検知パターン（＝人間の入力に由来する文字列）が入る（AC-4-6）。JSON 方式はここにエスケープ処理を要求し、AC-8-4 と同種の入力起因の破綻面を増やす

> **JSON 方式は未実測である。** 上記は公式ドキュメントの記述に基づく選択であり、実測で確認したのは終了コード方式の payload 側のみ。**JSON 方式へ切り替えるときは実測をやり直すこと。**

### P-2. 発火範囲 — **確定（実測）**

`UserPromptSubmit` は**人間がプロンプトを送信したときにのみ発火し、`Task` によるサブエージェント起動では発火しない**。Task でサブエージェントを1体起動させるプロンプトを1回実行し、記録された payload が1件のみであることを確認した。

**したがって、オーケストレーター → 工程エージェントの正規経路は本 hook にブロックされない。** 本仕様はこの性質に依存する。

> **payload にエージェント識別子のフィールドは存在しない**（`agent_id` / `agent_type` 等は無い。全キーは P-3 のとおり）。**hook 側でサブエージェント由来かを判定する手段は無く**、正規経路が守られるのは上記の発火範囲そのものによる。限界は AC-6-4 / AC-6-5 に記す。

### P-3. 入力形式 — **確定（実測）**

stdin に JSON が1つ渡る。全キーは次の7つ。

```
cwd / hook_event_name / permission_mode / prompt / prompt_id / session_id / transcript_path
```

- `hook_event_name` の値は `"UserPromptSubmit"`
- **人間の入力した文字列を持つキーは `prompt` である**（`user_input` ではない）。判定は `prompt` の値のみを見る
- 上記以外のキーは本仕様では使用しない

## 受け入れ条件

判定の優先順位は **AC-1（許可） > AC-2（ブロック） > AC-3（通過）** とする。

### AC-1. `[direct]` で始まるプロンプトは常に通す

許可の**唯一の**条件である。`prompt` の**先頭の空白文字を除いた直後**が、半角8文字の `[direct]` に完全一致する場合に許可する。

**先頭の空白文字の集合は、半角スペース / タブ `\t` / 改行 `\n` / 復帰 `\r` の4つとする。** 全角スペースは含まない（AC-1 は「曖昧な一致を許さない」側であり、可視的に区別できない文字を許可条件に入れない）。

> **`\r` を含めるのは意図的な決定である。**（往復2 W-3）実装は当初 `\r` を除いており、`\r\n[direct] 実装して` がブロックされていた（実測）。**仕様側（`\r` を含める）に寄せる。** 理由は、本仕様が AC-8-7 で「Windows からの貼り付けで CRLF は現実に起こる」としてブロック側に `\r` を足した以上、**同じ入力に対して唯一の逃げ道である `[direct]` が効かないのは非対称だから**である。CRLF で貼り付けた人間は、ブロックされたうえに回避手段も封じられ、貼り直す以外に復旧経路を持たない。`\r` は1バイト ASCII であり、他の判定を壊さない（AC-8-7 と同じ理由）。
>
> この4文字は**互いに独立して検査される**（AC-9-11）。SEP に `\r` を足して AC-1 に足さなかった種類の乖離は、群単位の fixture では検知できない。

| # | 入力（`prompt`） | 期待 | 備考 |
|---|---|---|---|
| 1-1 | `[direct] 一覧APIを実装して` | **通す** | ブロック条件に一致しても許可が優先する |
| 1-2 | `\n\n  [direct] 実装して` | **通す** | 先頭の空白・改行は無視する |
| 1-3 | `[direct]実装して` | **通す** | トークン直後の空白は要求しない |
| 1-4 | `[direct]` のみ | **通す** | 本文が無くてもよい |
| 1-5 | `よろしく [direct] 実装して` | **ブロック** | 冒頭でない |
| 1-6 | `実装して [direct]` | **ブロック** | 冒頭でない |
| 1-7 | `[Direct] 実装して` | **ブロック** | 大文字小文字を区別する |
| 1-8 | `[DIRECT] 実装して` | **ブロック** | 同上 |
| 1-9 | `［direct］ 実装して` | **ブロック** | 全角角括弧は一致しない |
| 1-10 | `[ direct ] 実装して` | **ブロック** | 内側の空白は一致しない |
| 1-11 | `(direct) 実装して` | **ブロック** | 括弧の種類が違う |
| 1-12 | `\t[direct] 実装して` | **通す** | 先頭空白 タブ |
| 1-13 | `\r\n[direct] 実装して` | **通す** | 先頭空白 `\r`。**仕様側に寄せた**（往復2 W-3）。実装は当初これをブロックしていた |
| 1-14 | `\r[direct] 実装して` | **通す** | `\r` 単独 |
| 1-15 | `　[direct] 実装して`（全角スペース） | **ブロック** | 全角スペースは先頭空白に含めない |
| 1-16 | ` [direct] 実装して`（半角スペース1個） | **通す** | 先頭空白 半角スペース |

**曖昧な一致を許さない。** 揺れを許すほど「うっかり一致」が増え、例外が意図的な選択でなくなる（ADR 0011 決定2）。

### AC-2. 工程をまたぐ依頼はブロックする

`prompt` が **B-1 または B-2 のいずれか**に一致したらブロックする。

#### B-1. 変更指示（コードベース・docs への変更を伴う依頼）

**一致させるのは指示形のみである。名詞単独では一致させない。**

`実装` `修正` のような名詞は、変更依頼だけでなく質問・説明・調査の対象としても最頻で現れる（「この実装どうなってる?」「この修正の意図を教えて」）。名詞で一致させると AC-3 の「質問・調査・説明は通す」が実挙動と食い違い、かつ質問のたびに `[direct]` を打つ習慣が生じて hook が実質無効化される（ADR 0011 悪い影響の退化リスクが例外ではなく常態になる）。したがって**動作語と指示語尾の連接**で一致させる。

##### B-1-a. 動作語（サ変名詞型）

| 記号 | 語 |
|---|---|
| S | `実装` `修正` `対応` `作成` `追加` `削除` `リファクタ` `リファクタリング` `コミット` `起票` |

一致条件は次のいずれか。**S の直後に連接すること**を要求し、間に助詞・空白・記号を挟むものは一致させない。

- `S` + `し` + 指示語尾 T
- `S` + `せよ`
- `S` + `お願い` / `S` + `おねがい`

##### B-1-b. 動作語（動詞連用形型）

| 記号 | 語 |
|---|---|
| V | `直し` `作っ` `消し` `書い` `書き換え` `置き換え` |

一致条件は `V` + 指示語尾 T。**`ろ` は適用しない**（`直しろ` は非文であり、五段動詞の命令形 `直せ` `作れ` `消せ` は下記の理由で拾わない）。

##### B-1-c. 指示語尾 T

| # | 形 | 一致する例 | 一致しない例 |
|---|---|---|---|
| T-1 | `て` + **終助詞**（0個以上）+ **区切り** | `実装して` / `実装して、` / `直して。` / `実装してね` / `実装してよ` | `実装している` / `実装しても` / `修正してよかった` |
| T-2 | `て` + **依頼接尾**（1個以上）+ **依頼活用尾**（0個または1個）+ **終助詞**（0個以上）+ **区切り** | `実装してください` / `直してもらえる?` / `実装してくれる？` | `実装してくれた` / `実装してもらいました` / `実装してほしいと言われた` |
| T-3 | `といて` | `実装しといて` / `直しといて` | — |
| T-4 | `ろ`（B-1-a のみ） | `実装しろ` | — |

- **終助詞**: `ね` `よ` `な`。**0個以上の繰り返しを許す**（`実装してよね` も一致する）
- **区切り**: 次の**26要素**。群としてではなく、**1要素ずつ**が対象である（AC-9-3）。
  1. 文字列の終端
  2. 改行 `\n` / **復帰 `\r`**（AC-8-7。CRLF 由来）
  3. 空白: 半角スペース / 全角スペース / タブ
  4. 句読点・終止記号: `。` `、` `．` `，` `.` `,` `!` `！` `?` `？`
  5. 閉じ記号・列挙記号: `」` `』` `）` `)` `”` `"` `:` `：` `;` `；`
- **依頼接尾**: `くれ` `ください` `下さい` `ほしい` `欲しい` `おいて` `もらえ` `もらい` `もらっ` `いただけ` `いただき`
  - **1個以上の連接を許す**（`〜しておいてください`）。**連接するときに限り**、2つの接尾の間に `て` を1つ挟んでよい（`〜してもらってください`）
  - **末尾の接尾の直後に `て` を置くことは許さない。** 許すと `実装してくれて、ありがとう` が区切り `、` で一致し、感謝・報告の最頻表現が偽陽性になる（AC-6-2）
- **依頼活用尾**: `る` `たい` `ます` `ますか` `ませんか` `ない` `ないか` `ていい` `てもいい`。**0個または1個**（繰り返さない）

**終助詞を「区切りそのもの」ではなく「区切りの前に置ける文字」として定義するのが要点である。** 終助詞を区切り集合に直接入れると `修正してよかった` `実装してない` `対応してねぇ` が一致してしまう（`よ` `な` `ね` の直後がなお本文である）。**終助詞 + 区切り**の形に限ることで、`実装してよ`（依頼）を拾いつつ `修正してよかった`（回想）を通せる。この形なら終助詞を足しても新たな偽陽性は生じない。

##### T-2 に境界規則を置く理由（往復2 W-1）

**T-2 も T-1 と同じ二段構えにする。** 当初の T-2 は「`て` + 依頼接尾」で閉じており、**接尾の直後が何であっても一致した**。その結果、次がすべてブロックされていた（実測。いずれも依頼ではない）。

```
実装してくれた / 修正してくれたのは誰？ / 対応してもらえなかった / 実装してもらいました
対応してもらった件について / 実装してほしいと言われた / なぜ対応しておいてくれなかったのか
```

**これは AC-6-2 が「逃げ道で吸収せず検知条件の側を直す」と定めた種類の偽陽性である。** レビュー中心の運用では「実装してもらった件」「直してくれたのは誰か」は最頻の言い回しであり、`修正してよかった` を通すために T-1 で払った労力と非対称になる。

境界規則は次の形をとる。**依頼接尾の直後に、依頼として自然な活用尾（依頼活用尾）を0個または1個だけ許し、その後は T-1 と同じ「終助詞\* + 区切り」で閉じる。**

| 語尾の型 | 例 | 扱い | 根拠 |
|---|---|---|---|
| 接尾 + 区切り | `直してくれ` / `修正して下さい` / `作成しておいて` | **拾う** | 命令形・終止形そのもの |
| 接尾 + 依頼活用尾 + 区切り | `実装してくれる？` / `直してもらいたい` / `直していただけますか` | **拾う** | 依頼の活用形 |
| **過去形** | `実装してくれた` / `対応してもらった件` / `実装してもらいました` | **通す** | `た` `ました` は依頼活用尾に無く、区切りでもない |
| **否定過去** | `対応してもらえなかった` | **通す** | `なかっ` は `ない` と一致しない |
| **引用・伝聞** | `実装してほしいと言われた` | **通す** | `と` は区切りに無い |
| **連体修飾** | `対応してもらった件について` | **通す** | 同上（`た` の直後が本文） |
| **過去 + 疑問** | `修正してくれたのは誰？` | **通す** | `？` は区切りだが、その手前が `たのは誰` であり接尾の直後ではない |
| **複合の報告** | `なぜ対応しておいてくれなかったのか` | **通す** | `おいて` + `くれ` まで連接するが、直後が `な`（`ない` は不一致） |

**「過去形を除外する」規則としては書かない。** 除外条件は後置きで成立させられるため（B-1-c 末尾の方針、ADR 0011 却下案）。書くのは**通す側の列挙ではなく、拾う側の列挙**である。`た` は依頼活用尾の列挙に入っていないから拾われない、というだけであり、除外面は増えない。

`ない` `ないか` を依頼活用尾に含めるのは `直してくれない?` `直してもらえないか` が依頼だからである。**代償として `彼が実装してくれない。`（不満の報告）は偽陽性になる。** 依頼と不満は同綴で機械的に区別できず、ADR 0011 決定5 の「迷ったらブロック側」に従う。これは最頻のやり取りではないため AC-6-2 に触れない。

閉じ記号を区切りに含めた結果、`「実装して」と言われた`（引用・報告）は偽陽性としてブロックされる。**これは承知のうえで採る。** 引用と依頼を機械的に区別できず、ADR 0011 決定5 の「迷ったらブロック側」に従う。質問・調査のような最頻のやり取りではないため、AC-6-2 が禁じる「常時発火する偽陽性」には当たらない。

区切りと依頼接尾を列挙で閉じるのは、`実装している` `実装しても`（進行・仮定であって依頼ではない）を通すためである。**列挙で閉じる以上、列挙に無い文字を後置きすれば一致は外れる。** 実際、初期の列挙は終助詞と閉じ記号を欠いており、`実装してね` `PRを作ってね` `実装して」` `この機能実装して:` が通っていた（実測により反証。往復1 C-1）。本節はこれらを区切り側に加えて塞いだが、**「後置きでは逃げられない」ことを保証はしない。**

**T-2 に境界規則を置いたことで、この非対称はさらに小さくなった。** 以前は「T-2 が依頼表現側を独立に、後続を問わず拾う」ため、後置きだけで逃げるには依頼性を薄める必要があった。**その退路は塞がれていない。** T-2 も区切りで閉じる以上、`実装してください〜` のような後置きは T-1 と同様に外れる。**T-2 の偽陽性（W-1）を下げた代償として、T-2 側の後置きすり抜けを引き受けた。** これは AC-6-10 が記録する限界と同じ面であり、**T-1 / T-2 のどちらも列挙の外側は捕捉しない**。取りこぼしは AC-6-1 / AC-6-10 の偽陰性として扱う。

**穴を塞ぐ方向は「区切りを増やす」側に限る。** 「質問形の語尾を除外条件にする」ような**後置きで除外が成立する**規則は採らない（ADR 0011 却下案。Issue #25 往復4 C-1 と同型の穴を新設する）。区切りの追加は検知を強める側であり、除外面を増やさない。

##### 補集合方式を検討し、棄却した（往復2 W-2）

列挙方式には後置きすり抜けが**類型として開いたまま**残る。実測で次がすべて通る。

```
実装して〜 / 実装して… / 実装して🙏 / 実装してw / 実装して笑 / 実装して- / 実装して】
```

`実装して〜` `実装して…` は口語の依頼として自然であり、往復1 で Critical とされた `実装して」` より頻度が低いとは言えない。**列挙方式を選び続ける以上、その根拠を残す。**

**検討した代替**: 区切りを列挙ではなく**補集合**で定義する（`て` + 終助詞\* + **ひらがな以外**）。reviewer の実測では、AC-3 の通す側8件を1件も壊さずに上記7件をすべて捕捉できた。**検知性能の点では列挙方式より優れている。**

**それでも棄却する。** 理由は検知性能ではなく実装基盤との衝突である。

| 論点 | 内容 |
|---|---|
| 文字クラスを要する | ひらがなの補集合は `[ぁ-ゟ]` のような**多バイト文字を含む文字クラス**でしか書けない。本スクリプトは「多バイト文字を character class に入れない」を方針としている（Makefile に記録された mawk の区間指定事故と同型のリスク回避） |
| `LC_ALL=C` と正面から衝突 | 判定用 grep は `LC_ALL=C` に固定されている（UTF-8 ロケール下で `\b` が多バイト文字の前後で不安定になる実測による）。`LC_ALL=C` では `[ぁ-ゟ]` は**文字範囲ではなくバイト範囲**として解釈され、意図した集合にならない |
| 外すと往復1 で塞いだ罠に戻る | `LC_ALL=C` を外せば文字クラスは動きうるが、**多バイト境界に起因する環境依存の破綻**（mawk 型）を再び背負う。それは往復1 で塞いだ種類の罠と同型であり、**検知1件の改善と引き換えに、検知そのものが環境で壊れる面を増やす** |

**代償は明記する。** 口語の後置き（`〜` `…` 絵文字 `w` `笑` 記号類）は**偽陰性へ回る**。これは AC-6-9 の「列挙漏れ」とは性質が違い、**塞げないものではなく、基盤上の理由で塞がないと選んだもの**である（ADR 0011 悪い影響の「片方を締めれば他方が緩む」と同じ目盛り）。限界は AC-6-10 に記す。

**この棄却は恒久ではない。** 判定基盤が変わる（`LC_ALL=C` を外せる根拠が実測で得られる、あるいは grep 以外の判定系に移る）なら、補集合方式は再検討に値する。**そのときは本節の3行の論点が消えているかを確認すること。**

##### B-1-d. 拾わない形（意図的な偽陰性）

| 形 | 例 | 理由 |
|---|---|---|
| 名詞単独 | `この実装どうなってる?` `テストの修正箇所はどこ?` | 上記のとおり。**これが本節の主目的である** |
| 助詞を挟む依頼 | `実装をお願いします` `修正のほうお願い` | S と指示語尾の間に助詞が入る。連接規則を緩めると名詞形の質問へ再び波及する。**代償として偽陰性へ回ることを承知で採る** |
| 五段動詞の命令形 | `直せ` `作れ` `消せ` | 可能形（`直せますか?` `作れる?`）と同綴で区別できない。質問を誤爆する |
| 進行・仮定・完了 | `実装している` `実装してある` `実装しても` | 依頼ではない。T-1 / T-2 の列挙から外れる |

##### B-1-e. 英語

`implement` のみを、**大文字小文字を区別せず語境界で**一致させる。

- **`implement` は残す。** 名詞形は `implementation` であり別語なので、語境界一致すれば動詞用法だけを拾える。名詞形の混入が起きない
- **`fix` は語彙から外す。** 名詞と動詞が同綴（`the fix` / `a quick fix`）で、語境界一致では区別できない。残すと `What is the fix?` のような質問がブロックされ、日本語側で是正したのと同じ非対称を英語側に残すことになる
- **`the` / `a` / `this` などの限定詞を前置きの除外条件にする案は採らない。** 文字列の付加によって除外が成立する構造であり、Issue #25 の往復4 C-1 で塞いだすり抜けと同型になる
- 代償として `fix this bug` は偽陰性へ回る。本リポジトリの運用言語は日本語（ADR 0010 §G）であり、英語の網羅より判定規則の一貫性を優先する

### AC-5. 通過時の出力

| 6-6 | **指示形に絞ったことで、助詞を挟む依頼が偽陰性へ回る。**「実装をお願いします」「修正のほうお願い」は通る（3-21）。これは 6-1 と違い**設計上の選択**であり、名詞形の偽陽性（6-2）を下げるために意図的に引き受けた代償である（ADR 0011 悪い影響）。**連接規則を緩めて拾いにいかないこと。** 緩めれば名詞形の質問へ再び波及する |
| 6-7 | **英語は `implement` のみを拾い、`fix` は拾わない**（B-1-e）。`fix this bug` は通る（3-22）。名詞と動詞が同綴で機械的に区別できないための選択であり、日本語運用（ADR 0010 §G）を前提に許容している |
| 6-8 | **P-1 / P-2 / P-3 は Claude Code 2.1.214（2026-07-18 実測）に対する前提であり、バージョン依存である。** 将来のバージョンで payload のキー名・終了コード規約・発火範囲が変わると本仕様は成立しなくなる。**この破綻は fixture では検知できない**（fixture は仕様どおりの入力を再現するだけで、実環境が同じ入力を送ることを保証しない）。**実環境でしか検知できず、しかも通過側に倒れれば静かに壊れる**（キー名が変われば AC-7-3 の警告が全プロンプトで出るため気づけるが、発火範囲の変化は無症状で進む） |
| 6-9 | **区切りの列挙には列挙漏れが残りうる**（B-1-c）。初期の列挙は終助詞・閉じ記号を欠き、`実装してね` `実装して」` が通っていた（往復1 C-1、実測）。塞いだのは実測で見つかった範囲であって、**列挙外の後置き文字が今後見つからない保証はない**。塞ぐ方向は区切りの追加（検知の強化）に限り、除外条件の追加では塞がない |
| 6-10 | **口語の後置きは偽陰性へ回る**（B-1-c「補集合方式を検討し、棄却した」）。`実装して〜` `実装して…` `実装して🙏` `実装してw` `実装して笑` `実装して-` `実装して】` は通る（実測）。補集合方式（`て` + 終助詞\* + ひらがな以外）ならこれらを捕捉でき、AC-3 の通す側も壊さないことが実測で確認されているが、**多バイト文字の character class と `LC_ALL=C` に衝突するため採らない**。6-9 が「塞げていない列挙漏れ」であるのに対し、**これは基盤上の理由で塞がないと選んだもの**である。判定基盤が変われば再検討する |
| 6-11 | **T-2 の依頼活用尾も列挙であり、長い丁寧形は取りこぼす**（B-1-c）。`直していただけますでしょうか` `実装してくださいませんでしょうか` は列挙外のため通る。6-9 と同種の列挙漏れであり、塞ぐなら依頼活用尾の追加（検知の強化）で行う |
| 6-12 | **T-2 の `ない` `ないか` は依頼と不満で同綴である**（B-1-c）。`直してくれない?`（依頼）を拾うために `彼が実装してくれない。`（不満の報告）が偽陽性になる。ADR 0011 決定5 の「迷ったらブロック側」に従った選択であり、最頻のやり取りではないため AC-6-2 には当たらない |

**「完全な検知を保証する」と読める受け入れ条件を後から足さないこと。** 保証できない主張をハーネスに書くと、通ったことの意味が変わる。

### AC-7. 判定不能な入力は警告して通す

| # | 入力 | 期待 |
|---|---|---|
| 7-1 | stdin が空 | 通す。終了コード **1**（P-1 の「0 / 2 以外」＝非致命エラー）。**stderr に警告。stdout には何も出さない** |
| 7-2 | stdin が JSON として壊れている | 同上 |
| 7-3 | JSON に `prompt` キーが無い | 同上 |

終了コードを 1 に固定するのは、fixture で期待値を1つに定めるためである。P-1 の規約上は 0 / 2 以外なら同じ扱いになる。

**ブロック側に倒さない。** 検査対象が人間の入力経路そのものであり、fail-closed にすると復旧の指示すら送れないデッドロックになる（ADR 0011 決定6）。ただし**黙って通さない**。警告は人間に見える形で出す。

### AC-8. 入力の頑健性

| # | 入力 | 期待 |
|---|---|---|
| 8-1 | `prompt` に改行を含む複数行プロンプト | 冒頭判定は最初の非空白文字を見る。B-1 / B-2 は全体を対象に判定する |
| 8-2 | `prompt` の JSON エスケープ（`\n` / `\"` / `\\`） | 解いた文字列に対して判定する |
| 8-3 | 数千文字のプロンプト | 切り捨てずに判定する |
| 8-4 | `prompt` に引用符・バッククォート・`$(...)` を含む | **シェルに展開しない。** 判定はファイル / 変数経由で行う（`check-review-trail.sh` が `TRAIL_FILE` を使うのと同じ理由） |
| 8-5 | `prompt` 以外のキー（`cwd` / `session_id` 等）に B-1 の語が含まれる | **判定に影響しない。** 取り出すのは `prompt` の値のみ（P-3） |
| 8-6 | `user_input` キーを持ち `prompt` を持たない JSON | AC-7-3 として扱う（通す + 警告）。**`user_input` へフォールバックしない** |
| 8-7 | `prompt` の改行が CRLF（`実装して\r\nよろしく`） | **ブロックする。** `\r` を T-1 の区切りとして扱う（B-1-c）。行末一致を `\n` だけに頼らない |
| 8-8 | CRLF で貼り付けた `[direct]`（`\r\n[direct] 実装して`） | **通す。** `\r` を AC-1 の先頭空白として扱う（AC-1、1-13）。**8-7 と対で扱う**。ブロック側にだけ `\r` を足すと、CRLF 入力に対して唯一の逃げ道が塞がる |

8-7 は実測で**通っていた**穴である（往復1 W-3）。`$` は `\n` の直前には一致するが、CRLF では `て` と行末の間に `\r` が入るため T-1 が成立しなかった。Windows からの貼り付けで現実に起こる。`\r` は1バイト ASCII であり、多バイト文字の途中に現れないため、区切り集合に加えても他の判定を壊さない。**`\r` を除去してから判定する実装でも、区切りに加える実装でも、8-7 と 2-29 を満たせばよい。**

**キー名は `prompt` に固定する**（P-3 の実測。`user_input` ではない）。8-6 は、誤ったキー名で書かれた実装が「たまたま動いてしまう」ことを防ぐための境界値である。フォールバックを許すと、payload 形式が変わったときに**壊れたことに気づけない**。

### AC-9. 語彙表の各行に fixture を対応させる

**本仕様が列挙した語彙は単一情報源である。実装との一致がテストで固定されていなければ、列挙は意味を持たない。**

| # | 対象 | 要求 |
|---|---|---|
| 9-1 | B-1-a の S（`実装` 〜 `起票`）の**各語** | ブロックされる fixture を**最低1件**持つ |
| 9-2 | B-1-b の V（`直し` 〜 `置き換え`）の**各語** | 同上 |
| 9-3 | B-1-c の区切りの**各要素**（**26要素**: 終端 / `\n` / `\r` / 半角スペース / 全角スペース / タブ / `。` `、` `．` `，` `.` `,` `!` `！` `?` `？` / `」` `』` `）` `)` `”` `"` `:` `：` `;` `；`） | 同上 |
| 9-4 | B-1-c の終助詞の**各語**（`ね` `よ` `な`） | 同上 |
| 9-5 | B-1-c の依頼接尾の**各語**（`くれ` 〜 `いただき`。11語） | 同上 |
| 9-6 | B-2 の各語（`やっ` `進め` `片付け` `着手` `お願い` `おねがい`） | 同上 |
| 9-7 | B-1-a の接続 `せよ` / `お願い` / `おねがい`、T-3 `といて`、T-4 `ろ` | 同上 |
| 9-8 | B-1-e `implement` の**大文字小文字非区別** | `IMPLEMENT` / `Implement` を含む fixture を持つ |
| 9-9 | T-4 の `ろ` が **B-1-b に適用されないこと** | `直しろ` が**通る** fixture を持つ |
| 9-10 | B-1-e が語境界で一致すること | `implementation`（3-20）が通る fixture を持つ |
| 9-11 | AC-1 の先頭空白の**各要素**（半角スペース / タブ / `\n` / `\r`） | **通る** fixture を最低1件ずつ持つ（1-16 / 1-12 / 1-2 / 1-13・1-14）。加えて全角スペースが**含まれないこと**の負例（1-15）を持つ |
| 9-12 | B-1-c の依頼活用尾の**各語**（`る` `たい` `ます` `ますか` `ませんか` `ない` `ないか` `ていい` `てもいい`。9語） | ブロックされる fixture を最低1件持つ |
| 9-13 | B-1-c の T-2 の**依頼接尾の連接**と、**連接時の `て` 連結** | それぞれブロックされる fixture を持つ（2-35 / 2-36） |
| 9-14 | **T-2 の境界規則そのもの**（接尾の直後を区切りで閉じること） | **通る** fixture を持つ（3-26〜3-33）。**この負例が無いと、境界規則を実装から落としても Green のままになる** |

**判定基準は「語彙表の1行を削ると、fixture が最低1件 Red になる」ことである。** 実装から語を黙って落としても Green のままなら、その行はテストに守られていない。往復1 のレビューはミューテーション13件のうち11件が生存することを確認しており（`implement` の大小非区別、B-1-b への `ろ` 非適用、SEP の `。` と全角スペース、依頼接尾 `下さい` `ほしい`、S の `削除` `コミット`、V の `消し` `書き換え` `置き換え`、B-2 の `進め` `片付け`）、**この受け入れ条件はその実測に対する応答である。**

**粒度は「各要素」に揃える。群単位にしない**（往復2 W-4）。9-3 は当初「句読点群 / 閉じ記号群」と群粒度で書かれており、他（9-1 / 9-2 / 9-4 / 9-5 / 9-6）の「各語」と不整合だった。**その結果、区切りの列挙から1要素を消しても fixture は111件 Green のまま**であり、実測では16要素（`．` `，` `！` `？` `』` `）` `”` `：` `；` `.` `,` `!` `?` `)` `"` `;`）が生存した。これは**前文の判定基準（1行削れば最低1件 Red）を、その基準を書いた節自身が満たしていない**状態である。群でよい理由は無い（要素ごとの fixture は1行で書け、コストは小さい）ため、**群粒度の側を捨てて各要素へ寄せる。**

9-9 / 9-10 / 9-14 のような**負例**を要求するのは、正例だけでは「一致しないこと」が固定されないためである。B-1-d の意図的な偽陰性（AC-3 の 3-17 / 3-21 / 3-22）も同じ理由で fixture を持つ。
