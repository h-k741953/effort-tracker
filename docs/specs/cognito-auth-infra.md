## なぜ仕様を2ファイルに分けるか（記録）

本 Issue の対象は「Cognito のインフラ」と「BFF のトークン終端」の2面にまたがる。**1ファイルにせず2ファイルに分けたのは、次の3点による**（分割そのものは仕様工程の判断であり、人間の決定ではない。覆すのは自由）。

1. **検証ハーネスが別系統である。** 本ファイルの受け入れ条件は `infra/terraform/tests/*.tftest.hcl`（`make test-tf`）で、`bff-auth-termination.md` の受け入れ条件は `apps/web` の vitest（`make test-web`）で検査される。**Red を踏む単位も、tester 工程が触るファイルも重ならない**（`infra-terraform.md` AC-9-12 が `.tftest.hcl` の Red と Go テストの Red を別々に踏ませているのと同型）
2. **未確定点の分布が偏っていた（分割時点＝2026-09-01 の Q 提示時点の記録）。** 当時、BFF 側は着手条件そのものが未決であった（同日の Q-A〜Q-E。出所は `bff-auth-termination.md` の Q 節で、**同節が「決定済み（2026-09-01 / 人間）」として当時の選択肢と採らなかった案を保存している**）。1ファイルにすると、**決着していた Cognito 側の条文まで未決の隣に置かれ、着手可否が読み取りにくくなる**という判断だった。**現況は同日中に全 Q が人間の決定で解消しており、着手可否の現況の持ち主は `bff-auth-termination.md` の Q 節と P-5 である**（本項は分割理由の記録であって、現況の記述ではない）
3. **参照の分界が明瞭になる。** 本ファイルは `infra-terraform.md` の隣接仕様として読まれ、BFF 側は `login-ui.md` / `domain-api-http-contract.md` の隣接仕様として読まれる。**指し先が違う条文を1つの見出しに混ぜない**

### AC-3. MFA は TOTP。SMS の経路を持たない

| # | 条件 | 期待 |
|---|---|---|
| 3-1 | TOTP | **TOTP（認証アプリ）による多要素認証を有効にする**（ADR 0016 決定 2・`login-ui.md` AC-2-2）。**MFA を無効（`OFF` 相当）のままにしない** |
| 3-2 | SMS を持ち込まない | **SMS による MFA の設定を持たない。** SMS の送信設定（送信元・SNS へ委譲する IAM ロール等）を構成に作らない。**ADR 0016 が「1通ごとの従量課金で $5 予算を溶かす」として退けた経路を、構成に残さない**（`docs/rules/cost-guardrails.md` と同 ADR 代替案表）。**理由の無い設定を「将来のために」空で残さない**（`infra-terraform.md` D-3 と同型） |
| 3-3 | MFA の適用範囲 | **MFA を任意にする**（Q-2 = (b)。2026-09-01 に人間が決定。利用者が選ぶ。TOTP が有効であることは構成で示す）。すなわち **MFA の設定は「無効」でも「必須」でもなく「任意」に相当する値**であること。**必須化しない** —— 公開デモで認証アプリの導入を全員に強いない。**帰結として、MFA を有効にしていない利用者が存在しうる**（限界は AC-11-10）。**検査は AC-9-b** |

### AC-4. Google OIDC 連携とクライアントシークレットの扱い

| # | 条件 | 期待 |
|---|---|---|
| 4-1 | ID プロバイダ | **Google をソーシャル ID プロバイダとして User Pool に登録する**（ADR 0016 決定 3）。**Google の Terraform provider を導入しない**（AC-1-3） |
| 4-2 | シークレットの入力経路 | クライアント ID とクライアントシークレットは **Terraform の変数で受け取り**、**値は `terraform.tfvars`（`.gitignore` 済み）から与える**（ADR 0016 トレードオフ・P-4）。**構成にも `docs/` にも実値を書かない**（`infra-terraform.md` AC-2-5 と同型） |
| 4-3 | 変数の宣言 | シークレットの変数は **`sensitive = true`** とし、**既定値を持たせない**（既定値を持たせると、与え忘れが「空のシークレットで apply される」形で通る）。**帰結として既存の `.tftest.hcl` へダミー値の追記が要る**（AC-1-5） |

### AC-9. `terraform test` が assert すること

**検査は `.tftest.hcl` に書き、`mock_provider` と `command = plan` を用いて AWS 認証情報なしで完走する**（P-6・P-9・`infra-terraform.md` AC-10-1 / AC-10-2）。**各 `run` を構成より先に書き、落ちることを確認してから実装へ入る**（同 AC-10-3・`docs/rules/development-process.md` TDD）。

**例外は AC-9-g / AC-9-r の「宣言側」だけである。** 変数が **`sensitive` として宣言されていること・既定値を持たないこと**（AC-4-3・AC-8-7）は、**この形では観測できない** —— `mock_provider` と `command = plan` による assert が参照できるのは **plan に現れる値**であって**変数の宣言そのもの**ではない。`sensitive` は宣言の属性であって値に現れず、既定値の不在は「値が無い」というエラーとして **`run` 全体を落とす**ため `expect_failures` でも捕捉できず、`plan_options.target` で対象を絞っても回避できない。**したがって、この2条の宣言側の検査だけを静的チェッカへ移す**（Q-G = (a)。2026-09-02 に人間が決定。受け入れ条件は **AC-12**、限界は **AC-11-13 / AC-11-14**）。**移すのは検査の形だけであり、要求（AC-4-3・AC-8-7）は一切緩めない。**

**例外をこの2条の外へ広げない。** 他の条を静的チェッカで検査したくなったら、**足さずに停止して人間へ上げる**（AC-1-7・`infra-terraform.md` D-24「構成の検査は `terraform test` の1系統に保つ。補う判断は人間の承認事項」）。**assert できない条は、引き続き限界として残す**（AC-11-1）。

### AC-12. AC-9-g / AC-9-r の宣言側 —— 静的チェッカ（Q-G = (a)）
