# 稼働実績の入力・編集 — UI/画面 仕様

MVP ユースケース1「稼働実績の入力・編集」の **UI/画面** 受け入れ条件。業務仕様は `docs/specs/daily-record-entry.md` が持ち、本仕様はそれと矛盾しない範囲で「入力・編集の画面が満たすべき形」だけを定める。画面骨格・状態×ロールの操作可否・read-only の共通挙動は `docs/specs/work-month-screen-ui.md`（以下「共通仕様」）が持つ。

業務ルール（時刻の粒度と値域・前後関係・休憩の位置・未来日・丸め・状態遷移）は、この仕様へ **書き写さない** ものとする。正解は `docs/specs/daily-record-entry.md` と `docs/domain/ubiquitous-language.md`。本仕様は参照のみ（ADR 0004）。

- **決定者**: 人間（プロジェクトオーナー）。UI 固有の論点（一覧の表示形態・入力ウィジェット）は人間が決定済み（共通仕様「確定事項」Q4・Q5。Q5 は 2026-10-09 の人間決定で時刻の選択へ改定）。祝日の表示は人間決定（ADR 0021 決定4）。保存前の稼働時間の表示は人間決定（2026-10-10。AC-3-6）
- **日付**: 2026-07-23（2026-10-10 改定: 時刻の選択による入力・祝日の表示・保存前の稼働時間の表示。2026-10-13 改定: 同日の人間決定により、AI 起案の箇所をすべて人間の承認済みへ改めた）
- **AI 起案の扱い**: 条文中に「AI 起案（2026-10-13 に人間が承認）」と書いた箇所は、AI が起案し、2026-10-13 に人間が一括で承認したものである。承認済みであり、その箇所をテストの期待値にしてよい

---

## スコープ

- **対象**: `Draft` 状態の勤務月画面における、日次実績の**一覧表示（カレンダー）・入力・編集・削除**の UI と、その状態（空／入力中／バリデーションエラー／締め後 read-only）。カレンダーの祝日の表示と、そのための祝日データの同梱（ADR 0021 決定4 が UI 仕様へ委ねた置き場所・更新の手順・対象の年）
- **非対象**: 締め・承認・差戻しの UI（`monthly-closing-ui.md` / `approval-ui.md`）、画面骨格・状態バッジ・操作可否マトリクス（共通仕様）、勤務月一覧・ログイン（`work-month-listing-ui.md` / `login-ui.md`）

### AC-1. 日次実績一覧（カレンダー）の表示

| # | 条件 | 期待 |
|---|---|---|
| 1-1 | 入力済みの日 | 対象日と、その日の稼働時間（`daily-record-entry.md` AC-2-1-a で算出した値）を一覧に表示する |
| 1-2 | 各日の表示値と総稼働時間 | **整合する**（画面上で各日を足した結果が総稼働時間と一致して見える）。丸め規則により各日は15分単位で切り捨てた寄与として扱われる（`daily-record-entry.md` AC-6／ユビキタス言語「丸め規則」） |
| 1-3 | レコードのない日 | 「稼働なし」として扱い、合計に寄与しない（明示ゼロ表示を強制しない。`daily-record-entry.md` D-5） |
| 1-4 | 一覧の表示形態 | **カレンダー**表示（人間決定 Q4）。日を選んで入力・編集する。入力済みの日と稼働時間が識別でき、総稼働時間と整合すること |
| 1-5 | 曜日の見出し | カレンダーは7つの曜日の見出しを持ち、土曜と日曜を見出しの文字で区別できる（色だけに頼らない。`design-system.md` 2-6）。週の始まりは**月曜**とする —— AI 起案（2026-10-13 に人間が承認。ハンドオフに倣った） |
| 1-6 | 入力済みの日の時刻の範囲 | 稼働時間に加えて、その日の開始時刻と終了時刻の範囲（例: `9:00〜18:00`）を示す —— AI 起案（2026-10-13 に人間が承認。ハンドオフに倣った）。休憩の時刻はカレンダーに示さない |
| 1-7 | 祝日 | AC-9 による |

### AC-3. 入力フォーム（時刻の選択）

入力の形は 2026-10-09 の人間決定（共通仕様「確定事項」Q5 の改定）による。時刻の粒度・値域・前後関係・休憩の回数は `daily-record-entry.md` D-10〜D-12・AC-3 が持ち、本 AC は書き写さずに参照する。

| # | 条件 | 期待 |
|---|---|---|
| 3-1 | 入力項目 | **対象日・開始時刻・終了時刻・休憩の有無**と、休憩ありのときに限り **休憩開始時刻・休憩終了時刻** を持つ（`daily-record-entry.md` AC-2-1）。稼働時間そのものを入力する欄は **設けない** ものとする（同 D-2） |
| 3-1-a | 休憩の欄の数 | 休憩開始時刻・休憩終了時刻の組は**1組だけ**とし、2つ目の休憩を加える操作を設けない（`daily-record-entry.md` D-12・AC-3-10） |
| 3-2 | 時刻の指定 | 4つの時刻はそれぞれ **時の選択と分の選択の2つ** で指定する（人間決定 Q5 の改定）。時・分を自由に打ち込む欄（数値入力・テキスト入力）を設けない。部品は `SelectField`（`design-system.md` 6-12） |
| 3-2-a | 選択肢 | 時の選択肢の集合は `daily-record-entry.md` D-10 の時の値域と、分の選択肢の集合は同 D-10 の分の4値と、それぞれ **過不足なく一致** させる（時 24 を含めない。同 D-11）。選択肢は値の昇順に並べる |
| 3-2-b | 未選択 | 時・分の選択はそれぞれ「未選択」の状態を持てる。未選択のまま保存したときは AC-4-1 で弾く（`daily-record-entry.md` AC-3-3・3-4） |
| 3-2-c | アクセシブル名 | 時・分の選択（休憩ありで最大8つ）は、どの時刻の時か分かを区別できる互いに異なるアクセシブル名を持つ（例: `開始（時）`・`開始（分）`）。名の文言は AI 起案（2026-10-13 に人間が承認） |
| 3-3 | 送信 | 妥当な入力は該当日の実績として反映する。既にレコードのある日への送信は編集として扱う（AC-5） |
| 3-4 | 休憩の有無の切替 | 休憩の有無を利用者が選ぶ。休憩なしのときは休憩開始時刻・休憩終了時刻の選択を **表示せず送信にも含めない** ものとする（`daily-record-entry.md` AC-3-4-a）。休憩ありのときは両方の選択を表示する |
| 3-5 | 新規入力の初期値 | 本仕様で固定しない（ハンドオフの初期値は参考）。初期値が業務ルールを満たさない組み合わせになっても、保存時に AC-4 で弾かれる |
| 3-6 | 保存前の稼働時間の表示 | 入力中に、選んでいる時刻から算出した稼働時間を **保存の前に表示する** ものとする（人間決定 2026-10-10）。算出は `daily-record-entry.md` AC-2-1-a の式による。表示の位置は画面固有の合成であり、本仕様で固定しない（8-4） |
| 3-6-a | 表示する時機 | 開始時刻・終了時刻の時と分がすべて選ばれ、休憩ありのときは休憩開始時刻・休憩終了時刻の時と分もすべて選ばれたときに値を示し、選択を変えるたびに示す値を改める。未選択が1つでも残るときは値を示さない —— AI 起案（2026-10-13 に人間が承認） |
| 3-6-b | 弾かれる入力のとき | 選んでいる時刻の組が `daily-record-entry.md` AC-3 の 3-B で「弾く」行に当たるとき（終了が開始より後でない、休憩の前後・位置、稼働時間が 0 になる）は、算出値を示さない（0 や負の値を示さない） —— AI 起案（2026-10-13 に人間が承認） |
| 3-6-c | 保存される値 | 保存される稼働時間は **ドメインの算出が正** とする（人間決定 2026-10-10）。画面が算出した値は表示のためだけに使い、送信に含めない（稼働時間を入力として受け取らない。`daily-record-entry.md` D-2・AC-2-1）。保存の後は、ドメイン API が返した値を一覧（1-1）と総稼働時間に示し、保存前に示していた値で置き換えない |
| 3-6-d | 算出の写しの突き合わせ（検証手段） | 画面の算出はドメインの算出（`daily-record-entry.md` AC-2-1-a）の写しになるため、両側を **同じ期待値の表で検査する** ものとする（人間決定 2026-10-10）。期待値の表の持ち主は `daily-record-entry.md` AC-3 の 3-B と 3-C の表であり、そのうち入力の列に時刻の組（開始〜終了／休憩）を示す行を使う。ドメインの算出のテスト（`services/`）と画面の算出のテスト（`apps/web/`）は、どちらも行をテストコードへ手で写さず、この表から入力と期待を読む。表の行を足したら両側の検査に同時に現れ、片方だけに行を足すことはできない形にする。期待は次のとおり読む: 「許可」の行では、両側の算出値がその行の稼働時間と一致する。「弾く」の行では、ドメインが弾き、画面は値を示さない（3-6-b。3-6-b は 2026-10-13 に人間が承認したため、画面側の「弾く」行の期待もテストの期待値にする）。表の解析の形（どのコードが表を読むか）はテスト工程が決める |

### AC-4. バリデーションエラー表示

弾く条件そのものは `daily-record-entry.md`（AC-2〜AC-4）が持つ。本 AC は**画面がどう弾き、どう伝えるか**を定める。エラー時の共通挙動（入力値を失わせない等）は共通仕様 AC-6。

| # | 入力 | 期待 |
|---|---|---|
| 4-1 | 時刻の時または分が未選択（`daily-record-entry.md` AC-3-3・3-4） | 送信を弾き、未選択である理由を提示する |
| 4-1-a | 時刻の粒度・値域の外（同 AC-3-1-a・3-2-a・3-2-b） | 選択肢に含めない（AC-3-2-a）ことで画面からは指定できない。ドメイン API がこの理由で弾いた場合は共通仕様 AC-6-1 の形で理由を提示する |
| 4-2 | 対象日が未来日（JST 当日より後） | 未来日の実績を保存させず、未来日不可の理由を提示する（`daily-record-entry.md` AC-4）。送信を弾く形でも、未来日を選んだ時点で時刻の選択と保存を出さずに理由だけを示す形でもよい |
| 4-3 | 対象日が当該勤務月の年月に属さない | 送信を弾き、理由を提示する（`daily-record-entry.md` AC-2-4） |
| 4-4 | エラー時 | 利用者が選んだ対象日・4つの時刻（時・分）・休憩の有無を保持し、再入力を強いない（共通仕様 AC-6-2） |
| 4-5 | 終了時刻が開始時刻より後でない（同 AC-3-5-a・3-5-b・3-5-c・3-5-e） | 送信を弾き、前後関係の理由を提示する。終了が開始より前の入力を翌日の勤務として扱わない（同 D-11） |
| 4-6 | 休憩終了時刻が休憩開始時刻より後でない（同 AC-3-6-a・3-6-b） | 送信を弾き、休憩の前後関係の理由を提示する |
| 4-7 | 休憩が開始時刻〜終了時刻の範囲に収まらない（同 AC-3-8・3-8-a・3-8-b） | 送信を弾き、休憩の位置の理由を提示する |
| 4-8 | 算出した稼働時間が 0時間0分 になる（同 AC-3-9・3-9-a） | 送信を弾き、稼働時間が 0 になる理由を提示する |
| 4-9 | 理由の区別 | 4-1・4-5・4-6・4-7・4-8 の理由は **互いに異なる文** で提示する —— AI 起案（2026-10-13 に人間が承認）。文言そのものは本仕様で固定しない |
| 4-10 | 弾いた送信の帰結 | その日の既存の表示値（レコードの有無・稼働時間）と総稼働時間を変えない |

### AC-8. 限界 — 本仕様が担保しないこと

| # | 内容 |
|---|---|
| 8-1 | 締め・承認・差戻しの UI は対象外（`monthly-closing-ui.md` / `approval-ui.md`） |
| 8-2 | 一覧の表示形態（カレンダー）・時刻の入力ウィジェット（時・分の選択）は人間決定済み（共通仕様「確定事項」Q4・Q5） |
| 8-3 | 勤務月一覧・ログイン・認証は別 spec（`work-month-listing-ui.md` / `login-ui.md`）が持つ |
| 8-4 | デザイントークン・具体レイアウトは ADR 0015 のデザイン工程が担う（受け入れ条件は `design-system.md`。時・分の選択の部品としての契約は同 6-12。土日・祝日の色は同 2-1-x〜2-1-ab・2-6。カレンダーと時刻入力の行は **画面固有の合成として後続の画面 Issue が持つ** —— 同 AC-5-3） |
| 8-5 | 同梱した祝日データが内閣府の公表と一致していることは、テストで検査しない。一致は AC-10 の更新の手順（差し替えの差分のレビュー）が担保する |
| 8-6 | 同梱データの対象の年の外にある日は、祝日であっても祝日として表示されない（AC-9-7。ADR 0021「悪い影響 / トレードオフ」）。データの更新が遅れた期間、その年の祝日は平日と同じに見える |
| 8-7 | 祝日の表示は業務ルールに影響しない（P-3）。祝日に稼働を入力しても、検証・算出・締めの扱いは平日と変わらない |
| 8-8 | 保存前に示す稼働時間（AC-3-6）と、保存されるドメインの算出値との一致は、3-6-d が使う表の行の範囲でだけ検査される。表に無い時刻の組で両側の算出が食い違うことは、テストでは排除できない。食い違っても保存される値はドメインの算出であり（3-6-c）、保存の後に示す値は正しい |

### AC-9. カレンダーの祝日の表示

祝日の判定は AC-10 の同梱データだけを引く。曜日の色の値は `design-system.md` 2-1-x〜2-1-ab が持ち、本 AC は「どの日をどう示すか」だけを定める。

| # | 対象日 | 期待 |
|---|---|---|
| 9-1 | 同梱データに載る日で、月〜金のいずれか | 祝日として示す: 日付の文字色・マスの地色を日曜と同じ系統（`--et-sun` / `--et-sun-bg`）にし、祝日であることを示す **文字の札** を出す |
| 9-2 | 同梱データに載る日で、日曜 | 9-1 と同じ（札を出す） |
| 9-3 | 同梱データに載る日で、土曜 | 9-1 と同じ（祝日の示し方を土曜の示し方より優先する）—— AI 起案（2026-10-13 に人間が承認） |
| 9-4 | 同梱データに載らない日曜 | 日曜の系統で示し、札を出さない |
| 9-5 | 同梱データに載らない土曜 | 土曜の系統（`--et-sat` / `--et-sat-bg`）で示し、札を出さない |

| 9-8 | 札の文言 | `祝` —— AI 起案（2026-10-13 に人間が承認。ハンドオフに倣った）。祝日の名称は示さない |

| 9-11 | read-only の状態・ゲスト | 9-1〜9-9 の示し方は状態・ロールによらず同じ（祝日の表示は操作ではない） |

### AC-10. 祝日データの同梱（置き場所・対象の年・更新の手順）

ADR 0021 決定4 が「データの置き場所・更新の手順・同梱する対象の年は、カレンダーを持つ画面の UI 仕様が持つ」と委ねた事項である。人間が決めたのは「内閣府の『国民の祝日』のデータを同梱し、外部から取得せず、表示だけに使う」ことまでであり、表の「決定の別」が AI 起案（2026-10-13 に人間が承認）の行は、AI が起案した具体である。
