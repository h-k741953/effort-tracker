# 月次締め — 仕様

MVP ユースケース2「**月次締め**」の受け入れ条件。根拠は Issue #6 の議論と `docs/domain/ubiquitous-language.md`。

**確定済みのユビキタス言語・丸め規則・状態遷移・精算幅の保持はこの仕様へ書き写さない。** 正解は `docs/domain/ubiquitous-language.md` にあり、本仕様はそれを参照して「締めが満たすべき形」だけを定める（ADR 0004）。

- **決定者**: 人間（プロジェクトオーナー）。業務ルールは `docs/ai-collaboration.md` の責務分界に従い人間が決定した（Issue #6 で選択）
- **日付**: 2026-07-23

---

## スコープ

**MVP ユースケース2（月次締め）のみ**を対象とする。

- 対象: 勤務月（`WorkMonth`）の締め（`Close`）操作、締め可否の判定、締め時の超過（`Excess`）／不足（`Shortfall`）の計算・保存、締めに伴う状態遷移（`Draft` → `PendingApproval`）
- 非対象: **承認（`Approve`）・差戻し（`Reject`）の操作仕様は Issue #7（UC3）が持つ。** 本仕様は「締め＝`PendingApproval` への遷移」までを対象とし、承認待ち以降の操作は UC3 へ委譲する
- 非対象: 稼働実績の入力・編集（Issue #5 / UC1）、契約の管理（与件として扱う。`docs/rules/scope.md`）、技術者の横断ビュー、請求・支払・ファイル添付、監査履歴

## 前提（P）— 確定事項（参照のみ、再定義しない）

`docs/domain/ubiquitous-language.md` の確定事項を前提とする。本仕様はこれらを覆さない。

| # | 前提 | 出典 |
|---|---|---|
| P-1 | 勤務月は `契約 × 年月` で一意。集約ルートは `WorkMonth` の1つのみ | ユビキタス言語「勤務月の同一性」 |
| P-2 | 勤務月は生成時に契約から精算幅（`SettlementRange`：`LowerBound`／`UpperBound`）を値オブジェクトとして複写している。契約変更は当該勤務月に遡及しない | ユビキタス言語「契約と精算幅の保持」 |
| P-3 | 総稼働時間（`TotalHours`）は、日次の各実績を**15分単位で切り捨て**てから合計した値。合計してから丸めない | ユビキタス言語「丸め規則」 |
| P-4 | 締め（`Close`）は入力を確定させ、**同時に承認を求める**操作。締めると状態は締め済（`PendingApproval`＝承認待ちを兼ねる）になる | ユビキタス言語「『締め』と『承認申請』の関係」 |
| P-5 | 状態遷移は `Draft` →（締め）→ `PendingApproval` →（承認）→ `Approved`、差戻しで `PendingApproval` → `Draft`。**承認済は終端で、遷移は循環しない** | ユビキタス言語「状態遷移」 |
| P-6 | 締め済（`PendingApproval`）・承認済（`Approved`）では技術者は稼働実績を編集できない | ユビキタス言語「状態と操作」／UC1 P-5 |
| P-7 | 超過（`Excess`）は総稼働時間が上限を上回った分、不足（`Shortfall`）は総稼働時間が下限を下回った分。いずれも**時間側の量** | ユビキタス言語「精算」 |

## 決定（Issue #6 で人間が選択した業務ルール）

推測で埋めず、Issue #6 で人間が明示選択した。**各行の決定者は人間である。**

| # | 論点 | 決定 |
|---|---|---|
| D-1 | 締められる条件（入力の完全性） | **未入力日があっても締められる。** 入力済みの稼働実績だけを合計する。UC1 の D-5「未入力日とゼロ稼働日を区別しない」と整合させるための選択。「全日入力済み必須」は設計上判定不能なので採らない |
| D-2 | 超過・不足の計算タイミング | **締め時に計算して保存する。** 締めた時点の事実を勤務月に固定する（精算幅スナップショットと同じ「遡及しない」思想）。勤務月が計算結果（超過または不足）を保持する |
| D-3 | 締めのタイミング | **いつでも締められる**（月末制約なし。月途中終了の契約に対応する） |
| D-4 | 締めの取り消し | **認めない。** 下書きへ戻す手段は承認者の差戻し（`Reject`、UC3）のみ。状態遷移を循環させない（P-5） |
| D-5 | 締められる人 | **技術者本人のみ**（承認者の代行締めは無い） |
| D-6 | 空の勤務月 | **締められる。** 稼働ゼロ（総稼働時間 0）も事実として確定させる。不足が出るがそれも精算上の事実 |

## 受け入れ条件（AC）

| AC | 主題 | 主に効く工程 |
|---|---|---|
| AC-1 | 締め操作の可否（状態別）（P-5・D-3） | tester・implementer |
| AC-2 | 締められる人（本人のみ）（D-5） | tester・implementer |
| AC-3 | 締め時の超過／不足の計算・保存（D-2） | tester・implementer |
| AC-4 | 超過／不足の算出ロジックと境界（P-7・P-3） | tester・implementer |
| AC-5 | 締めに伴う状態遷移と帰結（P-4・P-6） | tester・implementer |
| AC-6 | 締めの取り消し不可（D-4） | tester・implementer |
| AC-7 | 空月・未入力日を含む月の締め（D-1・D-6） | tester・implementer |
| AC-8 | 限界 — 本仕様が担保しないこと | reviewer |

### AC-1. 締め操作の可否（状態別）

締めは**下書き（`Draft`）からのみ**行える。締め済・承認済からは締められない（再締め・二重締めを禁じる）。

| # | 締め操作前の状態 | 締め（`Close`）操作 | 期待 |
|---|---|---|---|
| 1-1 | 下書き（`Draft`） | 実行 | **許可。** 締め済（`PendingApproval`）へ遷移する（AC-5） |
| 1-2 | 締め済（`PendingApproval`） | 実行 | **弾く**（既に締められている。二重締めを認めない） |
| 1-3 | 承認済（`Approved`） | 実行 | **弾く**（終端状態。P-5） |
| 1-4 | 締めのタイミング | 月末か月途中かを問わない | **月末制約は課さない**（D-3）。暦月の途中でも締められる |

### AC-2. 締められる人（本人のみ）

| # | 操作者 | 対象勤務月 | 期待 |
|---|---|---|---|
| 2-1 | その勤務月の技術者本人 | 自分の勤務月 | **許可**（D-5） |
| 2-2 | 本人以外の技術者 | 他人の勤務月 | **弾く**（自分の勤務月のみ操作できる） |
| 2-3 | 承認者 | 技術者の勤務月 | **弾く**（承認者による代行締めは無い。D-5）。承認者の関与は承認・差戻し（UC3）に限られる |

### AC-3. 締め時の超過／不足の計算・保存

締めた時点で超過／不足を**計算し、勤務月に保存する**（D-2）。以降この値は再計算しない（締めた時点の事実の固定）。

| # | 条件 | 期待 |
|---|---|---|
| 3-1 | 締めが成立する時（AC-1-1） | その時点の総稼働時間（P-3）と、勤務月が保持する精算幅スナップショット（P-2）を比較し、超過／不足を算出（AC-4）して勤務月に保存する |
| 3-2 | 保存後に契約側の精算幅が変更された | 保存済みの超過／不足は**変わらない**（P-2 の遡及しない思想。締めた時点の精算幅で固定される） |
| 3-3 | 締め後に総稼働時間の基となる実績を（何らかの手段で）変えても | 締め済では編集できない（P-6）ため、保存済みの超過／不足は変わらない |
| 3-4 | 超過と不足の同時成立 | **起こらない。** 総稼働時間は1つの値であり、上限超過と下限未達は同時に成立しない（AC-4）。少なくとも一方は必ず 0 |

### AC-4. 超過／不足の算出ロジックと境界

総稼働時間（`TotalHours`）と精算幅の下限（`LowerBound`）・上限（`UpperBound`）を**時・分の粒度で**比較する。総稼働時間は既に15分切り捨て合計済み（P-3）であり、**締め時に追加の丸めを行わない。** 超過・不足も時・分で表す（P-7）。

判定規則:

| 条件 | 超過（`Excess`） | 不足（`Shortfall`） |
|---|---|---|
| `TotalHours > UpperBound` | `TotalHours − UpperBound` | 0 |
| `LowerBound ≤ TotalHours ≤ UpperBound`（範囲内） | 0 | 0 |
| `TotalHours < LowerBound` | 0 | `LowerBound − TotalHours` |

**境界は両端とも「含む」（範囲内として扱い、超過・不足を発生させない）。** 以下、精算幅を `LowerBound = 140時間0分`／`UpperBound = 180時間0分` とした具体例で固定する。

| # | 総稼働時間 | 期待（超過 / 不足） | 主旨 |
|---|---|---|---|
| 4-1 | 180時間15分 | 超過 15分 / 不足 0 | 上限超過 |
| 4-2 | 180時間0分 | 超過 0 / 不足 0 | **上限ちょうどは範囲内**（上限を「含む」） |
| 4-3 | 160時間0分 | 超過 0 / 不足 0 | 範囲内（中間） |
| 4-4 | 140時間0分 | 超過 0 / 不足 0 | **下限ちょうどは範囲内**（下限を「含む」） |
| 4-5 | 139時間45分 | 超過 0 / 不足 15分 | 下限未達 |
| 4-6 | 0時間0分 | 超過 0 / 不足 140時間0分 | 稼働ゼロ（AC-7-2）。不足が下限そのものに一致する |

> 総稼働時間は15分の倍数（P-3 の帰結）。精算幅の下限・上限は分単位で保持しうるため、超過・不足の差分も分単位で表しうる（例: 上限が 180時間30分 なら 4-2 は超過 0）。**比較・減算はいずれも分単位で行い、締め時に丸めない。**

### AC-5. 締めに伴う状態遷移と帰結

| # | 締め成立（AC-1-1）後 | 期待 |
|---|---|---|
| 5-1 | 状態 | 締め済（`PendingApproval`）へ遷移する（P-4）。「締めたが未申請」という中間状態は作らない |
| 5-2 | 技術者による稼働実績の入力・編集・削除 | **弾く**（P-6）。締め済は編集不可 |
| 5-3 | 保持する値 | 総稼働時間（P-3）と、AC-3 で算出・保存した超過／不足を保持する |
| 5-4 | この先の遷移 | 承認（`Approve` → `Approved`）または差戻し（`Reject` → `Draft`）。**いずれも UC3（Issue #7）の対象**であり、本仕様は扱わない |

### AC-6. 締めの取り消し不可

| # | 条件 | 期待 |
|---|---|---|
| 6-1 | 締め済（`PendingApproval`）の勤務月を、技術者自身が下書きへ戻す操作 | **存在しない**（D-4）。締めの取り消し機能を提供しない |
| 6-2 | 締め済から下書きへ戻す唯一の手段 | 承認者による差戻し（`Reject`、UC3）のみ。技術者の締め取り消しと差戻しは**機能重複させない**（D-4） |

### AC-7. 空月・未入力日を含む月の締め

| # | 条件 | 期待 |
|---|---|---|
| 7-1 | 一部の日が未入力の勤務月 | **締められる**（D-1）。入力済みの稼働実績だけを合計して総稼働時間とする（P-3・UC1 D-5）。「全日入力済み」を締め条件にしない |
| 7-2 | 稼働実績が1件も無い勤務月（空月） | **締められる**（D-6）。総稼働時間は 0時間0分。下限が正なら不足が発生し（AC-4-6）、その不足も精算上の事実として保存する |
| 7-3 | 未入力日の扱い | 「レコードのない日＝稼働なし」として合計の項に現れない（UC1 D-5）。締め時に未入力を検出・警告しない（判定不能なため。D-1） |

### AC-8. 限界 — 本仕様が担保しないこと

**以下は仕様どおりであり、欠陥ではない。**

| # | 内容 |
|---|---|
| 8-1 | **承認・差戻しの操作は対象外。** 締め済（`PendingApproval`）以降の承認（`Approve`）・差戻し（`Reject`）の操作仕様は Issue #7（UC3）が持つ。本仕様は「締め＝`PendingApproval` への遷移」までに閉じる |
| 8-2 | **締めの完全性を問わない。** 未入力日・空月を締められる（D-1・D-6）ため、「全日入力済み」や「一定の稼働があること」を締めの前提条件にしない。これは UC1 D-5 との整合の帰結であり、意図的な仕様 |
| 8-3 | **締めの取り消し・承認取消しは無い**（D-4、およびユビキタス言語「承認済は終端」）。監査履歴も MVP スコープ外。誰がいつ締めたかの履歴を保持しない |
| 8-4 | **精算金額を算出しない。** 超過・不足はいずれも時間側の量（P-7）であり、金額への換算・請求・支払はスコープ外（`docs/rules/scope.md`） |
| 8-5 | 本仕様は受け入れ条件のみを定め、内部レイヤー配置（clean architecture の各リング）や永続化の詳細は実装工程が `docs/adr/0008` に従って決める |
