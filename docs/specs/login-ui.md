# ログイン — UI/画面 仕様

エンドユーザー認証（Amazon Cognito）のログイン画面、およびデモ用ロール切替の UI/画面 受け入れ条件。**決定と方式は ADR 0016 が持ち、本仕様はそれを参照して「ログイン・ロール切替が満たすべき形」だけを定める**（ADR 0004）。認証方式・MFA 方式・ロールの分界を本仕様へ書き写さない。

- **決定者**: 人間（プロジェクトオーナー）。認証方式は ADR 0016、ゲスト閲覧導線・デモ用ロール切替は人間決定（旧 N-1・N-2）。**AI が業務判断を足さない**
- **日付**: 2026-07-25（2026-10-10 改定: ヘッダーの構成 AC-9 を追加、ロールを切り替えたとき・URL を直接開いたときに、そのロールで開けない画面から既定の画面へ移す AC-6-7〜6-10 を追加。2026-10-13 改定: ログイン画面を開いたときの扱い AC-6-10・6-10-a を確定し、旧 LQ-2 を解消。同日の人間決定により、AI 起案の箇所をすべて人間の承認済みへ改めた。9-6 の遷移を `design-system.md` AC-8 の 8-1-j へ足した）
- **前提 ADR**: 0016（Cognito・3方式・ロール分界）／0013・0014（AWS ネイティブ・BFF 実行ロール）／0015（デザイン工程）／0021（閲覧系の画面）
- **AI 起案の扱い**: 条文中に「AI 起案（2026-10-13 に人間が承認）」と書いた箇所は、AI が起案し、2026-10-13 に人間が一括で承認したものである。承認済みであり、その箇所をテストの期待値にしてよい

---

## スコープ

- **対象**: ログイン画面における3つのログイン方式の提示、ゲスト（未ログイン）の閲覧導線への入口、**デモ用ロール切替コントロール**、認証の BFF 終端という前提の UI 上の帰結、ログイン失敗の表示、全画面に共通するヘッダーの構成（ロール切替・テーマ切替の置き場所）
- **非対象**:
  - Cognito のインフラ構成・トークン検証の実装（実装工程／ADR 0016）
  - **ユーザー・ロール管理画面**（非スコープ。`docs/rules/scope.md`／ADR 0016）
  - 承認者の割り当て・招待・組織管理（非スコープ。`approval.md` AC-9-5）
  - ゲスト向けデモ勤務月群・各一覧の中身（`work-month-listing-ui.md`）
  - デザイントークン・具体レイアウト（ADR 0015 のデザイン工程。受け入れ条件は `design-system.md`）

## 前提（P）— 確定事項（参照のみ、再定義しない）

| # | 前提 | 出典 |
|---|---|---|
| P-1 | 認証は Cognito（User Pool）。ログインは3方式（ゲスト＝閲覧のみ／メール+パスワード+MFA(TOTP)／Google OIDC） | ADR 0016 決定 |
| P-2 | エンドユーザー認証は BFF（Next.js Route Handler）で終端する。BFF がトークンを検証し、以降のドメイン API 呼び出しは実行ロールの SigV4 署名（ADR 0014）。ブラウザは Lambda を直接呼ばない | ADR 0016／`docs/rules/architecture.md` |
| P-3 | ロール（`Engineer`/`Approver`）は認可の関心事で認証とは別。**デモ用に切替可能**で、ロール管理画面は作らない | ADR 0016／`docs/rules/scope.md` |
| P-4 | 静的な長期認証情報を UI・クライアントに置かない。MFA は TOTP（追加コスト0・濫用ベクタを持たない） | `docs/rules/security.md`／`docs/rules/cost-guardrails.md`／ADR 0016 |
| P-5 | 自己承認排除（`approval.md` D-4）はロールに依存せず維持する | ADR 0016／`approval.md` |

AC-8（限界）の番号を保つため、2026-10-10 に加えた AC-9 は AC-8 の後ろに置く。

### AC-1. 3方式の提示

| # | 条件 | 期待 |
|---|---|---|
| 1-1 | ログイン画面 | 3つの入口を提示する——(a) ゲストとして閲覧のみで続行 (b) メール+パスワード (c) Google 連携（ADR 0016 決定） |
| 1-2 | 方式の欠落 | 3方式のいずれも欠かさない。SMS による MFA 等、ADR 0016 が退けた方式を提示しない |

### AC-2. メール + パスワード + MFA(TOTP)

| # | 条件 | 期待 |
|---|---|---|
| 2-1 | メール+パスワードの入口 | 新規登録とログインの両方に対応する |
| 2-2 | MFA | **TOTP（認証アプリ）**による多要素認証を行う（ADR 0016）。SMS を用いない |
| 2-3 | 機密の扱い | パスワード等の機密を URL・ログ・画面に露出させない。静的な長期認証情報をクライアントに置かない（P-4／`docs/rules/security.md`） |

> TOTP 登録（認証アプリのシークレット提示・QR 等）の具体的な画面フローは、Cognito の提供機能に依存する。本 AC は「TOTP による MFA を行う」ことのみ要求し、登録フローの細部は実装／デザイン工程が ADR 0016 に従って定める。

### AC-3. Google 連携（OIDC）

| # | 条件 | 期待 |
|---|---|---|
| 3-1 | Google の入口 | OIDC ソーシャルサインインで認証する（ADR 0016） |
| 3-2 | クライアントシークレット | UI・リポジトリに露出させない（`terraform.tfvars` は gitignore 済み。`docs/rules/security.md`／ADR 0016 トレードオフ） |

### AC-4. ゲスト（未ログイン）＝閲覧のみ

| # | 条件 | 期待 |
|---|---|---|
| 4-1 | ゲストとして続行 | Cognito のユーザーを作らず、未認証状態で閲覧導線へ入る（MAU を消費しない。ADR 0016） |
| 4-2 | ゲストの操作可否 | 状態を変える操作を提供しない（勤務月画面の共通仕様 AC-3 ゲスト行＝全操作を非表示・閲覧のみ） |
| 4-3 | ゲストの閲覧対象 | **デモ用サンプル勤務月群を読み取り専用で閲覧する**（人間決定・旧 N-1）。仕様は `work-month-listing-ui.md` AC-3 が持つ。本人一覧・承認待ち一覧はゲストの導線ではない |

### AC-5. 認証の BFF 終端という前提の帰結

| # | 条件 | 期待 |
|---|---|---|
| 5-1 | 認証処理 | BFF（Route Handler）で終端する。ブラウザから Lambda（ドメイン API）を直接呼ばない（P-2） |
| 5-2 | ログイン後の現在ユーザー | BFF が検証したトークンから決まる。画面はそれを前提に本人／承認者／ゲストの区別を反映する（共通仕様 P-4・P-6） |

### AC-6. デモ用ロール切替コントロール

デモ用に `Engineer` / `Approver` を切り替える軽量コントロール（人間決定・旧 N-2）。**ロール管理画面は作らない**（`docs/rules/scope.md`／ADR 0016 維持）。

| # | 条件 | 期待 |
|---|---|---|
| 6-1 | ログイン中（デモ） | **ヘッダー等に軽量なロール切替コントロールを置く**。`Engineer` / `Approver` を切り替えられる（P-3） |
| 6-2 | 切替の帰結 | 切替後のロールに応じて、勤務月画面の操作可否（共通仕様 AC-3）・承認待ち一覧への導線（`work-month-listing-ui.md` AC-2）が変わる |
| 6-3 | 管理 UI との分界 | これは**デモ用の切替に限り**、ユーザー・ロールの割り当てを管理する画面ではない（非スコープを維持。`docs/rules/scope.md`／ADR 0016） |
| 6-4 | 自己承認排除との関係 | ロールを `Approver` に切り替えても、自分が技術者である勤務月では承認・差戻しを非表示（自己承認排除はロール非依存で維持。P-5／`approval-ui.md` AC-3） |
| 6-5 | ゲスト | ゲスト（未ログイン）はロールを持たず、切替コントロールを提供しない（閲覧のみ。AC-4） |
| 6-6 | 勤務月画面で切り替えたとき | 同じ勤務月画面に留まり、操作要素だけが切替後のロールに応じて変わる（6-2・`work-month-screen-ui.md` AC-7「画面自体は遷移しない」の帰結） |

6-7〜6-9-b は 2026-10-10 の人間決定「ロールを切り替えたときや URL を直接開いたときに、そのロールで開けない画面だったら、そのロールの既定の画面へ移す。既定の画面は、技術者＝自分の勤務月、承認者＝承認待ち、ゲスト＝サンプル勤務月。勤務月画面はこれまでどおり、その場で操作が切り替わる」を条文にしたものである（`design-system.md` D-2-11。画面遷移の導出図は同 8-1-i）。6-10 は 2026-10-13 の人間決定「ログイン済みの技術者・承認者がログイン画面を開いたら、そのロールの既定の画面へ移す（2026-10-10 の決定と同じ扱い）」を条文にしたものであり、6-10-a はゲストについての既存条文からの帰結である。ゲストはロールを持たない（6-5）が、本節では利用者の区分としてロールと同じに扱う。

| # | 条件 | 期待 | 決定の別 |
|---|---|---|---|
| 6-7 | そのロールで開ける画面 | 技術者: 本人の勤務月一覧・契約一覧・稼働の推移・ヘルプ（`work-month-listing-ui.md` AC-10-2）と勤務月画面。承認者: 承認待ち一覧・ヘルプ（同 AC-10-3）と勤務月画面。ゲスト: デモ勤務月群・ヘルプ（同 AC-10-4）と勤務月画面。ログイン画面は 6-10・6-10-a が定め、ここに含めない。これ以外の画面を「そのロールで開けない画面」とする | 既存条文（サイドバーの項目の集合）からの帰結 |
| 6-7-a | 既定の画面 | 技術者は本人の勤務月一覧（`work-month-listing-ui.md` AC-1）、承認者は承認待ち一覧（同 AC-2）、ゲストはデモ勤務月群（同 AC-3） | 人間決定 |
| 6-8 | ロールを切り替えた時点で、切替後のロールで開けない画面を開いている | 切替後のロールの既定の画面（6-7-a）へ移す。例: 承認者として承認待ち一覧を開いたまま技術者へ切り替える → 本人の勤務月一覧へ。技術者として契約一覧・稼働の推移・本人の勤務月一覧のいずれかを開いたまま承認者へ切り替える → 承認待ち一覧へ | 人間決定 |
| 6-8-a | ロールを切り替えた時点で、切替後のロールでも開ける画面を開いている | 移さない。ヘルプは同じ画面に留まる。勤務月画面は同じ勤務月画面に留まり、操作要素だけが切替後のロールに応じて変わる（6-6） | 人間決定 |
| 6-9 | URL を直接開いた（リンク・再読み込み・アドレスの入力）とき、その画面が現在のロールで開けない画面だった | 現在のロールの既定の画面（6-7-a）へ移す。例: ゲストが契約一覧を開く → デモ勤務月群へ。承認者が稼働の推移を開く → 承認待ち一覧へ。技術者が承認待ち一覧を開く → 本人の勤務月一覧へ | 人間決定 |
| 6-9-a | URL を直接開いた画面が勤務月画面だった | 移さない（勤務月画面は 6-7 のどのロールでも開ける画面である）。操作要素は状態×ロールで決まる（共通仕様 AC-3）。どの勤務月のデータを取得できるかは本 AC の対象外であり、`domain-api-http-contract.md` と `bff-auth-termination.md` が持つ | 人間決定 |
| 6-9-b | 移したことの帰結 | 移すことは画面の遷移だけであり、勤務月の状態・稼働実績を変えない | 既存条文からの帰結（`work-month-listing-ui.md` AC-10-7 と同じ） |
| 6-10 | ログイン済み（技術者・承認者）でログイン画面を開く（リンク・再読み込み・アドレスの入力） | ログイン画面を表示せず、そのロールの既定の画面（6-7-a）へ移す。技術者は本人の勤務月一覧へ、承認者は承認待ち一覧へ。6-8・6-9 と同じ扱いであり、移したことの帰結は 6-9-b のとおり | 人間決定（2026-10-13） |
| 6-10-a | ゲスト（未ログイン）がログイン画面を開く | 移さない。ログイン画面を表示する。ゲストは未認証のまま閲覧しており（4-1・6-5）、メール+パスワードと Google の入口はログイン画面にある（1-1 (b)(c)）。ゲストをログイン画面から移すと、ログインする手段が無くなる | 既存条文（1-1・4-1・6-5）からの帰結 |

### AC-7. ログイン失敗・エラー表示

| # | 条件 | 期待 |
|---|---|---|
| 7-1 | 認証失敗（資格情報誤り・MFA 不一致等） | 失敗を提示し、機密を露出させず、再試行できる（共通仕様 AC-6 に準ずる） |
| 7-2 | 通信・サーバエラー | エラーを提示し、破壊的な副作用を伴わない |

### AC-8. 限界 — 本仕様が担保しないこと

| # | 内容 |
|---|---|
| 8-1 | **ユーザー・ロール管理画面を設けない**（非スコープ。`docs/rules/scope.md`／ADR 0016）。AC-6 はデモ用の切替に限る |
| 8-2 | **承認者の割り当て・招待・組織管理を行わない**（`approval.md` AC-9-5） |
| 8-3 | Cognito のインフラ構成・TOTP 登録フローの細部・トークン検証の実装は本仕様の対象外（実装工程／ADR 0016） |
| 8-4 | デザイントークン・具体レイアウトは ADR 0015 のデザイン工程が担う（受け入れ条件は `design-system.md`。ロール切替コントロールの部品としての契約は同 AC-6-3） |
| 8-5 | ハンドオフの「ロール切替で、一覧画面では相手のロールの一覧へ遷移する」は、2026-10-10 の人間決定により 6-8 の形で採った。移すのは切替後のロールで開けない画面を開いていたときに限り、切替後のロールでも開ける画面（ヘルプ・勤務月画面）では移さない（6-8-a） |
| 8-6 | 6-8・6-9・6-10 で移したときに、移したことを利用者へ知らせる表示は本仕様で要求しない。移した後の URL・履歴の扱い（置き換えるか積むか）も定めない（`design-system.md` 8-4 と同じく URL を固定しない） |
| 8-7 | 6-8・6-9・6-10 は画面の出し分けであり、認可の境界ではない。開けない画面のデータを取得させないことは本仕様では担保せず、データの取得の可否は BFF とドメイン API の側（P-2。`bff-auth-termination.md`・`domain-api-http-contract.md`）が持つ |

### AC-9. ヘッダーの構成（全画面に共通）

ヘッダーの部品は `AppHeader`（`design-system.md` AC-6 の 6-11）とする。テーマの切替・保存の仕組みは `design-system.md` AC-12 が持ち、本 AC は「どの画面のヘッダーに何を置くか」だけを定める（同 AC-12-2 が各 UI 仕様へ委ねた事項）。

| # | 条件 | 期待 | 決定の別 |
|---|---|---|---|
| 9-1 | 置く画面 | ログイン画面を含む全画面にヘッダーを置く | 既存（`design-system.md` 5-1-a「全画面」） |
| 9-2 | ロール切替 | ログイン中に限り置く（6-1・6-5）。ゲストとログイン画面には置かない | 人間決定（旧 N-2）からの帰結 |
| 9-3 | テーマ切替 | `ThemeToggle`（`design-system.md` 6-14）を、ログイン画面とゲストを含む**全画面**のヘッダーに置く | 切替を置くことは人間決定（2026-10-09）。置く画面と位置は AI 起案（2026-10-13 に人間が承認。ハンドオフに倣った） |
| 9-4 | テーマ切替とゲスト | テーマ切替は業務の操作ではない（`design-system.md` AC-12-5）。ゲストの「状態を変える操作を提供しない」（AC-4-2）の対象外であり、ゲストにも提供する | 既存条文からの帰結 |
| 9-5 | 認証の前後でのテーマ | ログイン・ログアウト・ロール切替の前後で、利用者が選んだテーマが変わらない（`design-system.md` AC-12-3「認証の情報と結び付けない」の帰結） | 既存条文からの帰結 |
| 9-6 | ゲストからログインへの導線 | ゲストの各画面のヘッダーに、ログイン画面へのリンクを置く。ログイン中とログイン画面には置かない | AI 起案（2026-10-13 に人間が承認。ハンドオフに倣った。承認を受けて、この遷移を `design-system.md` AC-8 の 8-1-j の辺として表と図に足した） |
| 9-7 | 右側の並び | ロール切替 → テーマ切替 → ログインへのリンク（出すものだけを、この順に並べる） | AI 起案（2026-10-13 に人間が承認。ハンドオフに倣った） |

## 未確定点（人間の決定を待つ）

推測で埋めない。決まった時点で該当の条文へ反映し、この節から消す（旧 N-1・N-2 はいずれも人間決定済み。AC-4-3・AC-6 に反映）。旧 LQ-1（ロールを切り替えた時点で、切替後のロールのサイドバーに無い画面を開いていた場合）は、2026-10-10 に人間が「そのロールの既定の画面へ移す」と決定し、AC-6-7〜6-9-b・8-5 に反映した。旧 LQ-2（ログイン済みの技術者・承認者がログイン画面を開いた場合）は、2026-10-13 に人間が「そのロールの既定の画面へ移す」と決定し、AC-6-10 に反映した。
