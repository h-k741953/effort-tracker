# スコープ

MVP の業務ユースケースは以下の3つに限定する。

1. 稼働実績の入力・編集
2. 月次締め
3. 承認申請・承認

これに加えて実装してよいのは、下記「閲覧系の画面」に**名指しした4画面だけ**である。3ユースケースと4画面以外を**実装しない**。

集約は **勤務月 (WorkMonth) の1つだけ**を厳密にモデリングする。
請求・支払・ファイル添付はスコープ外（README の「今後の展望」に記載する）。

## 閲覧系の画面（ADR 0021）

3ユースケースを支える閲覧系の画面として、次の4つをスコープ内とする。根拠は `docs/adr/0021-mvp-scope-expansion-and-self-hosted-fonts.md`。

- ヘルプ — 全ロール（ゲストを含む）が閲覧する
- 一覧の絞り込み — 自分の勤務月の一覧と、承認待ちの一覧に加える
- 契約一覧 — 技術者が自分の契約を閲覧する
- 稼働の推移 — 技術者が自分の勤務月の総稼働時間を、契約ごとに月を追って精算幅と見比べる

- 4画面はいずれも**状態を変える操作を持たない**ものとする。業務ユースケースを増やすものではない
- 列挙に無い画面は、閲覧系であっても**加えない**ものとする。加えるには ADR が要る
- 契約は与件であり、集約の外にある。契約一覧・稼働の推移は**参照系の関心事**として読み、集約を増やさない
- 契約一覧は、契約が持つデータ（契約表示名・精算幅・契約期間・技術者）をそのまま読む。契約期間は契約のデータに項目として足す。契約のデータは**デモデータとして投入**し、管理する手段を作らない。ただし、ログインした技術者の契約は、システムが自動で1件用意する（下記「ログインした技術者の契約」）
- 契約期間は年月の範囲で表し、終了の定まらない契約を許す（例: 2025年4月〜）。契約期間は**表示にだけ使い**、対象年月が契約期間の外にあるかを検査しない。整合の検査は将来の検討事項とする（ADR 0021「将来の検討事項」）
- 稼働の推移は、締め済と承認済の勤務月を「確定した月」として数える。下書きの勤務月は「入力中」として区別して示し、平均と「精算幅に収まった月」の数から外す
- 稼働の推移で比べる精算幅は、各勤務月が写し取った精算幅とする（契約のいまの精算幅を使わない）。平均は、選んだ期間の確定した月で求め、時間の小数で小数第1位まで示す（小数第2位を四捨五入する）
- **スコープ外のまま**: 承認担当者一覧（承認者が技術者ごとの勤務月を横断して見る画面）、技術者の横断ビュー、契約の管理（CRUD）。下記「ログインした技術者の契約」で自動で用意することは、契約の管理に当たらない

## ログインした技術者の契約（ADR 0023。提案中）

デモでログインした技術者が稼働実績の入力と月次締めを体験できるよう、**初回ログイン時に、システムが契約を1件自動で用意する**。2026-10-29 に人間が決定した。根拠は `docs/adr/0023-auto-provision-contract-on-first-login.md`、受け入れ条件は `docs/specs/engineer-contract-provisioning.md`。

- システムの内部処理であり、**業務ユースケースを増やさない**。閲覧系の画面も名指しの4つのままである
- **画面を作らない**。利用者が契約を作成・変更・削除する画面・操作は作らない。**契約の管理（CRUD）はスコープ外のまま**である
- 契約は与件であり、集約の外にある。集約を増やさない
- 用意する場所・契約の中身・日次リセットでの扱いなどは未決である（同仕様の Q 節）。未決の点を、この規約から推測で埋めない

## 認証基盤の扱い（横断インフラ）

デモ公開の前提として **エンドユーザー認証（Amazon Cognito）はスコープ内**とする。ただしこれは上記3ユースケースを支える**横断的なインフラ**であり、4つ目の業務ユースケースを追加するものではない。根拠と方式は `docs/adr/0016-cognito-end-user-authentication.md`。

- **スコープ内**: ログイン3方式（ゲスト=閲覧のみ／メール+パスワード+MFA(TOTP)／Google OIDC）、本人確認、`Engineer` / `Approver` ロールに基づく操作可否
- **スコープ外のまま**: **ユーザー・ロール管理画面**（ロールはデモ用に切替可能とし、割り当ての管理 UI は作らない）。承認者の割り当て・招待・組織管理も作らない
