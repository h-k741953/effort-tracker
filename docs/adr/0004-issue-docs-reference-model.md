# 0004. Issue と docs の責務を分け、レファレンス型で運用する

- **ステータス**: 承認済み
- **日付**: 2026-07-16
- **決定者**: 人間（プロジェクトオーナー）

## コンテキスト

SDD を採用しており、仕様は `docs/specs/` に書いてから実装に入る（`CLAUDE.md`）。一方、タスク管理と議論には GitHub Issue を使う。

ここで両者の境界を定めないと、**仕様が Issue と docs の2箇所に書かれる**。これは単なる重複ではなく、次の順序で破綻する。

1. Issue で仕様を議論し、結論が Issue のコメントに書かれる
2. docs に転記する。この時点では一致している
3. 後から Issue のコメントで仕様が修正される。docs は更新されない
4. **どちらが正解か分からなくなる**

4 に至ると、SDD の前提が崩れる。「仕様書を読んでテストを書く」が成立しなくなり、実装者（人間・AI を問わず）は Issue のコメント履歴を遡って最新の結論を探すことになる。これは仕様書が存在しない状態と実質的に等しい。

AI にとっては特に致命的である。AI は Issue のコメント履歴を自動的には参照しない。`docs/specs/` を読んで実装する以上、docs が古ければ**AI は古い仕様を正しく実装する**。テストごと古くなるため、Green は何も保証しなくなる。

この問題は「両方をこまめに同期する」では解決しない。同期を人間の規律に頼る規約は腐る。この判断は `CLAUDE.md` でドメイン層の依存規約について既に下しているものと同じである。

## 決定

**レファレンス（参照）型で運用する。Issue と docs の責務を排他的に分ける。**

| 置き場所 | 持つもの | 持たないもの |
|---|---|---|
| **GitHub Issue** | 実装の**タスク**、仕様を決めるための**議論** | 決定した仕様そのもの |
| **`docs/`** | 決定した**最新の**設計・仕様のみ | 議論の過程、タスクの進捗 |

**「正解のデータは常に docs にある」を唯一の原則とする。** Issue 本文および PR には `docs/` 配下へのリンクを貼り、参照させる。Issue に仕様を書き写さない。

### 議論と決定の流れ

```
Issue（議論）  ──決定──▶  docs/specs/（唯一の正解）  ◀──参照──  Issue（タスク）
                                    ▲
                                    └──参照── PR
```

議論は Issue で行ってよい。ただし**結論が出た時点で docs に反映し、Issue には docs へのリンクを残す**。Issue のコメントに結論を書いて終わらせない。

### 置き場所は `docs/specs/` に集約する

`docs/design/` は作らない。仕様（What）と設計（How）を別ディレクトリに分けると、参照先が2つに増え、両者の同期を人間が担保する必要が生じる。これは本 ADR が回避しようとしている二重管理を、docs の内部に作り直すことになる。

MVP はユースケースが3つしかない。分離の利益より、参照先が1つである利益が上回る。

用途ごとの置き場所は既存の構成を踏襲する。

| 内容 | 置き場所 |
|---|---|
| 機能の仕様・受け入れ条件・実装設計 | `docs/specs/` |
| アーキテクチャ上の決定 | `docs/adr/` |
| 用語 | `docs/domain/ubiquitous-language.md` |

### 規約は CI で担保する

**「PR に docs へのリンクを貼る」を人間の記憶に委ねない。** 委ねた規約は必ず守られなくなり、守られなくなった時点を誰も検知できない。

`services/` または `apps/` を変更する PR は、本文に `docs/` 配下への参照を含むことを CI で必須とする（`.github/workflows/ci.yml` の `spec-link` ジョブ）。仕様を要さない変更には `no-spec` ラベルで例外を認める。

例外に**ラベルという明示的な操作**を要求するのは、例外を使ったこと自体を記録に残すためである。黙って迂回できる例外は例外ではない。

## 影響

### 良い影響

- 実装者が読むべき場所が1つに定まる。AI が `docs/specs/` だけを読めば最新の仕様に到達できる
- Issue が肥大化しない。議論は議論として残り、仕様は仕様として残る
- **docs の更新漏れが PR の時点で検知される**。従来は「Issue に書いたから良い」で docs が放置されたが、CI が落ちる

### 悪い影響 / コスト

- **議論の結論を docs に反映する手間が毎回かかる。** これは意図的なコストである。この手間を惜しむと二重管理に戻る
- Issue だけを読んでも仕様が分からない。リンクを辿る必要がある
- `no-spec` ラベルの運用が形骸化するリスクがある。全 PR に付けられていたら、規約が機能していない兆候として扱う
- **CI が検査できるのは「リンクが貼られているか」だけ**である。リンク先の docs が実際に最新かは検査できない。ここは人間のレビューに残る

## 検討した代替案

| 案 | 却下理由 |
|---|---|
| Issue に仕様を書く（docs を持たない） | SDD が成立しない。Issue はクローズされ検索性が落ちる。バージョン管理されず、コードとの対応が追えない |
| docs に議論も残す | 決定に至らなかった選択肢や途中の誤りが docs に混ざる。「最新の正解のみ」という docs の性質が失われ、読み手が結論を探す必要が出る |
| 両方に書き、都度同期する | 同期を人間の規律に頼る。腐る。腐ったことを検知できない |
| `docs/design/` を新設し What/How を分離 | 参照先が2つに増え、二重管理を docs 内部に作り直す。MVP の規模では分離の利益が小さい |
| CI での必須化をせず、テンプレートのみ | 記入を促すだけで強制力がない。守られなくなった時点を検知できない |
