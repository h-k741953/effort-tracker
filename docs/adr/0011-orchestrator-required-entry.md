# 0011. オーケストレーターを必須の入口とし、main エージェントの直接処理を禁じる

- **ステータス**: 承認済み
- **日付**: 2026-07-18
- **決定者**: 人間（プロジェクトオーナー）

> 本 ADR は **ADR 0010 §D のうち「オーケストレーターは既定の入口とする。人間の直接呼び出しは禁止しない」という一決定のみを置換する**。0010 の §A / §B / §C / §E / §F / §G、Context（メモリ機構）、および ADR の分割単位に関するメタ決定は**すべて有効なまま残る**。§D 自体も、工程による分割・停止条件の保持・握り潰し禁止は置換の対象外である。

## コンテキスト

ADR 0010 §D は「オーケストレーターは既定の入口とする。**人間の直接呼び出しは禁止しない**」と決めた。却下理由はこう書かれている。

> 禁止するには強制手段が要り、「規律に頼る規約は腐る」という本リポジトリの立場と両立しない

**この理由は「禁止が望ましくない」ではない。「強制手段が無い」である。** 強制手段を用意できるなら、却下の前提そのものが消える。本 ADR はその前提が消えたことを記録する。

### 既定入口のままで何が漏れるか

main エージェントが「〜を実装して」を直接処理した場合、次がまとめて素通りする。

| 素通りするもの | 根拠 |
|---|---|
| 仕様 → テスト → 実装の受け渡し（SDD / TDD） | `docs/rules/development-process.md` |
| Red の確認 | `docs/harness/verification-loop.md`「Red の確認を飛ばさない」 |
| 停止条件の保持（各工程エージェントが持つ） | ADR 0010 §D |
| 握り潰し禁止の経路（工程 → オーケストレーター → 人間） | ADR 0010 §D |
| `docs:` → `test:` → `feat:` のコミット順序 | `docs/rules/commit-convention.md` |
| 2段承認ゲート（方向性 / ループ開始） | `docs/harness/verification-loop.md` |

**ハーネスが効くのはオーケストレーター経由の経路だけであるのに、効かない経路が既定で開いている。** しかも main の直接処理は「速い」ため、放置すれば実質的な既定になる。ADR 0010 が §D で「既定の入口」と書いた意図は、この経路を常用しないことにあった。だが**既定は選択の初期値でしかなく、選択を止める力を持たない**。

### 人間が決定済みの事項

本 ADR の起票にあたり、以下は人間（プロジェクトオーナー）が既に選択している。AI が選んだものではない。

1. **強制手段は hook と rules の両方**（機械 + 規律の二層）
2. **例外の指定手段はプロンプト冒頭の定型トークン `[direct]`**
3. **禁止に触れたときはブロックして人間へ提示**（黙って委譲・警告のみで続行は却下）

AI が設計したのは、検知ロジックの限界（偽陰性・偽陽性）の扱いと、複数決定を持つ ADR の部分置換をどう表記するかである。

## 決定

**オーケストレーターを必須の入口とする。工程をまたぐ依頼を main エージェントが直接処理することを禁じる。**

### 1. 強制は「機械 + 規律」の二層で行う

| 層 | 実体 | 効く範囲 |
|---|---|---|
| 機械 | `UserPromptSubmit` hook。工程をまたぐ依頼を検知してプロンプトをブロックする | 検知パターンに一致するもの |
| 規律 | `docs/rules/responsibility.md` に main エージェントの振る舞いとして明記 | hook をすり抜けたもの（偽陰性） |

**二層にすることが、ADR 0010 §D の却下理由への応答である。** 0010 は「強制手段が無いから禁止しない」と言った。本 ADR は強制手段を伴わせたうえで禁止する。ただし機械の層は完全ではないため（後述5）、規律の層を受け皿として併置する。**「規律だけの規約は腐る」を「規律を一切使わない」と読み替えない。** 腐るのは強制手段の無い規律であって、機械が取りこぼした残余を規律が受けること自体ではない。

hook の受け入れ条件は `docs/specs/orchestrator-entry-hook.md` に置く。**本 ADR に検知パターンを書き写さない**（ADR 0004。正解は仕様書側の1箇所）。

### 2. 例外の指定手段は、プロンプト冒頭の定型トークン `[direct]` とする

プロンプトの冒頭が固定文字列 `[direct]`（半角8文字、大文字小文字を区別）に一致する場合**のみ**、main の直接処理を許す。

- **完全一致で機械判定できる。** 判定に解釈の余地が無く、fixture で固定できる
- **人間が意図的に打つ必要がある。** 打たない限り既定はオーケストレーター経由であり、「なし崩しに既定へ戻る」ことがない
- 例外を使った事実がプロンプトに残る。`no-spec` ラベルや `loop-extended` ラベルと同じ原理で、**例外には明示的な操作を要求する**

### 3. 禁止に触れたときはブロックし、理由と回避手段を人間へ提示する

hook はプロンプトを main に渡さずに停止し、人間に対して次を示す。

- ブロックした理由（工程をまたぐ依頼はオーケストレーターが入口であること）と、一致した検知パターン
- 回避手段1: オーケストレーターを使う
- 回避手段2: 冒頭に `[direct]` を付けて直接処理させる

**判断は AI ではなく人間に返す。** 「黙ってオーケストレーターへ委譲する」案は、どちらの経路で処理すべきかの判断を AI 自身にさせる点で、ADR 0010 §D の握り潰し禁止と同じ構造の問題を持つ。

### 4. 検知の対象は「工程をまたぐ依頼」であり、あらゆる依頼ではない

短い質問・調査・説明の依頼は通す。ブロックするのは、コードベースへの変更を伴う依頼と、Issue / PR への着手指示である。具体的な条件と境界値は `docs/specs/orchestrator-entry-hook.md` が持つ。

### 5. 検知は正規表現ヒューリスティックであり、偽陰性が残ることを認めたうえで採る

**自然言語の依頼が「工程をまたぐか」を機械的に完全判定することはできない。** 検知は正規表現ベースにならざるを得ず、次の2種の誤りが必ず残る。

| 誤り | 例 | 扱い |
|---|---|---|
| **偽陰性**（検知漏れ） | 「例のやつ、いい感じにしといて」 | **塞げない。** 規律層（`docs/rules/responsibility.md`）が受け皿。限界として記録する |
| **偽陽性**（誤爆） | 「docs に1行追加して」のような軽微な変更 | `[direct]` を付けて通す。逃げ道は用意済みで、恒久的に詰まることはない |

**偽陰性を「無い」ことにしない。** これは `check-domain-deps` が最内周しか見ないこと、`review-trail` が記録しか見ないことと同種の限界であり、このリポジトリは限界を隠さず書く方針を取っている（`docs/harness/verification-loop.md`「ハーネスの限界」）。

**非対称に倒す。** 偽陽性は人間が1トークン打てば解消するが、偽陰性はハーネスを黙って素通りさせる。したがって検知パターンは、迷ったら**ブロック側**に倒す。ただし例外が2つある。**入力が解釈できなかった場合は通す**（下記6）。もう1つは、**逃げ道で吸収できない種類の偽陽性**である。

**「`[direct]` があるから偽陽性は安い」が成り立つのは、偽陽性が稀な場合に限る。** 最頻のやり取り（質問・調査）で常時発火する偽陽性は、`[direct]` を毎回打つ習慣への退化を招き、hook を実質無効化する（下記「悪い影響」）。**退化が常態化する偽陽性は、逃げ道ではなく検知条件の側で下げる。** 具体的な線引きは仕様書が持つ。

### 6. 判定不能な入力は、ブロックせずに警告して通す

hook が入力（プロンプト JSON）を解釈できなかった場合、ブロックせず警告を出して通す。

**これは「検査対象を読めなかったことは、違反が無いことを意味しない」（`docs/harness/verification-loop.md`）からの意図的な逸脱である。** 理由は、この検査対象が**人間の入力経路そのもの**だからである。パースのバグでブロック側に倒すと、人間はあらゆるプロンプトを拒否され、復旧に必要な指示（設定を直せ）すら送れなくなる。**復旧手段が検査対象の内側にある場合、fail-closed はデッドロックになる。** ドメイン依存検査のように「落ちても人間が別経路で直せる」ものとは条件が異なる。

黙っては通さない。警告を人間に見せる（`docs/harness/verification-loop.md`「黙って成功させない」）。

### 7. Issue #16（Hooks 導入）の一部を先食いする

`UserPromptSubmit` hook の導入は、ADR 0010「承認後に切る実装 Issue」の5番（Hooks の導入 = Issue #16、未着手）の一部にあたる。**本 ADR の実装は、その先食いである。**

- 先食いするのは `UserPromptSubmit` の1イベントと、本 ADR が定める検知に限る。ADR 0010 §F の `PreToolUse`（プロンプトインジェクション検査）は先食いしない
- Issue #16 が着手される時点で、既に `.claude/settings.json` に `hooks` キーと1つの実装例が存在することになる。**Issue #16 側はそれを置き換えるのではなく、イベントを追加する**

### 8. 複数決定を持つ ADR の部分置換は、ステータス行への併記と §への注記で表す

ADR 0001 の運用ルール3は「古いほうのステータスを `廃止（NNNN により置換）` に変更する」と定める。**この規定は単一決定の ADR を前提にしている。** ADR 0010 は A〜G と Context を含む複合 ADR であり、そのステータスを `廃止` にすることは事実に反する（0010 の大半は生きている）。

そこで、部分置換の表記を本 ADR で定義する。**この表記の決め方自体を、以後の先例として記録する。**

- 旧 ADR の**ステータス行は変更しない**（`承認済み` のまま）。直下に1行を併記する
  ```
  - **一部置換**: §D の「人間の直接呼び出しは禁止しない」は ADR 0011 により置換（他の決定は有効）
  ```
- 置換された**節の該当箇所の直下に、注記を1行だけ入れる**
  ```
  > 上記のうち「人間の直接呼び出しは禁止しない」は **ADR 0011 により置換された**。工程をまたぐ依頼を main エージェントが直接処理することは禁止される。
  ```
- **本文は書き換えない。** 覆された決定の文面はそのまま残す（ADR 0001「決定が変わった事実自体が記録に値する」）

節への注記まで入れるのは、**ステータス行だけでは発見できないから**である。0010 §D は他の docs から名指しで参照されており（`docs/ai-collaboration.md`、`.claude/agents/orchestrator.md`）、リンクを踏んで §D だけを読む読者・AI が、覆された決定を生きているものとして読む。これは本リポジトリが最も警戒する失敗モード（古い docs を読んだ AI が古い仕様を正しく実装する。ADR 0004）そのものである。

ADR 0001 の「追記もしない」との関係は次のように解する。**禁止の趣旨は「決定内容を後から書き足し、いつ何が決まったかを不明にすること」であり、置換の告知はこれに当たらない。** 同ルールが既にステータス行の編集を認めていることからも、「置換された事実を旧 ADR 上に示す編集」は禁止対象外と読める。**この解釈は AI の判断であり、人間の承認を要する。**

## 影響

### 良い影響

- ハーネスが効かない経路が塞がる。SDD / TDD / 停止条件 / 握り潰し禁止 / コミット順序が、規律ではなく**構成上**の既定になる
- ADR 0010 §D の却下理由（強制手段が無い）に、強制手段を伴わせて正面から応じた記録が残る。**却下理由を無視して覆すのではなく、前提が消えたことを示して覆す**
- 例外が `[direct]` という1トークンに集約され、**例外を使った事実がプロンプトに残る**。`no-spec` / `loop-extended` と同じ形になり、例外の扱いがリポジトリ全体で一貫する
- 複数決定を持つ ADR の部分置換という、ADR 0001 が想定していなかったケースの表記が定まる（先例になる）

### 悪い影響 / コスト

- **偽陰性を塞げない（決定5）。** 検知は正規表現ヒューリスティックであり、平易な言い換え（「例のやつやっといて」）は通る。**「禁止した」と「禁止を強制できている」は同じではない。** 機械の層が保証するのは検知パターンに一致する範囲だけで、残余は規律層に依存する。この点で ADR 0010 §D が指摘した「規律に頼る規約は腐る」というリスクは、**縮小したが消滅していない**
- **偽陽性が人間の摩擦になる。** 軽微な変更依頼もブロックされ、`[direct]` の再入力を要する。逃げ道はあるが、頻発すれば「毎回 `[direct]` を付ける」習慣に退化し、hook が実質無効化されうる。**この退化は機械では検出できない**（`[direct]` 付きプロンプトの比率を人間が気にかけるしかない）
- **偽陽性を下げた分だけ偽陰性が増える（非対称原則の調整）。** 初期実装は変更語を名詞のまま登録しており、「この実装どうなってる?」のような質問が一律ブロックされた。上記の退化リスクが**例外ではなく常態**になるため、検知を指示形に絞った。その代償として「実装をお願いします」のように**助詞を挟む依頼が偽陰性へ回る**
  - 上の項の偽陰性（決定5）が**塞げないもの**であるのに対し、これは**塞がないと選んだもの**である。連接規則を緩めれば拾えるが、緩めれば名詞形の質問へ波及する。**両者は同じ目盛りの上にあり、片方を締めれば他方が緩む**
  - 英語も同じ観点で `fix` を外した（名詞と動詞が同綴で機械的に区別できない）。`implement` は名詞形が別語のため残る
  - **語尾を列挙で閉じる方式は、列挙漏れという二次的な偽陰性を持つ**（実測で `実装してね` の通過を確認した）。塞ぎ方は**列挙を増やす＝検知を強める側に限る**。「質問形の語尾を除外条件にする」型の規則（下記却下案）は後置きで除外が成立するため採らない。列挙漏れの残余は仕様書 AC-6 に限界として記録する
  - **この目盛りをどこに置いたかは仕様書が持つ**（`docs/specs/orchestrator-entry-hook.md` の B-1）。本 ADR に語彙を書き写さない（ADR 0004）
- **判定不能時に通す（決定6）ことで、fail-open な穴が1つ空く。** hook スクリプトが壊れれば検知は全滅する。デッドロック回避との引き換えであり、警告の可視化でしか埋め合わせていない
- **hook の前提は Claude Code の特定バージョンの実測に立脚する**（2.1.214 / 2026-07-18。payload のキー名・終了コード規約・サブエージェントで発火しないこと。詳細は仕様書の P-1〜P-3）。**バージョンが上がれば無症状で壊れうる。** 偽陰性が「検知パターンの穴」であるのに対し、これは**検知そのものが消える**種類の穴であり、fixture では検知できず実環境でしか気づけない
- **hook はローカルの `.claude/settings.json` に依存する。** CI では動かず、設定を外せば無効化できる。**この強制はリポジトリ外の実行環境に依存し、`review-trail` のような必須チェックとは強度が違う**（ADR 0009 の「保護設定はリポジトリ外にある」と同じ構造）
- **Issue #16 のスコープが本 ADR によって削られる（決定7）。** Issue の内容と実装の実体がずれる期間が生じる
- **旧 ADR に手を入れる先例を作る（決定8）。** ADR 0001 の不可変性を、解釈によって一段緩めることになる。緩め方を本 ADR で限定したが、限定が守られるかは規律に依る

## 検討した代替案

| 論点 | 却下した案 | 却下理由 |
|---|---|---|
| 強制手段 | 現状維持（ADR 0010 §D のまま既定入口に留める） | 既定は選択の初期値でしかなく、選択を止めない。ハーネスの効かない経路が開いたままになる |
| 強制手段 | rules への明記のみ（hook 無し） | ADR 0010 §D が却下した構図に戻る。強制手段の無い規律であり「規律に頼る規約は腐る」に該当する |
| 強制手段 | hook のみ（rules への明記なし） | 偽陰性の受け皿が無くなる。検知漏れがそのまま素通りする |
| 例外の指定 | 自然文フレーズの列挙（「直接やって」「自分でやって」等を許可表現とする） | 判定が曖昧で、言い換えが無限にある。列挙を増やすほど検知側と衝突し、**なし崩しに既定へ戻る** |
| 例外の指定 | 環境変数フラグ（`ORCHESTRATOR_BYPASS=1` 等） | 一度立てると恒久的に効き、**都度の意図的な選択にならない**。例外が既定に化ける |
| ブロック時の挙動 | 黙ってオーケストレーターへ委譲する | どちらの経路で処理すべきかの判断を AI 自身にさせる。ADR 0010 §D の握り潰し禁止と同じ構造で衝突する |
| ブロック時の挙動 | 警告を注入して続行する | 強制力が無く、ADR 0010 §D の却下理由（強制手段が要る）を克服できない。警告は無視できる |
| 判定不能時 | ブロックする（fail-closed） | 検査対象が人間の入力経路そのものであり、復旧に必要な指示すら送れなくなる。デッドロックになる |
| 名詞形の偽陽性 | 現状維持（名詞でもブロックする） | 仕様書 AC-3「質問・調査・説明は通す」と実挙動が食い違ったままになる。質問は最頻のやり取りであり、毎回 `[direct]` を打つ退化が常態化して hook が実質無効化される |
| 名詞形の偽陽性 | 質問形の語尾（`?` / 「教えて」/「説明して」）を除外条件にする | 「実装して。あとこれ説明して」のように**後置きで除外が成立**する。Issue #25 の往復4 C-1 で塞いだ「後置き文字列によるすり抜け」と同型の穴を新設することになる |
| 部分置換の表記 | ADR 0010 全体のステータスを `廃止` にする | 事実に反する。0010 の大半（A/B/C/E/F/G/Context）は生きている |
| 部分置換の表記 | ステータス行への併記のみ（節に注記を入れない） | §D は他 docs から名指しで参照されており、リンクを踏んだ読者・AI が覆された決定を生きたものとして読む |
| 部分置換の表記 | 0010 に一切手を入れず、0011 側からのみ参照する | 旧 ADR を先に読んだ側が置換に気づけない。ADR 0001 の運用ルール3が旧側の更新を求める趣旨に反する |

## 承認時に行う作業（適用済み）

**本 ADR は承認済みであり、以下は適用済みである。** 記録として残す（提案中の段階で先行適用しなかったのは、「置換された」と書いた時点で docs が虚偽になるためである）。
