# 0003. Lambda Function URL を IAM 認証で保護する

- **ステータス**: 承認済み（未決事項は ADR 0005 で解決済み）
- **日付**: 2026-07-16
- **決定者**: 人間（プロジェクトオーナー）

## コンテキスト

ADR 0002 で Lambda Function URL を採用した。Function URL は**インターネットから直接到達可能な HTTPS エンドポイント**であり、`authorization_type` に2つの選択肢がある。

- `NONE` — 誰でも叩ける
- `AWS_IAM` — SigV4 署名が必要

デモURLを README で公開する以上、URLは**必ず第三者に知られる**。「URLを知らせなければ安全」は成立しない。加えて Function URL のドメインは規則的な形式であり、秘匿性に依存した設計は成り立たない。

### `NONE` を選んだ場合に起きること

`NONE` は「認証を BFF 側でやるから Lambda 側は素通し」という発想で選ばれがちだが、これは**認証と到達可能性を混同している**。BFF にセッション認証を実装しても、攻撃者は BFF を経由せず Function URL を直接叩ける。BFF は迂回可能な checkpoint に過ぎない。

具体的な影響は3つある。

1. **業務ロジックの無認可実行** — 他人の勤務月を読み書きできる。BFF でしか認可していないなら、Lambda 側には誰であるかの情報すらない
2. **コスト増幅** — 呼ばれた分だけ課金される。攻撃コストはほぼゼロ、防御側は実費
3. **DB への到達** — Lambda 経由で Neon の無料枠（コンピュート時間・ストレージ）を消費させられる

このプロジェクトの文脈では 2 が特に効く。ADR 0002 で「月 $5 で無期限公開」という前提を置いた以上、**課金される呼び出しを誰でも発火できる状態は前提を破壊する**。

### 認証と到達可能性は別の層である

整理すると、必要な防御は2層ある。

| 層 | 問い | 担当 |
|---|---|---|
| 到達可能性 | **そもそも呼べるのは誰か** | Function URL の `AWS_IAM` |
| 認可 | 呼べる人の中で、**どのデータに触れてよいか** | BFF のセッション + ドメイン層 |

`NONE` はこの上段を空にする。上段が空なら、下段がどれだけ堅くても、下段を通らない経路が残る。

## 決定

**`authorization_type = "AWS_IAM"` を採用する。`NONE` は禁止する。**

これにより Function URL の呼び出しには SigV4 署名が必須になる。署名できるのは AWS 認証情報を持つ主体だけであり、**ブラウザからは構造的に到達できない**。「BFF を経由してのみ Lambda を呼ぶ」というアーキテクチャ上の制約が、規約ではなく仕組みとして担保される。

### 多層防御

IAM 認証は単独の対策ではない。**認証情報が漏れた場合**に何が起きるかを想定し、被害を有限にしておく。

| 層 | 対策 | 何を防ぐか |
|---|---|---|
| 到達可能性 | Function URL `AWS_IAM` | 無認可の第三者による直接呼び出し |
| 呼び出し権限 | IAM ポリシーを `lambda:InvokeFunctionUrl` の当該関数のみに限定 | 認証情報が漏れた際の、他 AWS リソースへの波及 |
| **課金の上限** | **予約同時実行数 = 5** | **認証情報が漏れても、課金の最悪値が構造的に有限になる** |
| 流量 | Route Handler のレート制限 | 正規経路を通る過剰リクエスト |
| 認可 | BFF セッション + ドメイン層の不変条件 | 正規利用者による他人のデータへのアクセス |
| 検知 | AWS Budgets（実績80% / 予測100%） | 上記すべてが破れた場合の事後検知 |

**予約同時実行数 = 5 がコスト面の最終防衛線**である点を強調しておく。IAM 認証が破られる（＝認証情報が漏れる）シナリオでも、同時実行数が5に固定されている限り、単位時間あたりの課金は上限が決まる。認証は「破られない」前提を置けないので、**破られた後に効く対策**を必ず1枚挟む。これが `NONE` + レート制限のみの構成との決定的な差になる。

### Terraform 上の表現

```hcl
# infra/terraform/function_url.tf
resource "aws_lambda_function_url" "api" {
  function_name      = aws_lambda_function.api.function_name
  authorization_type = "AWS_IAM" # NONE は禁止（ADR 0003）
}

# infra/terraform/lambda.tf
resource "aws_lambda_function" "api" {
  # ...
  reserved_concurrent_executions = 5 # コストの最終防衛線（ADR 0002 / 0003）
}
```

## 未決事項 → **ADR 0005 で解決済み**

> **この節は起票時点の記録である。** 結論は **ADR 0005**（案A の Vercel OIDC federation を採用）にある。以下の記述は、当時何が分かっていなかったかを残すためにそのまま保持する。
>
> なお本節は当初「決定後、本 ADR を廃止し新規 ADR を起こす」と書いていたが、**その方針は採らなかった**。本 ADR の決定（Function URL を IAM 認証で保護する）は覆っておらず、未決だった問いに答えが出ただけである。廃止扱いにすると「IAM 認証を見直した」と誤読される。判断は ADR 0005 に記録した。

**Vercel から AWS への認証情報をどう渡すか**が未決である。この判断は ADR を要するため、AI は決定しない。

CI/CD の AWS 認証は OIDC で確定している（静的アクセスキーを GitHub Secrets に置かない）。しかし **Vercel のランタイムから Lambda を SigV4 署名で呼ぶ**主体は CI ではなく、別途認証情報が必要になる。選択肢は2つある。

| 案 | 内容 | 懸念 |
|---|---|---|
| **A. Vercel OIDC federation** | Vercel が発行する OIDC トークンを AWS の IAM Role に federate し、静的キーを持たない | **Hobby プランで利用可能かの検証が必要**。利用可否がプランに依存する場合、この案は成立しない |
| **B. IAM ユーザーの静的キー** | 最小権限（`lambda:InvokeFunctionUrl` の当該関数のみ）の IAM ユーザーを作り、アクセスキーを Vercel の環境変数に置く | 「静的アクセスキーを使わない」という方針と**正面から衝突する**。ただし方針の原文は CI/CD 文脈であり、ランタイムに適用されるかは解釈の余地がある |

案 B を採る場合でも、予約同時実行数 5 により**キーが漏れた際の課金被害は有限**である点は変わらない。とはいえ、ポートフォリオとして「静的キーを使わない」と掲げながらランタイムで使うのは、説明を要する状態になる。

→ **A の実現可能性を検証したうえで、人間が判断する。**

## 影響

### 良い影響

- ブラウザから Lambda へ直接到達する経路が**存在しなくなる**。BFF 経由という制約がコードレビューではなく仕組みで守られる
- URL の秘匿性に依存しないため、README でデモURLを堂々と公開できる
- 認証情報の漏洩を想定した設計になっており、その想定自体がポートフォリオの説明材料になる

### 悪い影響 / コスト

- **BFF に SigV4 署名の実装が必要**になる。`apps/web/src/lib/lambda-client.ts` に集約する
- **ローカル開発で Lambda を直接 curl できない**。署名が必要になり、動作確認の手数が増える
- Vercel ランタイムの認証情報管理という**新しい問題を持ち込む**（→ 未決事項）
- **認証情報の漏洩が単一障害点**になる。予約同時実行数で被害は有限化されるが、ゼロではない

## 検討した代替案

| 案 | 却下理由 |
|---|---|
| `NONE` + BFF のセッション認証のみ | BFF を迂回して直接叩ける。認証と到達可能性の混同。**コスト増幅を防げず、ADR 0002 の前提を破壊する** |
| `NONE` + 共有シークレットヘッダ | 自前の認証を実装することになる。SigV4 と違い、リプレイ・タイミング攻撃・鍵ローテーションをすべて自前で正しく実装する必要がある。IAM で足りるものを自作する理由がない |
| API Gateway + WAF | Function URL より多機能だが、WAF は月 $5〜/ACL + ルール課金で**予算を単独で使い切る**（ADR 0002 の予算前提と衝突） |
| CloudFront + OAC → Function URL | 到達可能性の制御としては有効。ただし Vercel が既に CDN 層であり、その手前にもう1枚 CDN を置く構成は重複している。CloudFront 自体も設定を誤れば課金要素になる |
