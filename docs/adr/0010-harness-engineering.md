# 0010. ハーネスエンジニアリングの5構成要素を導入する

- **ステータス**: 承認済み
- **日付**: 2026-07-18
- **決定者**: 人間（プロジェクトオーナー）

## コンテキスト

このリポジトリは検証ハーネス（`docs/harness/verification-loop.md`）を持つが、ハーネスエンジニアリングの5構成要素（**Rules / Skills / Hooks / Feedback Loops / Context**）のうち、揃っているのは Rules と Feedback Loops の一部だけである。

| 要素 | 現状 | 実体 |
|---|---|---|
| Rules | ある | `CLAUDE.md`（9.6KB）/ `docs/ai-collaboration.md` / `.claude/settings.json` の `permissions` |
| Skills | **無い** | `.claude/skills/` が存在しない。手順（TDD の回し方、ADR の起こし方）は CLAUDE.md に散文で埋まっている |
| Hooks | **無い** | `.claude/settings.json` に `hooks` キーが無い。規約の強制が CI（push 後）まで遅延する |
| Feedback Loops | 一部ある | `make verify` と CI。ただしループの経緯が残らない。AI の試行錯誤はセッションが終われば消える |
| Context | **無い** | メモリ機構が無い。毎回 CLAUDE.md を読み直すのみ |

CLAUDE.md は「**判断の経緯がリポジトリに残っていないものは、存在しないものとして扱う**」と定めている。この基準を自身のハーネスに適用すると、5要素のうち3つ（Skills / Hooks / Context）は存在しないことになる。

加えて、AI駆動開発における責務分界の可視化はこのプロジェクトの主題そのものである（ADR 0001）。ハーネスの構成は主題の中核にあたるため、**会話で決めてリポジトリに残さないことを許容できない**。したがって本 ADR で決定を記録する。

導入にあたり、要求された各項目のうち **7点が既存の規約と衝突する**（論点A〜G）。本 ADR はその衝突の解決を含めて記録する。**実装は本 ADR の承認後に別 Issue へ切る**（仕様書・ADR のない実装をしない、CLAUDE.md）。

## 決定

**5構成要素をこのリポジトリに導入する。** 既存規約との衝突は以下のとおり解決する。決定者はいずれも人間である。

### A. 自己改善の境界 — 改変してよい範囲を列挙し、未列挙は禁止する

「ハーネスに問題が見つかった場合に自己改善させる」は、既存の2つの規約と正面から衝突する。検証ループは「テストを消す・skip する・アサーションを緩めることで Green にすることを禁止する。ハーネスが壊れれば、以降の Green はすべて無意味になる」と述べ、責務分界は「ガードレールを緩める必要が出た」を AI の停止条件に置いている。

衝突の本質は、**「ハーネスの改善」と「ハーネスの弱体化」が AI 自身からは区別できない**ことにある。どちらも「検査が通るようになった」という同じ観測結果を生む。

そこで、AI が承認なしに改変してよい範囲を**具体名で列挙**し、列挙されていないものは**既定で禁止**とする。

| 区分 | 対象 |
|---|---|
| 改変してよい | Skills の手順、サブエージェントへの指示文、ユーザー向けメッセージの文言 |
| 改変してはならない（人間の承認が要る） | 検査の閾値、許可リスト（依存ライブラリ・`domain` の許容 import）、停止条件、コストガードレール、ADR の決定 |

既定を禁止に倒すのは、CLAUDE.md の「許可リストにライブラリを黙って追加しない」と同じ思想である。**列挙されていない改変は、弱体化の疑いがある側に倒す。**

改変の検出手段は残された課題である。`.claude/` と `docs/harness/` の差分を CI で検知して人間のレビューを強制する案があるが、ADR 0009 で承認必須を廃止しているため、CODEOWNERS 的な強制は効かない。当面は**差分を CI の警告として可視化するに留め**、ブロックはしない。この限界は「悪い影響」に記録する。

### B. 規約の置き場所 — `docs/rules/` へ切り出し、CLAUDE.md から `@import` する

CLAUDE.md（9.6KB）の肥大化を rules として切り分ける要求は、ADR 0004 の「正解のデータは常に `docs/` にある」「二重管理を docs 内部に作り直さない」と衝突しうる。CLAUDE.md・`docs/ai-collaboration.md`・新設 rules の3箇所に規約が散れば、ADR 0004 が回避しようとした状態になる。

そこで、規約の実体は **`docs/rules/` に置き**、CLAUDE.md からは **`@import` で参照する**。

- 正解の実体が `docs/` 内に留まるため、ADR 0004 の「正解は docs」と整合する
- `@import` により、ツールは CLAUDE.md 経由で確実に規約本文を読む。`docs/rules/` を「読まれる保証のない場所」にしない
- `.claude/rules/` への切り出しは採らない。規約の実体が `docs/` の外に出て、ADR 0004 の例外を作るためである

**肥大化の測定基準は「毎回読まれるトークン量」とする。** バイト数や見出し数ではなく、セッションごとにコンテキストへ載る量で測る。測れない基準は守られない。

### C. ループ上限3回 — 実装↔レビューの反復回数であり、既存の停止条件とは別物

「フィードバックループ上限は3回」は、検証ループの既存の停止条件「同じ失敗で3回修正に失敗したら人間に相談」（`verification-loop.md`）と**同じ数字だが別の規則**である。

| 規則 | 主語 | 数える対象 |
|---|---|---|
| 既存（検証ループ） | AI 単独 | 同一の失敗に対する再試行 |
| 本 ADR（新規） | オーケストレーター↔工程エージェント | 実装工程→レビュー工程→実装工程…の往復 |

両者は主語も数える対象も異なるため、**別の規則として定義する**。ただし ADR 0004 が排除した二重管理（同じ数字が2箇所に載り、片方だけ変わっても誰も検知できない）を避けるため、**本 ADR に「なぜ別か」を明記し**、統合を将来にわたって禁じる。運用手順は `docs/harness/verification-loop.md` 側に追記する。

- 実装↔レビューの往復が **3回**を超えたら、停止条件に該当し**人間へ上げる**（下記 D の握り潰し禁止に乗る）
- 反復の**経緯は PR にコメントで残す**（Feedback Loops の要求「経緯を要約して PR にコメント」）。PR に残すのは*決定した仕様*ではなく*経緯・証跡*であり、ADR 0004 とは衝突しない（`spec-link` と同じプロセス側の性質）

### D. サブエージェント構成 — 工程で分割し、オーケストレーターを既定入口とする

サブエージェントを導入すると、`docs/ai-collaboration.md` の責務分界表（人間／AI の2者前提）が足りなくなる。オーケストレーターとサブエージェントの間の分界を持たないためである。

- **分割は工程で行う**（仕様 / テスト / 実装 / レビュー）。これは TDD のコミット規約（`docs:` → `test:` → `feat:`）と一致する。レイヤー分割（domain / usecase / adapter / driver）は採らない。工程エージェントは逐次かつ依存する（実装はテストが書いた `_test.go` を前提にする）ため、工程で分けるほうが受け渡しと整合する
- **オーケストレーターは既定の入口とする。人間の直接呼び出しは禁止しない。** 禁止するには強制手段が要り、「規律に頼る規約は腐る」という本リポジトリの立場と両立しないためである
- **停止条件は各サブエージェントが保持し、オーケストレーターは握り潰さず人間へ上げる。** 握り潰せるなら停止条件は実質存在しないことになる。この「握り潰し禁止」を規約として明文化する

責務分界表は、この2者（オーケストレーター／サブエージェント）の分界を含むよう拡張する（別 Issue）。

### E. worktree による並列 — 導入しない

「サブエージェント並列実行時、worktree によって競合を防止する」は導入しない。

理由は、本 ADR で採ったサブエージェント構成（D）が**逐次かつ依存**するためである。`isolation: worktree` は各エージェントに別の作業ツリーを与えて同時編集の競合を防ぐが、工程エージェントは実装がテストの未コミット変更を必要とするため、isolation は TDD の Red→Green の受け渡しを壊す。worktree が活きるのは互いに独立した並列タスクであり、1タスク内の工程ではない。

加えて、統合コストが効果を上回る蓋然性が高い。ADR 0009 でマージ方式を rebase 限定にしているため、並列ブランチを積むと後続 rebase が連鎖競合しうる。効果（並列による短縮）は未実測であり、Issue #10 の「上回らないなら入れない判断もありうる」に従う。

なお、`isolation: worktree` 方式そのものは `.claude/settings.json` の `deny`（`git reset *` / `git rebase *`）とは抵触しない（worktree の作成・破棄はハーネスが管理し、エージェントの Bash 呼び出しではない）。抵触を理由に見送るのではなく、**構成が逐次依存であること**を理由に見送る。将来サブエージェント構成が独立並列へ変わるなら、本決定は再検討の対象となる。

### F. プロンプトインジェクション対策 — 既存の性質を明示し、機械的に止められる範囲を Hook で止める

現状 `.claude/settings.json` の `deny` は `.env` / トークン / 鍵の読み出しを塞いでおり、**流出の後段は一定カバーされている**。決めるのは前段、すなわち信頼できない入力をどこまで想定するかである。

- **想定する入力源**: Issue / PR 本文・コメント、CI ログ、Web 取得内容、依存パッケージの README
- **既存の性質を対策として明示する**: ADR 0004 は「Issue のコメントは docs より優先されない」と定めている。これは**外部が書き込める場所を正解の置き場所にしない**という点で、インジェクション対策として機能する。この性質を対策として明示的に位置づける
- **機械的に止められる範囲は `PreToolUse` Hook で止める**。止められないものを「規約で禁止」と書くだけでは対策と呼べないため、Hook で検査する範囲と、規約に留まる範囲を分けて記録する（実装は別 Issue）

### G. 表記ルール — セッション回答を日本語に統一し、今後書く docs にのみ mermaid を適用する

- **「回答は全て日本語」** は、docs の記述言語ではなく、**セッション上でのエージェント回答（会話・ターミナル出力）を日本語に統一する**という振る舞いのルールである。docs は既にすべて日本語であり、これとは別の対象（エージェントの応答言語）を定める。既存の規約とは衝突しないため、Rules に明文化する
- **「図は mermaid 記法」** は、現在 docs 内に mermaid が1つも無く（すべて ASCII アート）、既存 ADR を書き換えると ADR 0001 の運用ルール3「ADR は書き換えず、追記もしない」に抵触する。したがって**今後書く docs にのみ適用**し、既存 ADR は据え置く。当面 ASCII と mermaid が混在するが、既存 ADR の不可変性を優先する

### Context（メモリ機構）— ループの作業記憶を導入する

5要素の Context は、B の Rules 切り出し（静的な規約）に加えて、**ループの作業記憶**（動的な状態）を導入して満たす。

- **格納するもの**: 進捗（`progress.md`）、過去のエラーログ、試行錯誤の履歴。次回以降のループで読み込む
- **格納しないもの**: 決定した仕様・設計。これらは従来どおり `docs/` に置く。progress.md はプロセス状態のみを持つ
- **優先順位は `docs/` > `progress.md`**。ADR 0004 の「Issue コメントは docs より優先されない」と同じ構造。さもないと「古い作業記憶を次ループが正しいと信じて実装する」という、このリポジトリが最も警戒する陳腐化の失敗モードを、メモリ機構が新たに持ち込む
- **置き場所とライフサイクル**: `.gitignore` してローカルに保持し、**タスク完了 / PR マージで破棄**する。リポジトリ履歴を汚さず、docs との二重管理も避ける。恒久的な証跡の要約は PR コメント（C）に残るため、progress.md は使い捨ての作業記憶に徹する

### ADR の分割単位 — 本 ADR 1本に集約する

論点A〜G と2つのメタ決定は、「ハーネスの5構成要素を導入するか」という**単一の決定**の内部構造である。ADR 0001 は「すべてを ADR にすると誰も読まなくなる」と粒度に釘を刺している。個別に ADR を割ると数が増えて読まれにくくなるため、**本 ADR 1本にまとめ**、各論点は節として記録する。将来いずれかの決定だけが覆る場合は、その時点で当該論点を切り出した新 ADR を起こす。

## 影響

### 良い影響

- ハーネスの5要素が「主張」ではなく「記録された決定」になる。自身のハーネスに CLAUDE.md の基準（経緯が残らないものは存在しない）を適用した結果を、ポートフォリオとして示せる
- 自己改善の境界（A）を具体名で列挙したことで、AI が自分の制約を自分で緩める構造を、既定禁止で塞げる
- 規約の実体を `docs/rules/` に集約（B）することで、CLAUDE.md の肥大化を解きつつ ADR 0004 の「正解は docs」を保てる
- ループ上限（C）を既存の停止条件と別物として記録したことで、同じ数字が二重管理される事故を将来にわたり防げる
- サブエージェントの停止条件（D）を握り潰し禁止として明文化したことで、多段化しても停止条件が形骸化しない

### 悪い影響 / コスト

- **自己改善の改変を機械的にブロックできない（A）。** ADR 0009 で承認必須を廃止しているため、差分は CI の警告として可視化するに留まり、マージは止まらない。改変が弱体化かどうかの最終判断は、人間のレビューに依存する。「検出できないものは人間が持つ」という既存の分界の帰結だが、限界として記録する
- **表記が当面混在する（G）。** 既存 ADR は ASCII、今後の docs は mermaid になる。統一されるのは十分に時間が経った後である
- **メモリ機構が新たな陳腐化リスクを持ち込みうる（Context）。** 優先順位（docs > progress.md）とライフサイクル（タスク完了で破棄）で抑えるが、ライフサイクルの運用が緩めば、古い作業記憶を次ループが信じる失敗モードが再発する
- **サブエージェント導入で責務分界表の拡張が必要になる（D）。** 拡張前に運用を始めると、オーケストレーターとサブエージェントの分界が未定義のまま動くことになる。実装 Issue の順序で、表の拡張を先行させる必要がある
- **並列化の短縮を放棄する（E）。** 逐次実行のままとなり、独立タスクが増えた場合の速度上限は上がらない

## 検討した代替案

| 論点 | 却下した案 | 却下理由 |
|---|---|---|
| A | 全面的に自己改善を許す | ハーネスの信頼性を放棄する。「許可リストを黙って追加しない」と両立しない |
| A | 提案までに限る（全て人間承認） | 既存の停止条件と整合するが「自己改善」と呼べず、ループの自律性が上がらない |
| B | `.claude/rules/` へ切り出し | 規約の実体が `docs/` の外に出て、ADR 0004 の「正解は docs」の例外を作る |
| B | 現状維持（CLAUDE.md 単体） | 肥大化の閾値を決めないままで、いつ破綻するか誰も判断できない |
| C | 既存の停止条件と同一扱いにする | 主語（AI単独 vs オーケストレーター↔工程）と数える対象（同一失敗 vs 実装↔レビュー往復）が異なり、同一視できない |
| D | レイヤーで分割（domain/usecase/adapter/driver） | ADR 0008 とは一致するが、逐次依存する工程の受け渡しと整合せず、TDD のコミット規約ともずれる |
| D | 直接呼び出しを禁止する | 強制手段が要り、「規律に頼る規約は腐る」立場と両立しない |
| E | worktree 並列を導入する | 構成が逐次依存のため isolation が Red→Green の受け渡しを壊す。統合コストが効果を上回る蓋然性が高く、効果は未実測 |
| F | 規約の明文化のみ（Hook なし） | 止められないものを「規約で禁止」と書くだけでは対策と呼べない |
| G | 既存 ADR も mermaid に書き換える | ADR 0001 の書き換え禁止に抵触する |
| メタ | 複数 ADR に分割する | 単一の決定の内部構造であり、分割すると数が増えて読まれにくくなる（ADR 0001 の粒度の指摘） |

## 承認後に切る実装 Issue

本 ADR の承認後、以下を別 Issue として切る（仕様書・ADR のない実装をしない）。

1. 責務分界表の拡張（オーケストレーター／サブエージェントの分界を追加）— D の前提
2. `docs/rules/` への規約切り出しと CLAUDE.md の `@import` 化 — B
3. Skills の作成（TDD の回し方、ADR 起票手順など）
4. サブエージェント定義（`.claude/agents/` に工程別＋オーケストレーター）— D
5. Hooks の導入（`PreToolUse` のインジェクション検査、握り潰し禁止の担保）— D / F
6. メモリ機構（`progress.md` 等の作業記憶、`.gitignore`、ライフサイクル）— Context
7. `docs/harness/verification-loop.md` への実装↔レビューループ上限3の追記（既存の停止条件との別物明記）— C
8. 自己改善の改変許可リストの明文化と CI 差分警告 — A
9. 表記ルール（日本語必須 / mermaid）の Rules への明文化 — G
