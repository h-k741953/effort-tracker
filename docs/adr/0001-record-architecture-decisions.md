# 0001. アーキテクチャ決定を記録する

- **ステータス**: 承認済み
- **日付**: 2026-07-16
- **決定者**: 人間（プロジェクトオーナー）

## コンテキスト

このプロジェクトは案件獲得用ポートフォリオを兼ねており、目的の一つは「AI駆動開発における人間とAIの責務分界を可視化すること」である。

その目的に対して、コードだけを見せるのでは不十分である。コードは「何を作ったか」しか語らず、**「なぜそれを選んだか」「何を捨てたか」「誰が決めたか」**を語らない。技術力の証明としては、後者のほうが希少性が高い。

さらに、AIが実装の大部分を担う開発では、意思決定の経緯がチャットログに埋もれる。チャットログは消える。消えた判断は、数ヶ月後に「なぜこうなっているのか分からないコード」として負債化する。AIは過去の会話を参照できないので、記録がなければ**AI自身が過去の決定を破る**。

判断の記録先として、以下を検討した。

- **コード内コメント**: 局所的な理由は書けるが、「ECS を使わない」のような不在の理由を書く場所がない
- **README**: 読者は利用者。意思決定の履歴を置くと肥大化して本来の役割を果たさなくなる
- **Wiki / 外部ツール**: コードとバージョンが同期しない。PR レビューの対象にならない
- **ADR**: 上記の弱点をすべて回避できる

## 決定

**アーキテクチャ上の決定を ADR (Architecture Decision Record) として `docs/adr/` に記録する。**

Michael Nygard が提唱した形式を採用する。

### 運用ルール

1. **連番 + ケバブケース**でファイル名を付ける（例: `0002-serverless-over-ecs.md`）
2. 各 ADR は **ステータス / 日付 / 決定者 / コンテキスト / 決定 / 影響 / 検討した代替案**を持つ
3. **ADR は書き換えず、追記もしない**。決定が覆った場合は新しい ADR を起こし、古いほうのステータスを `廃止（0005 により置換）` に変更する。これは「決定が変わった事実」自体が記録に値するため
4. **「決定者」を必ず明記する**。人間が決めたのか AI が決めたのかを区別することは、このプロジェクトの主題そのものである
5. ADR を要する判断の範囲は `docs/ai-collaboration.md` の責務分界表に従う。**技術選定の変更は人間の承認が必要**であり、AI が単独で ADR を「承認済み」で起票しない

### ステータスの遷移

```
提案中 → 承認済み → 廃止（NNNN により置換）
```

## 影響

### 良い影響

- 「なぜ NAT Gateway を使わないのか」のような**不在の設計判断**を記録できる。不在の判断はコードには現れないが、コストとセキュリティに最も効く
- AI が過去の決定を参照できる。CLAUDE.md から ADR を参照させることで、AI が独断で覆すことを防げる
- PR レビューの対象になる。決定がコードと同じ重みでレビューされる

### 悪い影響 / コスト

- 判断のたびにドキュメント作成のオーバーヘッドが乗る
- **粒度の判断が必要**。すべてを ADR にすると誰も読まなくなる。目安として「後から覆すのが高価な決定」「不在の理由を説明する必要がある決定」に限る
- 追記禁止ルールにより、細かい修正でも新規 ADR が必要になる場面がある

## 検討した代替案

| 案 | 却下理由 |
|---|---|
| 記録しない | プロジェクトの目的（責務分界の可視化）を達成できない |
| README に集約 | 読者層が違う。肥大化して README が機能しなくなる |
| GitHub Wiki | コードとバージョンが同期せず、PR レビューに乗らない |
| RFC 形式 | 提案・議論のプロセスが重い。単独開発には過剰 |
