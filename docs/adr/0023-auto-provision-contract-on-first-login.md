# 0023. ログインした技術者に、初回ログイン時にシステムが契約を1件自動で用意する

- **ステータス**: 提案中
- **日付**: 2026-10-29
- **決定者**: 人間（プロジェクトオーナー）。2026-10-29 に、discussion #142 について AskUserQuestion で明示選択した（main セッション経由で受領）。本文の起草は仕様工程

> 決定の中身は、人間が 2026-10-29 に明示選択したもの（下の決定1〜3）と、人間が推奨を受けて選んだ根拠（「検討した代替案」の却下理由）である。この ADR の文面は **AI（仕様工程）が起草した**。AI は ADR を「承認済み」で起票しないため（ADR 0001 運用ルール5）、ステータスは「提案中」とする。
>
> 本 ADR は、**ADR 0021 のうち次の2か所を、下の決定の範囲に限って置き換える**ことを提案する。ADR 0021 のほかの決定（4画面の採否・契約期間・稼働の推移・フォント・祝日）は置き換えない。
>
> - 決定1「採らないもの」の「契約の管理（CRUD）。契約一覧は**閲覧のみ**であり、契約の作成・変更・削除の画面も操作も作らない」のうち、**システムが契約を作成することまで禁じると読める部分**
> - 決定2 の「契約の管理（CRUD）は**作らない**ものとする。契約のデータはデモデータとして投入する。投入の手段は実装工程が決める」のうち、**契約のデータの出所をデモデータに限る部分**
>
> 利用者が契約を作成・変更・削除する画面と操作を作らないこと（契約の管理（CRUD）を非スコープとすること）は、ADR 0021 のまま変わらない（決定2）。
>
> **ADR 0021 には手を入れていない**（ADR 0001 運用ルール3）。本 ADR が承認されたとき、ADR 0021 の側に置換を示すかどうか、示すならどの形にするかは決まっていない（下の「未決のまま残るもの」U-A）。

## コンテキスト

1. **ログインした技術者は入力と締めを体験できない** — `docs/specs/demo-data-reset.md`（#56）は、デモの契約を固定の技術者識別子だけに付けると決めた（同 Q-4 (a)）。Cognito でログインした利用者の `sub` を指す契約は無い。このため `Engineer` として入っても、本人の勤務月の一覧・契約一覧・稼働の推移は空になり、稼働実績の入力（UC1）も締め（UC2）も行えない（同 AC-13-1）。#56 はこの穴を扱わず、「契約を作る口を足すか」を discussion #142 へ切り出した
2. **契約は与件であり、作る手段を持たないと定めてきた** — ADR 0021 決定1・決定2、`docs/rules/scope.md`「契約一覧」、`docs/domain/ubiquitous-language.md`「契約が持つもの（参照系）」、`docs/specs/workmonth-implementation-design.md` AC-6-2・AC-9-17-c・AC-10-21 ②・AC-13-7 は、契約のデータをデモデータとして投入し、作成・更新の手段を設けないと定めている。`docs/specs/demo-data-reset.md` Q-4 は、起草時に「(c) 契約を利用者ごとに用意する」を、この定めに反するとして退けていた
3. **既に決まっている制約** — `X-Actor-Id` に載せるのは検証済みトークンの `sub` だけである（`docs/specs/bff-auth-termination.md` AC-5-2）。利用者のデータとゲスト向けデモ勤務月群は、技術者識別子で分ける（`docs/specs/demo-data-reset.md` Q-5 (a)）。閲覧系の画面は名指しした4つに限る（`docs/rules/scope.md`）

## 決定

### 1. ログインした技術者には、初回ログイン時に、システムが契約を1件自動で用意する

- 用意するのはシステムの内部処理であり、利用者の操作ではない
- 用意する場所・用意する契約の中身・日次リセットでの扱いは、本 ADR の決定に含まれない（「未決のまま残るもの」）

### 2. 画面を作らない。契約の管理（CRUD）は非スコープのままとする

- 契約を作成・変更・削除する画面も、利用者がそれを行う操作も作らない（ADR 0021 決定1 の閲覧のみの契約一覧、`docs/specs/contracts-ui.md` AC-4-1・AC-6-2 を変えない）
- 閲覧系の画面は名指しした4つのままであり、画面を加えない

### 3. 業務ユースケースを増やさない

- 自動で用意することはシステムの内部処理であり、業務ユースケースを増やさない。業務ユースケースは3つのまま変えない
- 集約は `WorkMonth` の1つのままである。契約は与件であり、集約の外にある（ADR 0021 決定2 を変えない。これは決定1・2 からの帰結であり、新しい決定ではない）

決定を受け入れ条件に落とした仕様は `docs/specs/engineer-contract-provisioning.md` である。

## 影響

### 良い影響

- **ログインした技術者が、デモで稼働実績の入力（UC1）と締め（UC2）を体験できる**ようになる
- **`X-Actor-Id`＝`sub` を保てる**（`docs/specs/bff-auth-termination.md` AC-5-2）。用意する契約の技術者は、その利用者の `sub` である
- **技術者識別子による分離を保てる**（`docs/specs/demo-data-reset.md` Q-5 (a)）。訪問者は、それぞれ自分の `sub` を技術者とする契約を持ち、他の訪問者の契約と勤務月に入力しない
- **認証情報を公開しない**。共有アカウントを作らない
- **画面と業務ユースケースの数が変わらない**。4画面の限定（`docs/rules/scope.md`）を保つ

### 悪い影響 / トレードオフ

- **契約のテーブルへ書き込む経路が、デモデータの投入（リセット用 Lambda の中に閉じる＝`docs/specs/demo-data-reset.md` AC-5-2）のほかに1つ増える。** 「契約は読み取り専用の与件」と定めた条文（`docs/specs/workmonth-implementation-design.md` AC-6-2・AC-9-17-c・AC-10-21 ②・AC-13-7）は、書き込みをどの層が持つかが決まった時点で改める必要がある
- **「契約を作る手段を作らない」との境界を、別の形で守ることになる。** 利用者が値を与えて契約を作る口にならないこと（技術者を `sub` だけから決め、外から契約の値を受け取らないこと）が要る。その方法は未決である
- **デモの契約以外の契約の行が、運用の中で生じる。** `docs/specs/demo-data-reset.md` U-8 の決定（初回デプロイの前に、そうした行が無いことを人が確かめる）は初回デプロイの前の手順として残るが、その後は自動で用意した行が生じる。日次リセットでそれをどう扱うかは未決である
- **同じ人でも、ログイン方式ごとに別の契約を持つ。** 方式ごとに別の `sub` になる（`docs/specs/cognito-auth-infra.md` AC-4-6）ため、決定1 の「1件」は `sub` ごとに数えることになる
- **承認の体験は変わらない。** ある訪問者が締めた勤務月は、承認待ち一覧が承認待ちの勤務月を技術者横断で返す（`docs/specs/domain-api-http-contract.md` AC-3-2）ため、承認者として入った他の訪問者にも見える。自分の勤務月は自己承認の排除（`docs/specs/approval.md` D-4）により自分で承認できない。この扱いをどうするかは未決である（`docs/specs/engineer-contract-provisioning.md` Q-9）

## 検討した代替案

却下理由は、2026-10-29 に人間が推奨を受けて選んだときの根拠である。

| 案 | 却下理由 |
|---|---|
| (a) 現状維持（ログインした技術者には体験させない） | デモで誰も UC1・UC2 を体験できない |
| 契約を作る画面を足す | 閲覧系の画面を名指しの4つに限る定め（`docs/rules/scope.md`）を保てない。自動で用意する方式なら画面を足さずに済む |
| (b) BFF が、ログインした技術者を共有のデモ技術者へ写す | `X-Actor-Id`＝`sub`（`docs/specs/bff-auth-termination.md` AC-5-2）に反する。訪問者どうしが同じ技術者の勤務月に入力し、干渉する |
| (d) Cognito の共有アカウントを公開する | 認証情報を公開することになる。訪問者どうしが干渉する（`docs/specs/demo-data-reset.md` Q-4 (d) の評価では、訪問者が他の訪問者を締め出せる） |
