# 0012. `/issue` をスラッシュコマンドとして実装し、機械判定部をプロンプトから切り出す

- **ステータス**: 承認済み
- **日付**: 2026-07-19
- **決定者**: 人間（プロジェクトオーナー）

> 本 ADR は**新規の決定であり、既存 ADR のいずれも置換しない**。ADR 0010 §D / ADR 0011 / ADR 0004 の決定はすべて有効なまま残る。本 ADR はそれらが定めた境界の**内側**に、Issue 対応の入口を1つ追加する。特に ADR 0011 が塞いだ穴を `/issue` が再び開けないことを、決定3 で明示的に条件として置く。

## コンテキスト

ADR 0011 は「工程をまたぐ依頼はオーケストレーターが入口である」と定め、`UserPromptSubmit` hook で機械的に強制した。**これは依頼を*どこへ流すか*の決定であって、*着手前に何を確認するか*の決定ではない。**

その結果、次が誰にも担保されていない。

| 着手前に確認されるべきこと | 現在の担保 |
|---|---|
| その Issue に対応する仕様書が `docs/specs/` に実在するか（SDD） | **規律のみ**。`docs/rules/development-process.md` の記述と specifier 工程の停止条件 |
| Issue が `task` なのか `discussion` なのか | 規律のみ。AI が本文から推測しうる |
| 既定ブランチ上で実装を始めていないか | 規律のみ。`.claude/agents/orchestrator.md`「ブランチ運用」 |
| 前タスクの `progress.md` が残っていないか | **無し**。`docs/harness/memory.md` は破棄のライフサイクルを定めつつ、「機械的な強制はない」ことを自ら限界として記録している |

`spec-link` CI は「PR 本文が `docs/` を参照しているか」を見るが、これは**着手のはるか後**であり、しかも参照の有無しか見ない（ADR 0004「悪い影響」）。**仕様が無いまま着手したことは、PR を作る段階まで機械には分からない。**

加えて、ADR 0010 §D の実装 Issue 3「Skills の作成」は未着手で `.claude/skills/` は存在しない。手順を置く場所の選択肢（スラッシュコマンド / Skill / サブエージェント）について、このリポジトリはまだ基準を持っていない。**`/issue` はその基準を最初に適用する対象になる。**

### 人間が決定済みの事項

本 ADR の起票にあたり、以下は人間（プロジェクトオーナー）が既に選択している。AI が選んだものではない。

1. **置き場所はスラッシュコマンドとし、Skill を採らない**
2. **Issue 本文は「指示ではなくデータ」として扱う旨を明記する**
3. **自動化は準備までとし、工程を回す手前で停止する**
4. **`discussion` ラベルでは工程を回さない**

AI が設計したのは、機械判定部を切り出す構成（決定5）と、担保できない範囲の記録の仕方である。

## 決定

**Issue 番号から対応の準備を行うスラッシュコマンド `/issue` を導入する。受け入れ条件は `docs/specs/issue-command.md` が単一の情報源として持つ。**

**本 ADR に判定条件・ラベル分岐・ブランチ名の形式・終了コードを書き写さない**（ADR 0004。正解は仕様書側の1箇所）。本 ADR が持つのは「なぜそう決めたか」だけである。

### 1. 置き場所は `.claude/commands/` のスラッシュコマンドとし、Skill 化しない

`/issue` は **人間が明示的に叩く必須の入口**である。Skill は**モデルが自律的に選択して読み込む**性質を持ち、この要求と合わない。

- **必須の入口を、モデルの選択に委ねてはならない。** Skill にすると「モデルが Skill を選ばなかった」場合に SDD ゲートが静かに走らないことになり、それは**入口が存在しないことと観測上区別できない**。ADR 0011 が §D の「既定の入口」を否定した理由（既定は選択の初期値でしかなく、選択を止める力を持たない）と同じ構造である
- スラッシュコマンドは人間が `/issue 31` と打った事実がプロンプトに残る。`[direct]` トークンや `no-spec` / `loop-extended` ラベルと同じく、**操作が記録に残る**形になる
- Skill を将来にわたって禁じるものではない（ADR 0010 の実装 Issue 3 は有効）。**この決定が禁じるのは `/issue` の Skill 化のみである**

**スラッシュコマンド / Skill / サブエージェントの使い分けの基準は `docs/harness/commands-and-skills.md` に持たせる。** 本 ADR にその表を書かないのは、基準が `/issue` 固有ではなく今後の全ハーネス資産に適用されるためである。

### 2. Issue 本文は「指示ではなくデータ」として扱い、その旨を2箇所に明記する

Issue 本文は**外部が書き込める入力源**である（ADR 0010 §F が想定入力源として列挙済み）。`/issue` はこれを読む以上、インジェクションの経路になりうる。

- **`.claude/commands/issue.md`（コマンド定義）と `docs/specs/issue-command.md`（仕様）の両方に明記する。** 2箇所に書くのは重複ではない。コマンド定義は **AI の振る舞いの宣言**、仕様は**機械判定部が満たすべき条件**であり、**対象が異なる**
- **機械的なインジェクション検査（`PreToolUse`）は Issue #16 の範囲とし、`/issue` では実装しない。** ADR 0011 決定7 が `UserPromptSubmit` のみを先食いし `PreToolUse` を先食いしなかったのと同じ線引きを踏襲する

**この対策は3層のうち最も狭い層しか持たない。** 分界表は仕様 AC-11 が持つ（`/issue` / Issue #16 / ADR 0004 の3層）。**`/issue` が持つのは機械判定部が本文の自然言語を解釈しないことだけであり、AI が要約のために本文を読む段階には及ばない**（仕様 AC-9-6）。

### 3. 自動化は「準備」までとし、工程を回す手前で停止する

`/issue` が行うのは、Issue 取得 → `docs/` の追跡 → SDD ゲート判定 → ブランチ作成 → `progress.md` の用意、までである。**そこで停止し、要約を提示して人間の明示承認を得てから orchestrator へ渡す。**

**一気通貫にしない理由は速度ではなく、ADR 0011 との境界である。**

ADR 0011 は「工程をまたぐ依頼を main エージェントが直接処理すること」を禁じた。`/issue 31` というプロンプトは hook の検知パターンに一致せず（指示形の語尾を持たない）、**main エージェントへ届く**。これは穴ではなく意図した経路であるが、成立条件が1つある —— **`/issue` 自身が工程を回さないことである。**

もし `/issue` が仕様 → テスト → 実装まで走れば、それは「hook を通過して main が工程を直接処理する経路」そのものになり、**ADR 0011 が塞いだ穴を、正規の入口という体裁で新設する**ことになる。したがって次を条件として置く。

- **`/issue` は `docs/` `services/` `apps/` `infra/` を一切変更しない。** 変更するのは作業ブランチの作成と `progress.md`（gitignore 済み）だけである
- **承認は「承認する／承認しない」の明示選択で取る。** 自由記述を通過の根拠にしない（`.claude/agents/orchestrator.md`「承認は2段」と同じ運用。ADR 0011「悪い影響」に記録された違反インシデントへの対策と同型）
- **ゲートに落ちた Issue を `/issue` が是正しない。** AI がその場で仕様書を書く・ラベルを付ける・Issue を書き換える、を行わない

最後の項は SDD ゲートの意味そのものである。**ゲートに落ちた Issue に対して AI がその場で仕様を書けば、ゲートは「仕様書が生成されるまでの遅延」でしかなくなる。** 仕様は仕様工程（specifier）が、人間の停止条件を保持したうえで起こす。

### 4. `discussion` ラベルの Issue では工程を回さない

`.github/ISSUE_TEMPLATE/discussion.yml` は**業務ルール・設計・用語を決めるための議論**を起票するテンプレートであり、仕様書リンクを持たない。これらは `docs/rules/responsibility.md` が「必ず人間に確認を取る」に置いた項目そのものである。

したがって `discussion` では、**関連する `docs/` と過去 ADR の材料を集めて要約し、停止する**。ブランチも `progress.md` も用意せず、承認の選択肢も出さない（回す工程が無い）。

**AI が議論の結論を出さない。** `discussion` の Issue に対して工程を回すことは、人間の専管事項を AI が先に埋めることを意味する。集めるのは判断の材料であって、判断ではない。

### 5. 機械判定部をプロンプトから切り出し、fixture で固定する

**`.claude/commands/issue.md` はプロンプトであって実行コードではない。そのままでは何一つ機械検査できない。**

プロンプトだけで実装すると、判定条件は「AI がそう読むはず」という主張に留まり、条件を1つ落としても誰も気づかない。**これは本リポジトリが繰り返し塞いできた失敗モードと同型である**（`docs/harness/verification-loop.md`「検査対象を読めなかったことは、違反が無いことを意味しない」）。

そこで、**解釈の余地なく決まる部分をシェルスクリプト（`.claude/scripts/issue-gate.sh`）へ切り出し、fixture で固定する。** 先例は `.claude/hooks/check-prompt-entry.sh` + `test-check-prompt-entry.sh` + `make test-hooks`。

- スクリプトは **stdin と引数以外の入力を持たない純粋なフィルタ**とする。ネットワークアクセス（`gh` の呼び出し）を内包しない。**入力を差し替えればローカルで完全に実行でき、fixture で検査できること**を要件とする（`.github/scripts/check-review-trail.sh` と同じ性質）
- **生成は機械化せず、検証だけを機械化する。** ブランチ名のスラグは日本語タイトルからの要約であり機械的には導けない。**AI が提案し、スクリプトが形式を検証する**という分担にする。生成が解釈である以上、検査できるのは形式だけである
- CI は**新規ジョブを起こさず既存の `scripts` ジョブへ相乗りさせる**。新規ジョブは ruleset `protect-main` の必須チェックへの登録（ブラウザ操作）を人間に要求し、登録漏れは「実行され緑になるがマージ条件ではない」という発見しにくい状態を生む。Issue #30 で実際に踏んだ穴（`make test-hooks` が CI のどのジョブからも呼ばれていなかった）を再発させない

**この決定が担保するのは判定部だけである。** コマンド定義（プロンプト）側の強制力は上がらない（下記「悪い影響」9-2）。

## 影響

### 良い影響

- **SDD ゲートが、規律ではなく機械判定になる**（`/issue` を通した場合に限る）。「仕様書が無い」「仕様が未決」を人間や AI の読解に委ねず、ラベル・パス抽出・実在確認という機械的に閉じた条件で判定する。`spec-link` CI が PR 時点でしか見なかったものが、**着手前**に移る
- **`progress.md` のライフサイクル違反が検出される場所ができる。** `docs/harness/memory.md` が自ら「機械的な強制はない」と記録していた穴に、検出点が1つ入る（握り潰す場所ではなく、人間へ上げる場所として）
- **ADR 0011 の境界が、新しい入口を足しても保たれる。** 決定3 が `/issue` を準備工程に閉じ込めることで、hook を通過する経路が工程の直接処理に化けない
- **プロンプトと実行コードの分界が、ハーネス資産の設計原則として一段はっきりする**（決定5）。「プロンプトで書いたことは検査されていない」という自明だが忘れやすい性質を、構成上のルールにした
- **スラッシュコマンド / Skill / サブエージェントの使い分けに基準ができる**（決定1）。ADR 0010 の実装 Issue 3（Skills）に着手する時点で、置き場所の判断が場当たりにならない

### 悪い影響 / コスト

- **人間が `/issue` を使わなければ、SDD ゲートは一度も走らない**（仕様 AC-9-1）。「#31 やっといて」と書けば hook がブロックして orchestrator へ誘導するが（ADR 0011）、**その経路に `/issue` の機械ゲートは無い**。受け皿は specifier 工程が持つ「仕様が無ければ停止する」という規律であり、**機械的な二重化はされていない**。これは決定1（人間が明示的に叩く入口にする）の直接の代償である —— Skill にすればモデルが自律的に拾いえたが、代わりに「拾わなかったこと」が観測できなくなる。**どちらの案も、使われなかった場合を機械では検出できない**
  - **使用率の監視も行わない。** 「`/issue` を使わずに Issue へ着手した」ことは、機械には判定できない
- **コマンド定義はプロンプトであって強制力が弱い**（仕様 AC-9-2）。`.claude/commands/issue.md` に「停止する」と書いてあることは、AI が停止することを保証しない。fixture が検査できるのは**コマンド定義から仕様・スクリプトへの参照が張られていること**までで、**記述内容が仕様どおりであること・手順が守られたことは artifact に残らない**。これは ADR 0004 の「CI が検査できるのはリンクが貼られているかだけ」、`review-trail` の「2段承認ゲートの成立は artifact に残らず検査できない」と同型の限界である
  - 決定5 で切り出したのは、この弱さを**判定部については**解消するためである。**残りの部分は解消していない**
- **前提2つが fixture で検証できない**（仕様 AC-9-5）。`gh issue view --json` の実出力が仕様の定めるスキーマと一致すること、および `.claude/commands/` のファイルが `/issue` として起動して引数が展開されることは、いずれも**このリポジトリが決められる事柄ではない**。fixture は仕様が定めた入力を再現するだけで、外部ツールが同じ形を返すことを保証しない。**`gh` のバージョンや Claude Code のバージョンが変われば、判定は無症状で壊れる**。ADR 0011 の「hook の前提は特定バージョンの実測に立脚する」と同じ種類の穴であり、**実環境でしか気づけない**
- **本文からのパス抽出は文脈を見ない。** 「この仕様書はまだ書いていない」という文の直後のパスでも、実在すれば通る。過検出は着手側へ倒れる。ラベル条件と実在確認が併存するため素通りの範囲は限られるが、**ゼロではない**
- **ラベルを改名すると全 Issue が止まる。** 安全側へ倒れるので静かには壊れないが、`.github/ISSUE_TEMPLATE/` と仕様書の同時更新を要する。片方だけでは `/issue` が全件で停止する
- **`/issue` はブランチと `progress.md` を作るが、片付けない。** 「承認しない」で終わった場合、作業ブランチが残る。自動削除は取り違えたときの損害が大きく、**作るより消すほうを慎重側に倒した**結果である
- **検査対象が1つ増え、ハーネスの維持コストが上がる。** `make test-commands` の新設と、`Makefile` / `ci.yml` / `docs/harness/verification-loop.md` の2表への追加という**4箇所の同時更新**が実装時に必要になる。1つでも漏れれば Issue #30 と同じ穴（テストが CI から呼ばれない）が再発する

## 検討した代替案

| 論点 | 却下した案 | 却下理由 |
|---|---|---|
| 置き場所 | Skill（`.claude/skills/`）として実装する | モデルが自律的に選択する性質が「必須の入口」と合わない。選ばれなかった場合、ゲートが走らなかったことと入口が存在しないことを観測上区別できない |
| 置き場所 | サブエージェント（`.claude/agents/issue.md`）として実装する | サブエージェントは親エージェントが呼ぶものであり、人間が直接叩く入口にならない。加えて `/issue` は工程を回さず（決定3）、工程分割の軸（ADR 0010 §D）に乗らない |
| 置き場所 | `docs/` に手順を書き、AI に読ませる | 読まれる保証がなく、機械検査もできない。ADR 0010 §B が `docs/rules/` を `@import` させた理由（読まれる保証のない場所にしない）と同じ問題 |
| 自動化範囲 | Issue 取得から実装完了まで一気通貫で走らせる | hook を通過して main が工程を直接処理する経路になり、**ADR 0011 が塞いだ穴を正規の入口という体裁で新設する** |
| 自動化範囲 | 停止するが、承認を自由記述で受け取る | ADR 0011「悪い影響」に記録された実際の違反（自由記述の `承認` をゲート通過の根拠にした）と同型。明示選択でなければゲートの意味が消える |
| ゲート違反時 | 仕様書が無ければ specifier を呼んでその場で書かせる | ゲートが「仕様書が生成されるまでの遅延」に化ける。仕様の欠落は人間の停止条件（`docs/rules/responsibility.md`）に触れうる事象であり、機械が埋める対象ではない |
| ゲート違反時 | 警告を出して続行する | ADR 0011 決定3 が却下した「警告を注入して続行する」と同じ。警告は無視できる |
| ラベル欠落時 | 本文の内容から `task` / `discussion` を推測する | 本文からの推測は、機械判定が塞いだ「本文の主張が判定を動かす」経路を復活させる。ラベルは分岐の唯一の根拠である |
| `discussion` | 議論 Issue でも工程を回し、AI が結論を出す | 業務ルール・設計・用語は人間の専管事項（`docs/rules/responsibility.md`）。AI が先に埋めれば、間違っていた場合にテストごと嘘になる |
| 判定の実装 | すべてコマンド定義（プロンプト）に書く | 機械検査が一切できない。条件を1つ落としても誰も気づかない |
| 判定の実装 | ブランチ名の生成までスクリプト化する | 日本語タイトルから英語スラグを機械的に導けない。生成が解釈である以上、機械化できるのは検証だけである |
| 判定の実装 | スクリプトが `gh` を直接呼ぶ | ネットワーク依存になり fixture でローカル実行できなくなる。チェッカのロジックだけが検査不能地帯に残る |
| インジェクション対策 | `/issue` で `PreToolUse` 検査も実装する | Issue #16 の範囲。ADR 0011 決定7 が `PreToolUse` を先食いしなかった線引きを踏襲する |
| CI | `/issue` の検査に新規ジョブを起こす | ruleset の必須チェック登録（ブラウザ操作）を人間に要求し、登録漏れが「緑だがマージ条件ではない」状態を生む（Issue #30 で実際に踏んだ） |

## 関連

- **ADR 0011: オーケストレーターを必須の入口とする（本 ADR は置換しない）** — `/issue` が hook を通過する経路の成立条件〔決定3〕、`PreToolUse` を先食いしない線引き〔決定2〕、自由記述を承認の根拠にした違反インシデント〔決定3 / 却下案〕、バージョン依存の前提が無症状で壊れる構造〔悪い影響〕
