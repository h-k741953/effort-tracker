# 0009. ブランチ保護を ruleset に一本化し、承認必須をやめる

- **ステータス**: 承認済み
- **日付**: 2026-07-17
- **決定者**: 人間（プロジェクトオーナー）

## コンテキスト

`develop`（デフォルトブランチ）に、**2層の保護が同時に乗っていた**。

| 層 | 要求 |
|---|---|
| classic branch protection | 承認 **1件必須**、`enforce_admins: true` |
| ruleset `protect-main`（`~DEFAULT_BRANCH` を対象） | PR 必須、承認 **0件**、必須チェック3本、linear history |

GitHub は両方を評価し、**厳しいほうが勝つ**。したがって実効的な要件は「承認1件」だった。

この構成で **PR #3 がマージ不能になった**。

- リポジトリの collaborator は `h-k741953` 1人だけであり、PR #3 の author でもある
- **GitHub は自己承認を許さない**
- `enforce_admins: true` により管理者バイパスも無い
- ruleset の `bypass_actors` は空

チェックは5本すべて成功し `mergeable: MERGEABLE` でありながら、`mergeStateStatus: BLOCKED` で止まる。**コードの問題ではなく、単独開発では原理的に満たせない要件を課していたことによる詰みである。**

さらに2層構造そのものが調査を誤らせた。classic branch protection だけを見ると `required_status_checks` が無く、「CI がマージ条件になっていない」と読める。実際には ruleset が必須チェックを持っており、この読みは誤りである。**保護の実態が1箇所を見ても分からない状態になっていた。**

加えて、必須チェックの一覧に穴があった。`spec-link` と `Terraform (fmt / validate)` は全 PR で実行され成功していたが、**必須チェックに入っておらず、マージ条件ではなかった**。CLAUDE.md は spec-link を「必須」と書いているため、**規約とハーネスが食い違っていた**。

## 決定

**ブランチ保護を ruleset `protect-main` に一本化する。**

1. **`develop` の classic branch protection を削除する。** ruleset を唯一の真実とする
2. **承認要件は 0 のままとする。** 人間のレビューをマージ条件にしない
3. **必須チェックを 3 本から 5 本に増やす。** `spec-link` と `Terraform (fmt / validate)` を追加し、実行される全チェックを必須にする

結果としてマージのゲートは、**人間の承認ではなく機械的検査のみ**になる。

### 承認要件を 0 にする理由

**単独開発では、承認要件は満たせないか、さもなくば体裁でしかないためである。**

自己承認は GitHub が禁じている。2人目のアカウントや bot を collaborator に足せば要件は満たせるが、それは**承認の体裁だけを作る操作**であり、レビューは行われない。形骸化した承認は、記録として嘘になる。

そして、このプロジェクトはもともと**機械的検査を信頼の根拠に置いている**。CLAUDE.md は依存規約について「この規約はレビューでは腐るため、CI で import を機械的に検査する」と述べている。承認要件を捨てて必須チェックを増やす本決定は、**その主張を保護設定にも一貫させるものである**。

### ruleset を残し classic を消す理由

- ruleset は `~DEFAULT_BRANCH` を対象とするため、デフォルトブランチが変わっても追従する。classic は `develop` という名前に固定される
- 必須チェックを持っているのは ruleset のほうである

## 影響

### 良い影響

- **PR #3 のマージ不能が解ける。** 以後、単独開発である限りマージが詰まらない
- **保護の実態が1箇所を見れば分かる。** 2層を突き合わせる必要がなくなり、本 ADR のコンテキストに書いた誤読が構造的に起きなくなる
- **spec-link が規約から機械的ゲートに昇格する。** CLAUDE.md と ADR 0004 が「必須」と書いていたものが、初めて実際にマージ条件になる
- **Terraform の fmt / validate が #8 の前に閉じる。** `infra/` を本格的に書き始める前に、未通過のままマージされる経路が消える

### 悪い影響 / コスト

- **人間のレビューによるゲートを、明示的に放棄する。** 設計として壊れているコードは、CI さえ通れば入る。CI が見るのは lint / test / `domain` の依存方向 / secret / `docs` 参照の**有無**だけであり、**設計の妥当性も、仕様の正しさも、誰も検査しない**。単独開発では元から成立していなかった要件だが、「無かったこと」と「捨てたこと」は別であり、後者として記録する
- **2人目が入ったら再検討を要する。** 本決定の根拠は「collaborator が1人であること」に全面的に依存しており、前提が変われば根拠ごと消える
- **保護設定はリポジトリに存在しない。** GitHub 上の設定であり、コードと同じ PR レビューには乗らず、変更されても差分に現れない。ADR 0001 が Wiki を却下した理由（コードとバージョンが同期しない）が、そのまま当てはまる。**本 ADR は決定を記録するが、設定が ADR どおりである保証は与えない**。Terraform の GitHub provider による codify は #8 のスコープ外として見送る
- **`no-spec` ラベルの運用がマージ条件に直結する。** ADR 0004 は「`no-spec` の形骸化リスク」を挙げていたが、これまでラベルの有無はマージを止めなかった。今後は止める。ラベルを付け忘れた chore PR は、ラベルを付けるまでマージできない
- **ruleset 名 `protect-main` が実態とずれる。** 対象は `~DEFAULT_BRANCH` であり、デフォルトブランチは `develop` である。本 ADR では改名しない

## 検討した代替案

| 案 | 却下理由 |
|---|---|
| 承認要件 1 のまま、2人目の collaborator / bot を追加 | 要件は満たせるが、レビューは行われない。**承認の体裁だけが記録に残る**。形骸化した承認は嘘になる |
| `enforce_admins` を無効化し、管理者としてバイパス | 承認1件必須というルールを残したまま、常にバイパスすることになる。**ルールが装飾になり**、バイパスした事実も記録に残らない。ポートフォリオとして説明できない |
| classic を残し、承認要件だけ 1 → 0 に変更 | マージは通るが**2層構造が残る**。「どちらの層が効いているのか」が設定を2箇所見ないと分からない状態が続く。実際にその誤読が起きている |
| ruleset を削除し classic に一本化 | classic は対象ブランチ名が固定であり、デフォルトブランチの変更に追従しない。必須チェックを持っているのも ruleset のほうであり、移し替える作業が無駄 |
| 必須チェックを3本のままにする | `spec-link` は CLAUDE.md と ADR 0004 が「必須」と明記している。**規約が要求するものをハーネスが強制していない状態**を残す理由が無い |
